## 0. 한 줄 요약

**프로젝트 하나에 문서·일정·정산이 전부 묶여 있어서, "지금 어디까지 갔나"를 한 곳에서 답할 수 있게 한다.**

Excel·Drive·채팅으로 흩어진 정보를 합치는 게 아니라, **애초에 흩어질 수 없는 구조**를 만드는 것이 목적이다.

## 1. 최상위 4영역

서비스는 네 영역으로 나뉜다. **프로젝트가 전부를 품지 않는다.**

| 영역 | 프로젝트와의 관계 | 내용 |
|------|-----------------|------|
| **공고 / 입찰** | **이전** | 크롤링 링크 등록 → 크롤링 → 입찰정보 → AI 요약 → **프로젝트 생성** |
| **프로젝트** | 본체 | 스테이지 > 스텝 > 블록 / 이슈 / 로그 |
| **재무** | **밖 · 병렬** | 세금계산서, 입금내역, 실적 |
| **조직 · 계정** | **밖 · 기반** | 사원, 부서, 사업 카테고리, 계정 · 권한 |

**중요**: 입찰정보·크롤링 링크는 **블록이 아니다.** 프로젝트가 생기기 전 단계의 독립 기능이다.

### 1-1. 공고 → 프로젝트 전환 · 재크롤링 ⚠️

| 항목 | 확정 |
|------|------|
| 전환 시 | 공고 값을 프로젝트로 **스냅샷 복사** + 원문 링크 유지 |
| 재크롤링 주기 | 공고 목록은 **주기적 자동** |
| **프로젝트가 된 건** | **자동 재크롤링 안 함.** 원문 링크만 두거나 수동 버튼 |
| 재크롤링 결과 | **프로젝트 값을 절대 덮지 않는다.** `원본 변경됨` 배지 → 사람이 반영 여부 결정 → 반영 시 로그 |

§8-3 버전 고정과 **같은 원리**다. 기초금액 3억을 보고 참여 결재를 올렸는데 정정공고로 2억이 되고 그게 조용히 덮이면, **그 결재 기록은 거짓이 된다.**

## 2. 프로젝트 내부 계층

| 계층 | 정체 | 갖는 것 | **안 갖는 것** |
|------|------|--------|--------------|
| **프로젝트** | 최상위 소유자 | 참여자, 기간, 상태, 진척률, 권한 기본값 | — |
| **스테이지** | **스텝 묶음 라벨** | 이름, 순서 | **상태 · 권한 · 데이터** |
| **스텝** | **노션의 페이지** | 이름, 순서, 기간, 책임자, 완료 여부, 권한 | **도메인 의미(타입)** |
| **블록** | **실제 기능** | 타입별 데이터와 행위 전부 | — |
| **이슈** | **지라의 티켓** | 담당자, 기한, 상태 3단 | 진척률 반영 |

### 왜 이렇게 나눴나

- **스텝에는 타입이 없다.** 스텝 이름이 `2차 정산`이든 `중도금`이든 시스템은 모른다. 도메인 의미는 전부 **블록**이 갖는다. 이래야 회사마다 다른 업무 절차를 담을 수 있다.
- **스테이지는 분류일 뿐이다.** 권한·상태를 저장하지 않는다. 저장 지점이 3층(프로젝트/스테이지/스텝)이 되면 "이 사람이 이 스텝을 고칠 수 있나"를 사람이 추적할 수 없어진다.
- **모듈(M1 입찰 · M2 제안 · M3 수행 · M4 정산 · M5 외주)은 런타임 개념이 아니다.** 스테이지/스텝을 미리 깔아주는 **템플릿**일 뿐이다(§13). DB 에 `module` 테이블은 없다.

### 프로젝트 상태

```
진행 전  →  진행 중  →  정산 중  →  완료
   ↓          ↓
       종결 (미참여 / 유찰 / 미선정 / 취소)   ← 사유 필수
```

- **생성 경로 2개**: ① 공고 클릭 ② 직접 생성. **공고 없는 프로젝트가 정상 케이스다** (B2B 는 계약부터 시작).
- **종결도 프로젝트다.** 실무상 대다수가 종결로 끝난다. 그 사유가 쌓여야 "이 발주처 이 유형은 마진이 안 난다"를 데이터로 말할 수 있다. 목록이 지저분해지는 건 **조회 필터로 푼다.**
- 기간(시작일·종료일)은 **사용자가 직접 설정**한다. 자동 계산하지 않는다.

### 참여자 · 담당팀

| 항목 | 확정 |
|------|------|
| **참여자** | **개인 단위로만 확정** |
| **담당팀(부서)** | **집계용 라벨 + 인력 선택 후보 필터.** 참여자를 자동으로 늘리지 않는다 |

⛔ **팀을 넣었다고 팀원 전원을 참여자로 만들지 마라.** 팀에 인턴이 배정되는 순간 진행 중인 모든 프로젝트에 참여자로 들어가고 견적·단가가 다 보인다. §6-1 에서 부서 상속을 버린 것과 **정확히 같은 실패**다.

담당팀을 남기는 이유는 `EXECUTIVE` 의 전사 현황에서 **부서별 집계**가 필요하기 때문이다.

### 금액 필드 — 프로젝트 속성이다

| 값 | 출처 |
|-----|------|
| 기초금액 · 추정가격 | 공고에서 복사 |
| 투찰금액 · 낙찰가 · 순위 | 실무자 입력 |
| **계약금액(도급금액)** | 계약 시 입력. **§7-3 잔액 계산이 이 값에 의존한다** |

⛔ **블록에 저장하지 마라.** 블록·스텝은 사용자가 자유 편집하므로 금액이 스텝 재배치에 따라 사라질 수 있다. **블록은 입력 UI 일 뿐, 값은 프로젝트 필드에 쓴다** — 입금확인 블록과 같은 패턴이다.

> **수익성 분석(마진 계산)은 범위 밖이다.** 인건비 집계가 공수 관리라는 별도 도메인을 요구한다. 따라서 **투입 공수 · 외주비 집계 필드는 만들지 않는다.**

## 3. 블록

### 3-1. 기본 규칙

| 항목 | 확정 |
|------|------|
| 소유자 | **전부 스텝.** 예외 없음 |
| 타입 | **닫힌 enum.** 확장형 JSON 스키마 금지 |
| 테이블 | `block` 공통 테이블 + **타입별 상세 테이블** |
| 공통 컬럼 | `step_id`, **`project_id`(비정규화)**, `type`, `order`, 작성자, 생성/수정 시각 |

`project_id` 를 비정규화로 들고 있는 이유 — 프로젝트 전역 조회(대시보드, 정산 현황)가 **스텝 조인 없이** 되어야 한다.

닫힌 enum 으로 가는 이유:
1. 도메인 블록(입금확인·결재)은 JSON 에 안 들어간다. 매칭·상태머신·권한 제약이 붙는다.
2. "확장 가능"은 환상이다. 새 타입을 넣어도 **프론트에 렌더러가 없으면 못 쓴다** → 결국 매번 배포한다.

### 3-2. 블록 타입 목록

| 계열 | 타입 | 성격 |
|------|------|------|
| 콘텐츠 | 텍스트 · 이미지 · 파일 업로드 · 체크리스트 · 메모 | 자기 데이터를 갖는다 |
| 도메인 | **입금확인** · 세금계산서 조회 · 실적 조회 | **재무 영역 데이터를 읽기만 한다** |
| 프로세스 | **결재 상신** | 자체 상태머신 + 알림 |
| 외부 | AI 블록 | 파이썬 서버 연동 |

> 계열은 **설명을 위한 구분**이지 상속 계층이 아니다. 소유자는 전부 스텝으로 동일하다.

### 3-3. 체크리스트 vs 이슈 — 헷갈리지 마라

| | **체크리스트 블록** | **이슈** |
|---|-------------------|---------|
| 목적 | 내가 빠뜨리지 않으려는 확인 | **남에게 시키는 일** |
| 담당자 | **없음** | 필수 |
| 기한 | **없음** | 있음 |
| 알림 | 없음 | 발생 |
| 조회 | 그 블록 안에서만 | 칸반 · 내 이슈 · 대시보드 |
| 예 | `회사소개서 최신본 첨부 ☑` | `제안서 초안 — 김민수 — 8/13` |

**한 줄 규칙: 담당자와 기한이 붙으면 이슈, 안 붙으면 체크리스트.**
체크리스트 항목에서 `이슈로 승격` 버튼으로 이슈를 만들 수 있고, 그 이슈가 완료되면 항목도 자동 체크된다.

> ⛔ 체크리스트에 담당자·기한을 넣지 마라. 넣는 순간 이슈와 구분이 사라지고, 알림·마감관리·`내 할일` 인프라를 통째로 복제해야 한다.

## 4. 이슈

| 항목 | 확정 |
|------|------|
| 소유자 | **스텝** |
| 생성 | **스텝에서만** |
| 번호 | **프로젝트 전역 시퀀스** (`ISSUE-101`) |
| 조회 축 | **스텝 / 프로젝트 / 담당자(user_pk)** — 3축 |
| 이동 | `step_id` 변경으로 가능. 번호 유지 + 이동 이력 기록 |
| 상태 | 3단 (시작 전 / 진행 중 / 완료) |

**소유가 스텝인 이유**: "이 스텝의 이슈 3/5" 라는 분모가 나와야 한다. 프로젝트 소유면 분모가 성립하지 않는다.
**스텝 페이지의 `일정(ISSUE)` 탭은 필터 뷰**다. 소유가 아니다.

⚠️ **이슈가 달린 스텝을 삭제할 때는 이슈를 어디로 보낼지 물어야 한다.** 조용히 같이 지우면 이력이 증발한다.

## 5. 진척 · 완료

| 항목 | 확정 |
|------|------|
| **프로젝트 진척률** | **완료 스텝 / 전체 스텝 — 단일 원천** |
| 스텝 완료 | **수동 버튼.** 이슈가 미완료여도 완료 가능 |
| 누가 누르나 | **스텝 편집 권한자 전부** |
| 스텝 상태 | 미시작 / 진행 중 / 완료 (3상태) |
| 이슈 진척도 | **보조 지표.** 프로젝트 % 에 절대 섞지 않는다 |

### 왜 이슈를 진척률에 안 섞나

이슈는 자유 생성이다. 꼼꼼한 사람이 이슈를 20개로 쪼개면 진척률이 낮게 나온다.
**일 잘하는 사람이 지표에서 손해 보는 순간 아무도 이슈를 안 만든다.**

### 왜 자동 완료가 아닌가

이슈가 0개인 스텝이 정상 케이스다(`공고 확인`, `계약` 은 문서만으로 끝난다).
`0/0` 을 100% 로 보면 스텝 만들자마자 완료되고, 미완료로 보면 영원히 안 끝난다. 둘 다 못 쓴다.

⚠️ **완료된 스텝에 미완료 이슈가 남으면 유령이 된다.** 완료 버튼을 누를 때 미완료 이슈 수를 보여주고 `그대로 두기 / 함께 종료` 를 고르게 한다. 남은 이슈에는 `완료된 스텝` 배지를 단다.

## 6. 권한

권한은 **두 층**이다. 전역 role 이 탭을 열고, 프로젝트 권한이 그 안을 통제한다.

### 6-1. 전역 role

| role | 탭 | 추가 권한 |
|------|-----|----------|
| `DEVELOPER` | — | ADMIN 계정 발급 |
| `ADMIN` | 관리자 | **총관리자.** 전 데이터 수정 가능 — 단 **로그에 `ADMIN 권한으로 수정` 표기 필수** |
| `EXECUTIVE` | 전사 현황 | 전 프로젝트 **읽기 전용** |
| `FINANCE` | 재무 | 입금 확정 · 프로젝트 매칭 |
| `BIDDING` | 공고 / 입찰 | 크롤링 링크 관리 |
| `MEMBER` | 프로젝트 | 기본 |

- **다중 부여** (`user_roles` N:M). 대표는 `ADMIN` + `EXECUTIVE` 처럼 겹쳐 받는다.
- **부여는 전부 인원별 직접 지정.** 부서에서 상속하지 않는다.
- **부서는 조직도 전용.** 권한과 무관하다.
- **`MASTER` role 은 없다.** Master 는 결재선의 마지막 노드일 뿐이다 (§8-1).
- **`QUALITY` role 은 없다.** 품질검토는 결재선의 한 노드다 (§8-1).

#### 왜 부서 상속이 아닌가

| 방식 | 부여를 잊었을 때 | 실패 방향 |
|------|---------------|----------|
| 부서 상속 | 재무부서 인턴이 배정 즉시 **입금을 확정할 수 있다** | 열리는 방향 ❌ |
| **인원별 지정** | 재무 담당자가 재무 탭을 **못 본다** → 즉시 신고 들어옴 | 닫히는 방향 ✅ |

**권한은 잊었을 때 닫히는 쪽으로 실패해야 한다.**

#### 탭을 만드는 기준

**프로젝트 밖에 자기 데이터가 있는 영역만 탭이 된다.**
품질검토는 프로젝트 안 결재선에서 일어나므로 탭이 없고, 따라서 role 도 없다.

### 6-2. 프로젝트 권한

| 항목 | 확정 |
|------|------|
| 레벨 | **3단** — 뷰어 / 편집자 / 관리자 |
| 저장 층 | **2층** — 프로젝트(기본값) + 스텝(오버라이드) |
| 스테이지 | **권한을 저장하지 않는다.** 화면에서 "하위 스텝 일괄 적용" 편의 기능은 가능하나, 데이터는 스텝에만 떨어진다 |
| 기본값 | 참여 인원 등록 시 부여한 권한 → 스텝에서 개별 변경 |
| 권한 없을 때 | **잠금** (보이되 못 고침). 숨김은 별도 옵션 |

### 6-3. 블록 타입별 추가 제약

**권한은 "사람 × 스텝" 만으로 끝나지 않는다. 블록 타입에도 걸린다.**

| 블록 | 제약 |
|------|------|
| 입금확인 | **프로젝트 쪽은 전원 읽기 전용.** 확인 표시는 재무만 확정 |

실무자가 입금을 스스로 체크할 수 있으면 "받았다고 쳤는데 실제론 안 들어옴"이 생기고, 그 순간 정산 데이터를 아무도 못 믿는다.

## 7. 재무 경계 — 이 서비스의 핵심 이음매

### 7-1. 어디에 사나

**재무 도메인(세금계산서 · 입금내역 · 실적)은 프로젝트 밖 전사 영역이다.**

이유:
1. 재무부서는 프로젝트 참여자가 아니다. 프로젝트 안에 두면 전 프로젝트에 참여자로 넣어야 한다.
2. 재무의 동선은 "프로젝트별"이 아니라 **"이번 달 입금 예정 전체"** 다.
3. 홈택스·뱅킹 API 로 들어온 데이터는 애초에 어느 스텝 소속으로 들어올 수 없다. 들어온 뒤 프로젝트에 **매칭**되는 것이다.

### 7-2. 계획과 실행의 분리

| | 누가 | 어디서 |
|---|------|--------|
| **계획** (정산 회차 · 비율 · 청구조건) | **실무자** | 프로젝트 |
| **실행** (세금계산서 발행 · 입금 확정) | **재무** | 재무 영역 |

계약 조건(60/20/20)을 아는 건 계약을 따온 실무자지 재무가 아니다. 재무는 돈이 실제로 오갔는지만 확정한다.

### 7-3. 정산 회차 = 스텝 + 블록

**정산 3회차 = 스텝 3개, 각 스텝에 입금확인 블록 1개.**

정산 시점은 흩어진다(선급금 즉시 · 기성 6개월 뒤 · 잔금 1년 뒤). 각 회차가 `청구조건 → 청구서 → 품질검토 → 세금계산서 → 입금확인` 5단계를 각각 도는데, **절차 단위가 곧 스텝**이다.

**입금확인 블록이 곧 정산 회차 그 자체다.** 별도 회차 레코드를 두지 않는다 — 두면 블록과 이중 관리가 되고, 어긋났을 때 어느 쪽이 맞는지 아무도 모른다.

### 7-4. 매칭은 2단이다 ⚠️

```
① 프로젝트 매칭  (필수)      ← 블록이 없어도 가능
② 블록 연결      (선택)      ← 블록이 생기면 그때 연결
```

**돈은 블록보다 먼저 들어올 수 있다.** 계약 직후 선급금이 들어왔는데 실무자는 아직 정산 스텝을 안 팠을 수 있다. 1단만 있으면 그 입금은 시스템 밖에서 떠돈다 — Excel 시절과 똑같아진다.

### 7-5. 삭제 잠금 ⚠️

**입금이 연결된 블록과 그 블록이 든 스텝은 삭제할 수 없다.** 연결 해제는 재무만 할 수 있다.

### 7-6. 자동 매칭의 한계

은행 입금 적요에 용역명은 안 온다. 회사명 축약만 온다. 금액도 자주 안 맞는다(분할입금 · 상계 · 지연이자).

**자동 매칭은 "추천 후보 정렬"까지만. 확정 버튼은 사람이 누른다.** 오매칭이 정산 데이터를 오염시키면 되돌리기가 매우 비싸다.

## 8. 결재 · 파일 버전

### 8-1. 결재선

- 결재선은 **결재 상신 블록 안에서** 설정한다.
- **회사 템플릿에서 불러올 수 있다** (`일반 결재선` · `고액 결재선` 등).
- ⛔ **금액대별 자동 결정 규칙은 만들지 마라.** 기준이 회사마다 다르고 자주 바뀐다. 규칙 엔진을 넣으면 "왜 이 사람이 결재선에 있지"를 설명 못 하고, 기준이 바뀔 때마다 개발자를 불러야 한다. **템플릿을 여러 개 두고 사람이 고른다.**
- **Master = 결재선의 마지막 노드.** role 이 아니다. 5천만원 이하는 본부장이, 초과는 대표가 Master 인 식으로 **건마다 달라진다.**
- **품질검토도 결재선의 한 노드다.** 결재선에 `품질관리실 박OO` 를 넣으면 그게 곧 품질검토고, `승인/반려` 가 곧 `적정/보완` 이다. 품질관리실이 없는 회사는 그 노드를 안 넣으면 된다.
- 진행은 **순차**다.

### 8-2. 결재 대상 — 파일 블록을 지목한다 ⚠️

**결재 블록에 문서를 직접 업로드하지 마라.** 같은 스텝의 **파일 업로드 블록을 지목**한다.

직접 업로드하면 파일 블록의 원본과 결재본이 갈라져서 어느 게 최종본인지 모르게 된다. **`보고서_최종2.xlsx` 문제를 시스템 안에서 다시 만드는 것이다.**

### 8-3. 버전 고정 (freeze)

```
결재 상신  →  대상 파일의 그 시점 버전(v4)을 고정
                 ↓
   진행 중 새 버전(v5) 업로드는 허용
   단 결재 대상은 v4 유지 + `대상보다 새 버전 있음` 경고 배지
                 ↓
   승인 완료  →  "v4 승인됨" 이 영구 기록
```

버전 고정이 없으면 대표가 v4 를 보고 승인했는데 다음 날 v5 로 바뀌어 있게 된다. **그 승인은 무엇에 대한 승인인가 — 결재 이력이 거짓이 된다.**

### 8-4. 반려 · 재상신 ⚠️

**재개 지점은 대상 버전이 바뀌었는지로 시스템이 자동 판정한다.**

| 재상신 시 | 어디서 재개 | 근거 |
|-----------|------------|------|
| 대상 버전 그대로 | **반려 지점부터** | 앞 결재자가 본 것과 같은 문서다 |
| **대상 버전이 바뀜** (v4→v5) | **처음부터 전원 재승인** | 앞 결재자가 **본 적 없는** 문서다 |

항상 반려 지점부터 재개하면, 앞 결재자가 본 적 없는 v5 가 그들의 승인을 달고 통과한다. **버전 고정을 넣은 이유가 여기서 무너진다.**

자동 판정이 가능한 것은 §8-3 에서 버전을 고정했기 때문이다. 사람이 판단할 필요도, 설정할 필요도 없다.

### 8-5. 그 외 규칙

| 항목 | 확정 |
|------|------|
| 반려 사유 | **필수** (UC-08 의 "보완사유"). 사유 없는 반려는 재작업을 못 하게 만든다 |
| 상신자 회수 | **첫 결재자가 승인하기 전까지만** 가능 |
| 완료 후 취소 | **불가.** 되돌리려면 새 결재를 올린다 |
| 알림 | 활성화된 결재자에게 **액션 요구 알림** (§9) |

## 9. 알림

**두 종류를 절대 섞지 마라.**

| 종류 | 예 | 대상 | 형태 |
|------|-----|------|------|
| **액션 요구** | 이슈 배정 · 결재 상신 · 기한 임박(D-7/3/1) · 품질검토 요청 · 반려 | 특정 개인 | **뱃지.** 처리할 때까지 안 사라짐 |

블록 수정 전부를 뱃지로 쏘면 하루 수십 개가 쌓이고, 사람들은 알림을 끈다. **알림을 끄면 결재 상신도 못 본다.**

|------|------|
| 표시 조건 | **날짜가 있으면 자동으로 뜬다.** 별도 등록 스위치 없음 |

### 왜 등록 스위치를 안 쓰나

스위치는 날짜와 별개인 **두 번째 상태**다. `날짜는 있는데 스위치가 꺼진` 조합이 생기고, 그 일정은 존재하는데 아무 데도 안 뜬다. **그리고 아무도 그 사실을 모른다.**
**사람이 켜야 뜨는 일정은 사람이 잊으면 사라지는 일정이다.**

### 등급

| 등급 | 대상 | 표시 |
|------|------|------|
| **불가역** | 투찰마감 · 개찰일 | 빨강 · 이동 불가 · **필터로도 못 끔** · D-7/3/1 강제 알림 |
| 계획 | 스텝 기간 | 막대(구간). 드래그 조정 가능 |
| 작업 | 이슈 마감 | 점. 담당자에게 강조 |
| 예정 | 정산 예정일 | 흐리게. 조건 충족 시 진해짐 |

투찰마감을 놓치면 프로젝트가 통째로 죽는다. 스텝 기간을 하루 미루는 것과 같은 무게로 그리면 안 된다.

## 11. 삭제 정책 · 로그

### 11-1. 전면 soft delete

**하드 삭제는 없다.** 모든 삭제는 `deleted_at` 플래그다.

로그가 참조하는 대상이 물리적으로 사라지면 **로그가 고아 문자열이 된다.** `제안서_초안_v1.docx 를 업로드했습니다` 라는 로그가 있는데 그 블록이 사라지면 무엇을 가리키는지 알 수 없다. 이력 관리가 이 서비스의 존재 이유인데 그게 삭제 한 번에 깨진다.

### 11-2. 잠금 대상은 셋뿐 ⚠️

| 대상 | 규칙 |
|------|------|
| **입금이 연결된** 입금확인 블록 | 삭제 불가. **재무가 연결 해제해야** |
| **진행 중인** 결재 블록 | 삭제 불가. 회수하거나 완료해야 |
| **결재 대상으로 지목된** 파일 블록 | 결재 진행 중에만 삭제 불가 |

나머지는 전부 그냥 soft delete. **잠금을 늘리지 마라** — 잠금이 많으면 사용자가 지우지도 못하고 왜 안 되는지도 모른다.

### 11-3. 계층별 삭제

| 대상 | 규칙 |
|------|------|
| 블록 | soft delete (§11-2 잠금 제외) |
| 스텝 | 잠금 블록이 있으면 불가. **이슈는 `이동 / 함께 종료` 를 고르게 한다** |
| 스테이지 | **하위 스텝을 어느 스테이지로 옮길지만 고른다.** 스테이지는 라벨이므로 스텝을 같이 지울 이유가 없다 |
| 프로젝트 | **`진행 전` + 스텝·블록이 하나도 없을 때만** 삭제 가능. 그 외엔 `종결(취소)` 로 남긴다 |

**안 한 프로젝트도 데이터다.** 종결 사유가 쌓여야 수익성 환류가 된다 (§2).

> **보관 기능은 없다.** 목록 정리는 상태 필터로 한다.

### 11-4. 로그

**로그는 블록 활동(등록 · 수정 · 삭제) 기록이다.** 이슈에 매달리는 게 아니다.

**로그는 어떤 경우에도 삭제하지 않는다.**

⚠️ **로그는 대상 이름을 복사해서 저장한다.** FK 만 들고 있으면 대상이 지워질 때 표시가 깨진다.

```
log:  actor=김민수  action=UPLOAD  target_type=BLOCK  target_id=812
      target_name="제안서_초안_v1.docx"    ← 스냅샷. 원본이 사라져도 읽힌다
```

`ADMIN` 이 총관리자 권한으로 남의 데이터를 고치면 로그에 **`ADMIN 권한으로 수정`** 을 반드시 표기한다 (§6-1).

## 12. 페이지 체계

### 12-1. 최상위 탭 = 4영역 (§1)

| 탭 | 여는 role |
|-----|----------|
| 공고 / 입찰 | `BIDDING` |
| 프로젝트 | `MEMBER` |
| 재무 | `FINANCE` |
| 전사 현황 | `EXECUTIVE` |
| 관리자 | `ADMIN` |

### 12-2. 프로젝트 내부

**사이드바가 내비게이션이고, 사이드바 자체가 프로젝트 개요다.** 별도 `개요` 화면을 만들지 않는다.

```
사이드바                                  본문
─────────────────────────────            ─────────────────────────
프로젝트 정보 (이름·기간·상태·진척)
                                          ▸ 스텝 클릭
── 프로젝트 메뉴 ──                          [ 블록 | 이슈 | 활동기록 ]
   이슈 · 문서 · 정산 · 활동기록 · 설정
                                          ▸ 프로젝트 메뉴 클릭
── 진행 단계 ──  [+스텝추가]                 해당 화면
   스테이지 ˅ > 스텝 목록

참여자
```

| 메뉴 | 내용 |
|------|------|
| 이슈 | 전체 칸반 (스텝 필터) |
| **문서** | 파일 업로드 블록의 파일만 모은 **디렉토리 뷰**. 결재 상태는 안 가짐 |
| **정산** | **조회 전용.** 회차별 `청구 / 계산서 / 입금` |
| 활동기록 | 프로젝트 전체 로그 (스텝 필터) |
| 설정 | 참여자 · 권한 · 상태 · 종결 처리 |

- 스텝 탭은 `블록 / **이슈** / 활동기록`. (`일정` 아님)
- 스텝 탭과 프로젝트 메뉴에 `이슈`·`활동기록`이 둘 다 있는 건 중복이 아니라 **스코프 다른 뷰**다.

### 12-3. 문서 메뉴 ⚠️

- **디렉토리 구조는 `스테이지 > 스텝` 을 그대로 쓴다.** 사용자가 임의로 폴더를 만들게 하지 마라 — 사람마다 폴더 규칙이 달라지면 **Drive 문제가 그대로 재발한다.**
- **버전을 반드시 표시한다.** 버전과 최신본 표시가 없으면 이 메뉴를 만든 이유(`보고서_최종2.xlsx` 죽이기)가 사라진다.

### 12-4. 정산 메뉴 — 활성화 조건 ⚠️

```
활성화 =  입금확인 블록이 있다   OR   매칭된 입금이 있다
```

**`OR` 가 없으면 §7-4 의 2단 매칭이 무효가 된다.** 계약 직후 선급금이 들어왔는데 실무자가 아직 정산 스텝을 안 팠다면, 그 돈이 프로젝트 어디에서도 안 보인다.

블록 없이 입금만 있으면 이렇게 띄운다:

> ⚠️ **연결되지 않은 입금 1건** — 2026-08-14 · 15,000,000원
> 정산 스텝을 만들고 입금확인 블록을 추가하면 연결됩니다.

**정산 메뉴에서 등록·수정은 할 수 없다.** 등록은 재무 탭, 회차 생성은 입금확인 블록이다.

## 13. 템플릿 ⭐ 핵심 기능

**커스텀 자유도가 이 서비스의 차별점이고, 템플릿은 그 자유도를 재사용 가능하게 만드는 장치다.**

### 13-1. 단위 — 넷 전부

**프로젝트 · 스테이지 · 스텝 · 블록** 네 단위 모두 템플릿으로 저장하고 불러올 수 있다.

### 13-2. 프로젝트 생성

템플릿 선택 **또는** 빈 프로젝트, 둘 다 가능하다.
⛔ **템플릿을 강제하지 마라.** 자유도를 잃는 건 템플릿을 강제할 때지 제공할 때가 아니다.

### 13-3. 담기는 것 / 안 담기는 것

**원칙: `구조 + 설정` 은 담고, `실적(instance data)` 은 안 담는다.**

| 블록 | 담긴다 | 안 담긴다 |
|------|--------|----------|
| 텍스트 | **본문** (양식 문구 · 목차) | — |
| **체크리스트** | **항목 목록** | 체크 상태 |
| 파일 업로드 | 블록 껍데기만 | **업로드된 파일** |
| 이미지 · 메모 | 블록 껍데기만 | 내용 |
| **결재 상신** | **결재선** | 진행 상태 · 대상 지목 |
| 입금확인 | 블록 + 제목(`2차 정산`) | **연결된 입금** |
| 세금계산서 · 실적 조회 | 블록 껍데기만 | — |
| AI | 프롬프트 설정 | 실행 결과 |

**체크리스트 항목과 결재선이 템플릿의 진짜 값어치다.** 품질검토 체크리스트와 회사 표준 결재선이 매번 자동으로 깔리는 게 이 기능의 목적이다. 껍데기만 복사하면 스텝 이름만 깔리는 셈이다.

⛔ **파일은 담지 않는다.** 프로젝트 100개에 같은 파일이 100벌 생긴다. 양식 파일 관리는 별도 기능이다.
⛔ **프로젝트 상태 · 기간 · 참여자도 담지 않는다.**

### 13-4. 중첩은 스냅샷

상위 템플릿은 하위를 **통째로 복사해서** 담는다. 참조가 아니다.

참조로 하면 스텝 템플릿 하나 고쳤다가 프로젝트 템플릿 5개가 조용히 바뀐다. **템플릿은 "이대로 깔린다"는 예측 가능성이 전부인데** 그게 깨진다.

같은 이유로 **템플릿을 수정해도 이미 적용된 프로젝트는 따라가지 않는다.** 적용은 그 시점의 복사다.

### 13-5. 공개 범위 3단

| 단계 | 누가 보나 | 누가 올리나 |
|------|----------|-----------|
| **개인** | 만든 사람 | 저장 시 기본 |
| **팀** | 같은 부서 | 본인 |
| **전사** | 전원 | `ADMIN` |

목록은 `전사 표준 / 팀 / 내 템플릿` 으로 묶어 보여준다.

전부 전사 공개면 실험용 템플릿이 쌓여 목록이 쓰레기가 되고, 전부 개인이면 팀 표준이 안 생긴다.

> 부서가 권한 밖에서 기능적 역할을 갖는 유일한 지점이다(§6-1 은 부서를 조직도 전용으로 못 박았다). **가시 범위이지 권한이 아니므로 충돌하지 않는다.**

## 14. 조직 · 계정 (admin)

### 14-1. 계정과 사원은 **한 테이블**

`user` 하나에 인증 필드(계정 상태 · 비밀번호)와 조직 필드(부서 · 직급 · 재직 상태)를 둔다.

이벤트스토밍에서 `계정` 과 `사원` 이 별개 애그리거트로 그려진 것은 **행위의 종류가 다르기 때문**(인증 관리 vs 조직 관리)이지 엔티티가 둘이라는 뜻이 아니다. **화면은 둘로 나눠도 테이블은 하나다.**

지금 범위에 외부 계정(협력사)이 없다. 계정 없는 사원 · 사원 없는 계정을 만들 이유가 없다.

### 14-2. 퇴사 처리 ⚠️

**원칙: 자동으로 지우지 말고 경고 목록으로 뽑아라.**

| 항목 | 처리 |
|------|------|
| 계정 | **비활성화**(로그인 차단). soft delete 도 하지 않는다 |
| 로그 · 결재 이력 · 작성자 | **전부 유지.** 퇴사했다고 "누가 했는지"가 사라지면 안 된다 |
| 프로젝트 참여자 | 자동 제거 안 함. `퇴사` 배지 표시 |
| 담당 이슈 · 스텝 책임자 | 자동 해제 안 함. **경고 목록으로 뽑는다** (`퇴사자가 담당인 항목 12건`) |
| **진행 중 결재** | **퇴사 처리를 차단한다.** 결재자를 교체한 뒤 진행 |

자동 해제하면 담당자가 사라진 이슈가 조용히 방치되고, 자동 제거하면 이력이 깨진다.

진행 중 결재만 예외로 차단하는 이유 — 나머지는 방치돼도 나중에 고칠 수 있지만 **결재는 멈추면 프로젝트가 멈추고**, 위임 기능이 백로그라 자동으로 풀 방법이 없다.

### 14-3. ADMIN 관리 대상

| 대상 | 규칙 |
|------|------|
| 계정 | 발급(초기 비밀번호 생성) · 비밀번호 초기화 · 비활성화 |
| role | **인원별** 부여/회수 (§6-1) |
| 부서 | CRUD. 이름 중복 불가 · **소속 사원 있으면 삭제 불가** |
| 사원 | 등록 · 부서 배정 · 정보 수정 · 퇴사 처리 |
| 사업 카테고리 | CRUD. 이름 중복 불가 · **사용 중이면 삭제 불가** |
| 템플릿 | 전사 승격 (§13-5) |

크롤링 링크 관리는 `ADMIN` 이 아니라 `BIDDING` 소관이다 (§6-1).

## 15. 🚧 남은 것

**도메인 모델의 미결정 항목은 없다.** 흐름은 [`USECASE.md`](USECASE.md), 제품 정의는 [`PRODUCT.md`](PRODUCT.md) 에 있다.

다음 단계는 **엔티티 · 테이블 · API 설계**다. 그건 이 문서를 근거로 `.ai/api/{도메인}.md` 에서 진행한다.

### 백로그 (정했지만 나중에)

| 항목 | 왜 미루나 |
|------|----------|
| 결재자 부재 시 위임 | 순차 결재가 돌아간 뒤에 붙인다 |
| 병렬 합의 결재 | 상태머신이 두 배로 복잡해진다 |
| 기능 권한 사람 단위 오버라이드 | 실제로 문제가 되는지 보고 붙여도 늦지 않다 |
| **수익성 분석 (마진)** | 인건비 집계가 **공수 관리라는 별도 도메인**을 요구한다 |
| **송부 블록 타입** | 송부는 **스텝**으로 표현한다. 발송자·발송일시는 스텝 완료 로그에서 나온다. 방법·수신처 **집계**가 필요해지면 그때 블록을 만든다 |
