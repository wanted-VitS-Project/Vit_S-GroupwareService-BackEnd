# 🎯 제품 정의 — 문제 · 방향 · 핵심 기능

**최종 업데이트**: 2026-07-31 (초안 작성)
**작성/관리**: 김동현 (DevOps)

> **왜 만드는가**를 담는다. **무엇이 무엇인가**는 [`DOMAIN.md`](DOMAIN.md), **어떻게 흐르는가**는 유스케이스 문서 소관이다.
> 기능을 넣을지 말지 다툴 때 이 문서의 §2 문제 목록으로 돌아와라. **§2 에 없는 문제를 푸는 기능은 범위 밖이다.**

---

## 1. 한 줄 정의

**국가사업의 입찰 → 수행 → 정산을 하나의 흐름으로 관리하는 업무 관리 시스템.**

프로젝트 하나에 문서 · 일정 · 결재 · 정산이 전부 묶여 있어서 **"지금 어디까지 갔나"를 한 곳에서 답할 수 있게 한다.**

---

## 2. 문제 정의

국가사업 프로젝트의 업무가 하나의 시스템에서 관리되지 않고, Excel · 공유 Drive · 사내 메신저 등 여러 범용 도구를 조합해 비정형적으로 운영되고 있다.

### 현재 업무 방식

```
공고 발견
   ↓ 사내 채팅       "이 사업 한번 볼까요?"
   ↓ Excel           사업명 / 금액 / 일정 기록
   ↓ Drive           /2026년 사업/서울시사업/입찰,계약,보고서
   ↓ 사내 채팅       "1차 보고서 작성해주세요."
   ↓ Excel           진행상태 수정
   ↓ Drive           보고서_최종.xlsx · 보고서_최종2.xlsx · 보고서_진짜최종.xlsx
   ↓ 채팅            "팀장님 검토 부탁드립니다."
   ↓ Excel           정산 상태 관리
```

### 문제 세 가지

| # | 문제 | 구체적으로 |
|---|------|-----------|
| **P1** | **도구가 "지금 어디까지 진행됐는가"를 모른다** | Excel·Drive·채팅은 나쁜 도구가 아니다. 다만 **진행 상태를 이해하지 못한다.** 상태는 사람 머릿속과 채팅 스크롤에만 있다 |
| **P2** | **문서가 업무 단계와 연결돼 있지 않다** | `1차보고서.pdf` `1차보고서_수정.pdf` `1차보고서_최종.pdf` — 어느 게 검토를 통과했고 어느 게 발주처에 나갔는지 파일 이름으로만 구분한다 |
| **P3** | **회사 차원의 전체 현황 파악이 어렵다** | 대표나 PM 이 진척을 확인하려면 Excel 을 여러 개 열어 취합해야 한다. 그 취합 비용이 곧 운영 의사결정 비용이다 |

### 파생 문제 — 기존 데이터에서 실제로 관찰된 것

| 문제 | 관찰 |
|------|------|
| 결과가 안 남는다 | 입찰 대장 294건 중 **개찰 결과가 적힌 건은 24건**. 나머지 270건은 낙찰률조차 계산 불가 |
| 값이 제각각이다 | 참여 여부 칸에 `x` `X` `o` `○` `검토중` `보류` `고려중` `V` `./` 가 섞여 집계 불가 |
| 검토 이력이 없다 | 품질검토 칸이 체크박스 **1개**. 누가·언제·무엇을 지적했는지 안 남아 같은 실수가 반복돼도 모른다 |
| 회차를 표현 못 한다 | 진행상황 칸에 `1차기성` 또는 `Ⅱ-2` **하나만** 적을 수 있어, 정산 3회차 중 어디까지 갔는지 알 수 없다 |
| 완료 건이 사라진다 | 입금완료 행을 다른 파일로 **옮기고 삭제**하는 스크립트 때문에 완료 건을 진행 화면에서 못 본다 |

## 3. 추구 방향성

### 3-1. 프로젝트가 중심 객체다

문서를 모아두는 게 아니라 **프로젝트에 모든 것이 매달린다.**

```
프로젝트: 2026 서울시 데이터 분석 사업

현재 단계     입찰 ✓ → 수행 ● → 정산 ○      전체 진행률 62%
현재 업무     1차 보고서 작성                 담당 김용준 · 마감 8월 13일
승인 대기     품질검토 → 팀장 결재
최근 문서     1차보고서_v4.pdf
```

**이 한 화면이 나오면 P1·P2·P3 가 동시에 풀린다.**

### 3-2. 설계 원칙 다섯

이 서비스의 모든 결정은 아래 다섯 줄로 설명된다. **판단이 갈릴 때 여기로 돌아와라.**

| # | 원칙 | 뜻 |
|---|------|-----|
| **1** | **사람이 안 하면 깨지는 규칙을 만들지 마라** | 캘린더 등록 스위치를 없앤 이유, 부서 상속 대신 인원별 권한을 쓴 이유, 입금 매칭을 2단으로 나눈 이유 |
| **2** | **권한은 잊었을 때 닫히는 쪽으로 실패해야 한다** | 부여를 잊어서 "못 본다"는 신고가 들어오지만, 자동 부여를 잊으면 인턴이 입금을 확정한다 |
| **3** | **자유도는 조회에 주고, 저장은 하나로 고정한다** | 캘린더 필터 · 목록 필터. 저장 시점 옵션은 데이터를 갈라놓는다 |
| **4** | **이력은 지우지 않는다** | 전면 soft delete · 로그 영구 보존 · 종결도 프로젝트로 남김 |
| **5** | **한 사실은 한 곳에만 산다** | 결재 대상은 파일 블록을 지목(복사 금지) · 회차는 블록에만 · 금액은 프로젝트 속성 |

### 3-3. 안 하는 것 — 명시적 범위 밖

| 항목 | 왜 뺐나 |
|------|--------|
| 수익성 분석 (마진 계산) | 인건비 집계가 **공수 관리라는 별도 도메인**을 요구한다 |
| 투입 공수 관리 | 위와 같음 |
| 결재자 부재 시 위임 · 병렬 합의 결재 | 순차 결재가 돌아간 뒤에 붙인다 |
| 송부 방법·수신처 집계 | 송부는 **스텝**으로 표현한다. 집계가 필요해지면 블록을 만든다 |
| 문서 자산(양식) 버전 관리 | 프로젝트 안 파일 버전과는 다른 기능이다 |

## 4. 핵심 기능 — 문제와 1:1로 대응한다

| 기능 | 푸는 문제 | 한 줄 |
|------|----------|------|
| **① 계층 + 템플릿** | P1 | 회사마다 다른 절차를 **스테이지 > 스텝 > 블록**으로 조립하고 템플릿으로 재사용 |
| **② 프로젝트 중심 문서·이력** | P2 | 파일이 **버전 · 결재 상태 · 활동 로그**를 달고 업무 단계에 붙어 있다 |
| **③ 결재 + 버전 고정** | P2 | "무엇을 승인했는지"가 영구히 특정된다 |
| **④ 정산 정합성** | P1·P3 | 재무와 프로젝트를 분리하되 **입금을 프로젝트에 매칭**해 회차별 상태가 동시에 성립 |
| **⑤ 이슈 + 알림** | P1 | 채팅 지시를 대체한다. **이슈로 만들지 않으면 알림이 안 간다** |
| **⑥ 권한 2층** | P3 | 전역 role 이 탭을 열고, 프로젝트 권한이 안을 통제한다 |

## 5. 기능별 핵심

> 상세 규칙은 전부 [`DOMAIN.md`](DOMAIN.md) 에 있다. 여기는 **"왜 그렇게 만들었나"** 만 적는다.

### ① 계층 + 템플릿 — 회사별 절차를 담는다

- **스텝에는 타입이 없다.** 이름이 `2차 정산`이든 `중도금`이든 시스템은 모른다. 도메인 의미는 전부 **블록**이 갖는다. → 그래서 회사마다 다른 절차를 담을 수 있다
- **템플릿은 프로젝트·스테이지·스텝·블록 네 단위 전부.** 개인 → 팀 → 전사로 승격한다
- **템플릿의 진짜 값어치는 체크리스트 항목과 결재선**이다. 껍데기만 복사하면 스텝 이름만 깔린다

### ② 문서 · 이력 — `보고서_최종2.xlsx` 를 죽인다

- 파일은 **하나**고 **버전**이 붙는다. 파일명으로 구분하지 않는다
- 디렉토리 구조는 `스테이지 > 스텝` **고정**. 사용자가 폴더를 만들게 하면 Drive 문제가 그대로 재발한다
- 로그는 **대상 이름을 복사해서** 저장한다. 원본이 지워져도 `제안서_v1.docx 를 업로드함` 이 읽혀야 한다

### ③ 결재 — "무엇을" 승인했는지가 남는다

- 결재 블록은 **파일을 복사하지 않고 파일 블록을 지목**한다
- **상신 시점 버전을 고정**한다. 대표가 v4 를 보고 승인했는데 다음 날 v5 로 바뀌면 그 승인은 거짓이 된다
- **대상 버전이 바뀌면 처음부터 전원 재승인.** 시스템이 자동 판정한다
- 품질검토는 **결재선의 한 노드**다. 별도 개념이 아니다 → 품질관리실이 없는 회사도 쓴다

### ④ 정산 — 회차 3줄이 동시에 성립한다

```
1차 정산: 청구✓ 계산서✓ 입금✓
2차 정산: 청구✓ 계산서✓ 입금 —
3차 정산: 청구 — 계산서 — 입금 —
```

- **재무는 프로젝트 밖**이다. 재무담당자는 프로젝트 참여자가 아니고, 동선이 "이번 달 입금 전체"다
- **계획은 프로젝트, 실행은 재무.** 계약 조건을 아는 건 실무자, 돈이 왔는지 확정하는 건 재무
- **매칭은 2단** — ① 프로젝트(필수) ② 블록 연결(나중 가능). **돈은 블록보다 먼저 들어올 수 있다**
- 프로젝트 쪽은 **전원 읽기 전용.** 실무자가 입금을 체크할 수 있으면 정산 데이터를 아무도 못 믿는다

### ⑤ 이슈 · 알림 — 채팅을 대체한다

- **이슈만이 담당자에게 알림을 쏘고 `내 할일` 에 뜬다.** 채팅으로 시키면 아무 데도 안 남는다 → 시키는 사람이 이슈를 만들 **유인**이 생긴다 (강제가 아니다)
- **알림은 두 종류.** 액션 요구(뱃지, 처리까지 안 사라짐) vs 정보(피드). 섞으면 사람들이 알림을 끄고, 그러면 결재 상신도 못 본다
- 이슈는 **진척률에 안 들어간다.** 꼼꼼한 사람이 이슈를 20개로 쪼개면 진척률이 낮게 나온다 — **지표가 행동을 망가뜨린다**

### ⑥ 권한 — 2층

- **전역 role → 탭**, **프로젝트 권한 → 그 안**. 저장은 프로젝트 + 스텝 2층뿐
- 3층(프로젝트/스테이지/스텝) 오버라이드는 만들지 않는다. 유효 권한을 사람이 추적 못 하면 아무도 권한을 안 건드린다
- 권한 없으면 **숨김이 아니라 잠금**. 숨기면 사람마다 진척률이 다르게 보인다

## 6. 이 서비스가 새로 넣는 것

기존 업무 흐름에 **아예 없던** 항목들이다. 빼면 문제가 안 풀린다.

| 항목 | 없어서 생긴 문제 |
|------|----------------|
| **종결 사유 필수** | 미참여·유찰 이유가 안 쌓여 판단 기준이 개선되지 않았다 |
| **결재 이력 (검토자·검토일·지적사항)** | 체크박스 하나뿐이라 같은 실수가 반복돼도 몰랐다 |
| **회차별 독립 레코드** | 한 칸에 하나만 적을 수 있어 정산 진행 상태를 표현 못 했다 |
| **파일 버전 + 결재 상태** | 파일명으로만 구분했다 |
| **활동 로그** | "누가 바꿨냐"에 답할 수 없었다 |
| **기한 알림 (D-7/3/1)** | 규칙이 문서에만 있고 경고가 안 떴다 |
| **자동 스크리닝** | 지역·업종 제한으로 애초에 못 하는 건을 매번 눈으로 걸렀다 |
