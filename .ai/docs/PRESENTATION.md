## 1. 포지셔닝 — "위도 아래도 답이 있는데 이 구간만 없다"

| 규모 | 쓰는 도구 | 답이 되는 이유 |
|---|---|---|
| 100인 이상 (대기업·중견) | **ERP / 자체 구축 그룹웨어** | 전담 IT팀 + 예산으로 맞춤 구축·운영 |
| 1인~소수 (프리랜서·초소형팀) | **Notion 한 장** | 프로젝트가 단순해서 한 페이지로 충분 |
| **10~30인** ⭐ | **없음** | 프로젝트는 입찰→수행→정산으로 길고 복잡한데, **살 돈도 운영할 전담 인력도 없다** |

> ⚠️ **발표 시 주의** — `10~30인` 은 시장 조사 수치가 아니라 **작업 가정**이다.
> "이 규모대를 가정했다" 로 말하고, 주장의 무게는 §3 의 **S1(연결)** 에 싣는다.
> S1 은 숫자 없이 **구조만으로 증명된다** — 아래 §2 표가 그 증명이다.

## 2. 중소기업 현황 — 데이터가 5곳에 흩어진다

| 스텝 | 담당자 | 실제 쓰는 도구 | **데이터가 사는 곳** |
|---|---|---|---|
| 공고 확인 | 입찰 담당자 | 나라장터 + 케이비드/비드큐 등 알림 SaaS | 입찰 담당자 **개인 브라우저 즐겨찾기** |
| 참여 결재 | 팀장 | 그룹웨어 전자결재 (하이웍스·다우오피스 등) | 그룹웨어 서버 |
| 수행 (보고서 작성) | 실무자 | 노션/트렐로/엑셀 진행표 + 한글·워드 | 실무자 **개인 클라우드** |
| 보고서 결재·품질검토 | 팀장·품질관리자 | 다시 그룹웨어 전자결재 | 그룹웨어 서버 — **참여결재와 같은 시스템인데 서로 연결 안 됨** |
| 정산 (세금계산서·입금) | 재무 담당자 | 더존 위하고/Bill36524 + 은행 오픈뱅킹 | **재무팀 전용 시스템** |

**핵심은 4행이다.** 같은 그룹웨어 안에서조차 참여결재와 보고서결재가 안 이어진다.
도구를 통합해도 안 풀린다는 뜻이고, 그게 §3 의 출발점이다.

### 단계별로 실제 관찰된 것

| 단계 | 관찰 | 그래서 |
|---|---|---|
| 공고 확인 | 알림 SaaS 는 새 공고는 알려주지만 **사내 검토·결재·기록은 지원 안 함** | 알림에서 사내 프로세스로 넘어가는 지점이 비어 있다 |
| 리스트화 | 공고를 **엑셀 20개 이상 컬럼**으로 손입력해 보고 | 회사마다 컬럼 기준이 달라 사람이 매번 채운다 → 병목 |
| 투찰 준비 | 세부 단계마다 문서가 생성됨 | **어느 게 최종본인지 파일명으로만 구분** |
| 수주 확정 | 계약서가 프로젝트가 아니라 **Drive 계약서 폴더**에 저장 | 수행팀이 보려면 **담당자에게 물어야** 한다 |
| 인원 배정 | 엑셀 명단 · 메신저 언급 | **누가 참여 중인지 시스템으로 조회 불가** |
| 품질검토 | 워드/한글 오프라인 코멘트 + 외부 AI 툴 | 누가·언제·무엇을 지적했는지 **사내에 안 남는다** |
| 보고서 결재 | 회차마다 그룹웨어 상신 | **반려 후 재상신 이력과 원본 버전의 연결이 약하다** |
| 정산 | 재무팀 전용 시스템 | 실무팀·입찰팀장은 **정산 현황을 전혀 모른다** |

## 3. 구조적 문제 3개 ⭐

> **순서가 중요하다.** 돈(S3)을 앞세우면 "그건 가격 경쟁이지 기술이 아니다" 로 받아친다.
> **S1 · S2 는 숫자 없이 구조로 증명되므로 이 둘을 앞에 둔다.**

### S1. 다 사도 안 이어진다 — 결정적

> Drive 에 올린 파일이 그룹웨어 결재의 대상이 됐다는 걸 **아무도 기록하지 않는다.**

도구를 다 사도 그 사이의 **"연결"은 여전히 사람 손이 하는 일**이다.
그리고 **어느 도구에도 그 연결을 저장할 자리가 없다.**

| 사람이 손으로 하던 연결 | 저장할 자리가 있는 도구 |
|---|---|
| "이 파일 v4가 그 결재의 대상이었다" | ❌ 없다 |
| "이 입금이 그 프로젝트 2차 정산분이다" | ❌ 없다 |
| "이 공고가 이 프로젝트가 됐다" | ❌ 없다 |

### S2. 연결이 사람과 함께 사라진다

> 소규모 회사는 인원 이동이 잦고 인수인계 체계에 규칙이 없다.
> **그 사람이 바뀌면 연결이 끊긴다.**

**S1 과 다른 문제다.**

| | S1 | S2 |
|---|---|---|
| 무엇 | 연결이 **애초에 기록 안 된다** | 기록됐어도 **사람이 나가면 해석 불가**가 된다 |
| 증상 | "이 파일이 승인된 그 파일 맞나?" | "이 프로젝트가 왜 종결됐지?" · 신규 입사자가 **회사에 무슨 프로젝트가 있는지조차 모른다** |
| 대응 축 | FK 로 저장 | **이력을 지우지 않는다** |

### S3. 살 수가 없다 (보조 근거)

입찰정보 SaaS · 그룹웨어 · 프로젝트관리툴 · 회계프로그램 · 전자결재 별도 상품 —
조각을 다 구독하면 소규모 회사 IT 예산을 넘어선다.

> ⚠️ 이건 **왜 통합 도구가 없는가**의 배경 설명으로만 쓴다. 근거가 추정이라 주장의 축으로 삼지 않는다.

## 4. ⭐ 우리는 각 기능이 전문 도구보다 못하다 — 슬라이드 한 장 통째

> 이 장을 **우리가 먼저 꺼낸다.** 심사가 던질 가장 큰 반박을 선제로 꺾는 자리다.

| 기능 | 더 잘하는 도구 | 우리 수준 |
|---|---|---|
| 파일 버전 관리 | Google Drive · Dropbox | 못하다 |
| 전자결재 | 하이웍스 · 다우오피스 | 못하다 |
| 프로젝트 보드 | 노션 · 트렐로 · Jira | 못하다 |
| 세금계산서 · 회계 | 더존 위하고 · Bill36524 | 발행 기능조차 없다 (홈택스에서 수집만) |

### 그런데

> **버전관리는 Drive 가, 결재는 하이웍스가 낫다.
> 근데 "이 파일 v4 가 그 결재의 대상이었다"를 적을 자리는 어느 쪽에도 없다.**

우리가 만든 건 더 나은 기능이 아니라 **그 사이를 잇는 컬럼**이다.

| 사람 머릿속에 있던 연결 | 우리가 만든 데이터 |
|---|---|
| "이 공고가 이 프로젝트가 됐다" | `project.bid_notice_id` |
| **"이 파일 v4 가 그 결재의 대상이었다"** ⭐ | `approval_document.file_version_id` — 파일이 아니라 **버전**을 박는다 |
| "반려 후 이건 2회차 재상신이다" | `approval_revision` — 회차 단위로 이력이 남고 **반려 지점부터 재개**한다 |
| "이 입금이 그 프로젝트 2차 정산분이다" | 2단 매칭 — ① 프로젝트(필수) ② `payment.block_id`(선택) |
| "이 이슈는 그 블록 일이다" | `issue_block` (+ 같은 스텝인지 애플리케이션이 검증) |
| "이 스텝은 김OO가 8/13 에 발송했다" | 스텝 완료 = 발송자·발송일시 |
| "이 프로젝트는 왜 종결됐나" | `project.close_reason_code` + `close_reason_note` — **사유 필수** |

**전부 FK 하나다. 그리고 담당자가 퇴사해도 FK 는 안 사라진다.** → S1·S2 동시 해결.

## 5. 해법 — 프로젝트가 중심 객체다

문서를 모아두는 게 아니라 **프로젝트에 모든 것이 매달린다.**

```
프로젝트: 2026 서울시 데이터 분석 사업

현재 단계     입찰 ✓ → 수행 ● → 정산 ○      전체 진행률 62%
현재 업무     1차 보고서 작성                 담당 김용준 · 마감 8월 13일
승인 대기     품질검토 → 팀장 결재
최근 문서     1차보고서_v4.pdf
```

**이 한 화면이 §2 표의 5개 행을 하나로 접는다.**

### 계층 — 회사마다 다른 절차를 담는 방법

```
프로젝트 ─ 스테이지(분류 라벨) ─ 스텝(작업 단위) ─ 블록(실제 내용)
```

| 결정 | 이유 |
|---|---|
| **스텝에는 타입이 없다** | 이름이 `2차 정산`이든 `중도금`이든 시스템은 모른다. 도메인 의미는 전부 **블록**이 갖는다 → 회사마다 다른 절차를 그대로 담는다 |
| **스테이지는 상태도 권한도 없다** | 분류 라벨일 뿐. 권한은 프로젝트 + 스텝 2층에만 저장한다 |
| **스텝 순번은 선행 완료를 강제하지 않는다** | 제안서와 견적은 동시에 돈다 |
| **블록 타입은 닫힌 enum** | "확장 가능"은 환상이다 — 새 타입을 넣어도 프론트에 렌더러가 없으면 못 쓴다 |

## 6. 유스케이스별 — 어디서 끊기고, 무엇으로 이었나

| 구간 | **끊기는 지점** (기존) | **이은 기능** | 화면 | 권한 |
|---|---|---|---|---|
| **A. 공고→프로젝트**<br/>UC-01~03 | 공고는 개인 즐겨찾기, 검토는 엑셀 20컬럼 손입력 | 크롤링 수집 + **자동 스크리닝**(업종·지역 대조) · `프로젝트 시작` 버튼 하나 · AI 요약 초안(**사람이 반드시 확정**) | `/notices` | `BIDDING` |
| **B. 참여 결재**<br/>UC-04 | 그룹웨어 결재 ↔ 프로젝트 문서가 **다른 시스템** | 결재 블록이 **파일 버전을 지목** · 승인/반려 **2값 + 사유** · 미참여도 **종결 사유 필수** | `/projects/[id]/steps/[stepId]` → `/approvals` | 결재선에 있는 사람만 (**role 무관**) |
| **C. 입찰 준비→개찰**<br/>UC-05~11 | `보고서_최종2.pdf` · 품질검토 체크박스 **1개** | **파일 1개 + 버전 N** · 품질검토를 **결재선의 한 노드로 흡수** → 검토자·검토일·지적사항이 이력으로 남음 · 개찰 결과는 **사유 필수** | `/projects/[id]/files` | 스텝 권한 |
| **D. 수행**<br/>UC-12~16 | 노션/트렐로가 결재·정산과 **연동 안 됨**. 계약서는 Drive 폴더 | **보고서 회차마다 스텝 1개** · 반려 시 **revision 생성 후 반려 지점부터 재개** · 계약금액은 프로젝트 속성 · 참여자는 **개인 단위로 시스템에 등록** | `/projects/[id]` | `project_member` |
| **E. 정산**<br/>UC-17~19 | 재무팀 전용 시스템 → 실무팀·팀장은 정산 현황을 **전혀 모름** | **2단 매칭** · 입금확인 블록 = 정산 회차 · 청구/계산서/입금 **3열 동시 성립** | `/finance/payments/match` → `/projects/[id]/settlement` **조회 전용** | 확정은 `FINANCE`+`EDITOR` / 조회는 참여자 전원 |

### E 를 하이라이트로 쓴다 — 읽기는 열고, 쓰기는 재무만

```
1차 정산: 청구✓ 계산서✓ 입금✓
2차 정산: 청구✓ 계산서✓ 입금 —
3차 정산: 청구 — 계산서 — 입금 —
```

**이 세 줄이 동시에 성립한다.** 엑셀은 진행상황 칸에 `1차기성` 하나만 적을 수 있었다.

| 결정 | 이유 |
|---|---|
| **매칭은 2단** — ① 프로젝트(필수) ② 블록(선택) | **돈은 블록보다 먼저 들어올 수 있다.** 선급금은 계약 직후, 잔금은 1년 뒤 — 정산 시점이 프로젝트 진행과 다른 속도로 흐른다 |
| **자동 매칭은 후보 추천까지만** | 확정 버튼은 사람이 누른다. 은행 적요에 용역명은 안 온다 |
| **프로젝트 쪽은 전원 읽기 전용** | 실무자가 입금을 스스로 체크할 수 있으면 정산 데이터를 아무도 못 믿는다 |
| **블록 없이 매칭만 된 입금은 경고로 뜬다** | 안 그러면 그 돈이 프로젝트 어디에서도 안 보인다 |

## 7. 권한 — 부서를 권한에서 뺐다

### 7-1. 화면 구획이 곧 역할 경계다

프론트 `PAGE_ROUTES` 가 정본이다.

| 역할 | `pageCode` | 라우트 | 무엇을 하나 |
|---|---|---|---|
| **전사 관리** (인사) | `ADMIN_CONSOLE` | `/settings` | 사원·부서·직급·그룹·카테고리·**권한 부여** |
| **프로젝트 관리** (실무) | `BIDDING` · `PROJECT_CREATE` · `MY_PROJECT` | `/notices` · `/projects` | 공고·프로젝트·스텝·블록·이슈·로그 |
| **재무 관리** (재무) | `FINANCE` | `/finance` | 입출금·매칭·세금계산서·정산현황 |

**탭을 만드는 기준은 하나다 — 프로젝트 밖에 자기 데이터가 있는가.**
있으면 탭(`BIDDING`·`FINANCE`), 없으면 전원 오픈(홈·알림·결재관리).

### 7-2. ⭐ 부서를 권한 테이블에 넣지 않았다

**권한은 전부 인원별 직접 지정이다.** 부서·직급·그룹은 권한 판정에 쓰지 않는다.

| 왜 | |
|---|---|
| **원칙: 권한은 잊었을 때 닫히는 쪽으로 실패해야 한다** | 부여를 잊으면 "못 본다"는 신고가 들어온다. **자동 부여를 잊으면 인턴이 입금을 확정한다** |
| 부서 상속을 쓰면 | 인사이동 한 번에 권한이 **조용히 따라 움직인다.** 아무도 모른 채 |
| 그룹은? | **여러 명을 한 번에 고르는 선택 도구**일 뿐, 저장은 개인 단위 스냅샷이다. 그룹이 삭제돼도 권한은 안 흔들린다 |

### 7-3. 권한은 3층

| 층 | 값 | 행이 없으면 |
|---|---|---|
| ① 전역 role | `ADMIN` > `MASTER` > `MEMBER` | — (항상 하나는 있다) |
| ② 화면 접근 `page_permission` | `VIEWER` · `EDITOR` | **접근 불가** (메뉴는 보이되 잠김) |
| ③ 프로젝트 / 스텝 | `VIEWER` · `EDITOR` · `NONE` | **상위 층에서 상속** |

| 결정 | 이유 |
|---|---|
| **3층(프로젝트/스테이지/스텝) 오버라이드는 안 만든다** | 유효 권한을 사람이 추적 못 하면 **아무도 권한을 안 건드린다** |
| **권한 없으면 숨김이 아니라 잠금** | 숨기면 사람마다 진척률이 다르게 보인다 |
| **메뉴는 보이되 접근은 막는다** | 기능의 존재를 알리고 관리자에게 요청할 경로를 만든다 |

> ⚠️ **발표 시 주의** — `ADMIN` 은 실제 사원에게 부여하는 role 이 아니라 **개발자가 발급하는 시스템 계정**이다.
> "인사팀 팀장이 로그인해서 사원을 등록한다" 로 말하지 말고 **"전사 관리 화면을 여는 계정"** 으로 말한다.

## 8. 개발 최소범위 ⭐

### 판정 기준 — 한 문장

> ### 프로젝트 하나가 **생성 → 종결까지 끊기지 않고 흐르는 데 필요한 것만** 만든다.

**바퀴가 한 바퀴 도는가**가 유일한 기준이다. 집계·분석·통계는 **바퀴가 여러 번 돈 뒤에** 나오는 것이므로 전부 뺐다.

### 안에 넣은 것

| 기능 | 없으면 |
|---|---|
| 스테이지 > 스텝 > 블록 | 흐름을 표현할 단위가 없다 |
| 파일 버전 | 어느 게 최종본인지 모른다 |
| 결재 (순차) + 버전 고정 | 무엇을 승인했는지 특정 안 된다 |
| 이슈 + 알림 | 남에게 시킨 일이 아무 데도 안 남는다 |
| 2단 매칭 | 돈이 프로젝트 어디에도 안 보인다 |
| 활동 로그 | "누가 바꿨냐"에 답할 수 없다 |
| **종결 사유 필수** | 종결도 흐름의 끝이다. 사유가 없으면 **그냥 멈춘 것과 구분이 안 된다** |

### 밖에 둔 것 — 이유가 각각 다르다

| 뺀 것 | 이유 | 유형 |
|---|---|---|
| 수익성 분석 · 투입 공수 | 인건비 집계가 **공수 관리라는 별도 도메인**을 요구한다 | 도메인 경계 |
| 낙찰률 · 투찰금액 · 순위 | 바퀴가 **여러 번 돈 뒤**에 나오는 집계 | 집계 |
| 전사 현황 · 템플릿 | 〃 (프론트 `UNROUTED_PAGES` 에 미구현으로 명시) | 집계 · 시간 |
| 송부 방법 · 수신처 집계 | 송부는 **스텝**으로 표현된다. 집계가 필요해지면 블록 타입을 추가한다 | 확장 경로 확보 |
| 결재 위임 · 병렬 합의 | **순차 결재가 돌아간 뒤에** 붙인다 | 순서 |
| **3층 권한 오버라이드** | 넣으면 오히려 사람이 권한을 안 건드려 **흐름이 막힌다** | ❌ 영구 제외 |

> ⭐ **마지막 줄이 이 장의 핵심이다.** 나머지는 "나중에 한다"지만 이건 **"안 만드는 게 낫다"**다.
> **안 만든 것도 설계다** — 발표에서 이 문장으로 §8 을 닫는다.

### 같은 기준으로 설명되는 다른 결정들

| 결정 | 같은 이유 |
|---|---|
| 캘린더 **등록 스위치가 없다** | 날짜가 곧 표시 조건. 사람이 스위치를 잊으면 일정이 사라진다 |
| 문서 디렉토리는 `스테이지 > 스텝` **고정** | 사용자가 폴더를 만들게 하면 Drive 문제가 그대로 재발한다 |
| **삭제 잠금을 전부 폐기**했다 | 잠금의 탈출구가 "재무팀에 요청"뿐이라 사용자가 갇혔다. 막는 대신 **확인을 요구**하고, 살릴 블록은 다른 스텝으로 **옮기게** 한다 |
| **이슈는 진척률에 안 들어간다** | 꼼꼼한 사람이 이슈를 20개로 쪼개면 진척률이 낮게 나온다 — **지표가 행동을 망가뜨린다** |

| 항목 | 왜 v1 에서 못 했나 | v2 확장 경로 |
|---|---|---|
| **템플릿** (체크리스트 항목 · 본문 재사용) | 화면 미구현 (`TEMPLATE` → `UNROUTED_PAGES`) | ✅ **설계는 끝나 있다** — `BlockDetailPort.copyDetail()` 기본 구현이 빈 행을 만들어, 타입 담당자가 각자 자기 어댑터에서 순차로 연다 |
| **전사 현황 대시보드** | 화면 미구현 (`COMPANY_STATUS`) | 집계 원천(`project`·`step`)은 이미 있다 |

> **"확장점을 미리 뚫어놨다"가 이 장의 메시지다.** 템플릿은 못 만든 게 아니라 **구멍을 내놓고 안 채운 것**이다.

## 부록 B. 예상 질문 · 답변

| 질문 | 답 |
|---|---|
| **"그냥 노션 + 드라이브 쓰면 되지 않나"** | 노션에 `approval_document.file_version_id` 에 해당하는 자리가 없다. **연결을 저장할 곳이 없다**는 게 §4 의 요지다 |

| **"왜 부서 기반 권한이 아닌가"** | 인사이동에 권한이 조용히 따라 움직인다. **잊었을 때 닫히는 쪽으로 실패해야 한다** (§7-2) |
| **"낙찰률은 왜 없나"** | 바퀴가 여러 번 돈 뒤 나오는 집계다. v1 기준은 **한 바퀴가 끊기지 않고 도는가**였다 (§8) |
| **"10~30인 근거가 뭔가"** | 작업 가정이다. 주장의 근거는 규모가 아니라 **§2 표의 구조** — 같은 그룹웨어 안에서조차 참여결재와 보고서결재가 안 이어진다 |
| **"AI 는 왜 초안만 만드나"** | 결재 판단 자료라 **사람이 반드시 검토·확정**한다. 미확정 요약은 프로젝트 전환에 쓰지 않는다 |
| **"품질검토 기능이 왜 없나"** | 결재선의 한 노드로 흡수했다 → **품질관리실이 없는 회사도 쓴다** (§6 C) |
