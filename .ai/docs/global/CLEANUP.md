## 0. 판단 기준 — 소프트 삭제냐, 명시적 영구 삭제냐, CASCADE냐

삭제 요구가 생기면 아래 순서로 판단한다.

| 질문 | 처리 |
|---|---|
| 사용자의 일반 삭제 요청이며 엔티티가 `deleted_at`을 사용하는가? | 소프트 삭제만 한다. 보존기간 경과를 이유로 전역 스케줄러에 등록하지 않는다. |
| API·유스케이스 계약에 명시적인 영구 삭제(PURGE 등)가 있는가? | 해당 도메인의 명시적 유스케이스에서만 수행한다. 전역 SPI·스케줄러를 추가하지 않는다. |
| 부모가 **명시적 영구 삭제**될 때 자식이 부모 없이 존재할 의미가 없는가? | §2 CASCADE 후보를 검토한다. |
| 감사·재무 보존이 필요하거나 참조가 비즈니스 규칙의 근거인가? | CASCADE를 금지하고 `SET NULL` 또는 애플리케이션 검증을 사용한다. |

전역 자동 삭제와 명시적 영구 삭제는 성격이 다르다. 파일 PURGE나 이미지의 명시적 영구 삭제처럼
별도 계약으로 실행되는 기능은 이 문서의 전역 정리 대상이 아니며, 각 도메인 유스케이스가 책임진다.

---

## 1. 전역 자동 하드 딜리트는 없다

다음 구조는 제거됐으며 새 도메인도 다시 도입하지 않는다.

| 제거된 구조 | 상태 |
|---|---|
| `global/application/cleanup`의 `HardDeleteTarget`, `HardDeleteOperation`, `DefaultHardDeleteTarget`, `HardDeleteExecutor` | 제거 |
| `global/infrastructure/cleanup/HardDeleteScheduler` | 제거 |
| `{domain}/infrastructure/cleanup/{Domain}CleanupConfig`의 자동 삭제 대상 등록 | 사용 금지 |

`@EnableScheduling`은 다른 기능의 예약 작업에도 사용될 수 있으므로, 전역 하드 딜리트 제거만을 이유로
변경하지 않는다. 설정을 수정해야 하면 실제 `@Scheduled` 사용처를 먼저 확인한다.

### Issue 정책

Issue 삭제는 기존처럼 `deletedAt`을 설정하는 소프트 삭제만 수행한다.
`SpringDataIssueRepository`에는 보존기간 기준 `DELETE` 쿼리가 없고, Issue를 자동 물리 삭제하는 설정·스케줄러도 없다.

## 2. CASCADE — 명시적 영구 삭제의 종속 데이터 처리

부모가 도메인 계약에 따라 명시적으로 영구 삭제될 때, **자체 삭제 API가 없는 종속 데이터**를 함께 정리할지 판단하는 기준이다.
전역 스케줄러 등록과는 무관하다.

### 2-1. CASCADE를 걸어도 되는 조건 (전부 만족해야 함)

1. 자식이 부모 없이 존재할 이유가 없다 — 부모 콘텐츠 그 자체이거나 순수 연결 행이다.
2. 자식 자체에 독립적인 감사·재무·법적 보존 요구가 없다.
3. 자식이 지워져도 되돌릴 수 없는 정보 손실이 아니다.

### 2-2. CASCADE를 걸면 안 되는 조건 (하나라도 해당하면 금지)

1. 감사로그류 — 정책상 영구 보존해야 하는 데이터(`activity_log` 등).
2. 재무 기록 — 부모가 사라져도 회계적으로 남아야 하는 데이터.
3. FK 참조 자체가 삭제 차단 같은 비즈니스 규칙의 근거인 경우.

### 2-3. 대안 — `SET NULL`

CASCADE는 금지지만 참조 컬럼이 nullable이고 기록이 대상 이름·내용의 스냅샷을 보유한다면,
`ON DELETE SET NULL`로 기록은 보존하고 참조만 끊을 수 있다.

## 3. Flyway 반영

FK 삭제 동작을 바꾸는 것은 스키마 변경이므로 [FLYWAY.md](FLYWAY.md)를 따른다.

- 이미 적용된 마이그레이션은 수정하지 않고 새 마이그레이션으로 `DROP FOREIGN KEY` 후 제약을 다시 추가한다.
- FK 이름은 기존 이름을 재사용해 추적성을 유지한다.
- 스키마 정본인 [ERD.md](../domain/ERD.md)에도 같은 변경을 반영한다.
