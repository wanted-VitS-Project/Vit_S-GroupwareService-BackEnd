## 0. 등장 인물

**2026-08-01 개편**: 전역 role 은 `ADMIN`·`MASTER`·`MEMBER` **3종뿐**이다. 나머지는 `page_permission` 으로 받는다 → [`PERMISSION.md`](PERMISSION.md).
⚠️ **서열이 이름과 반대다** — `ADMIN` > `MASTER` > `MEMBER`. 부여·회수는 전부 `ADMIN` 이 하고 `MASTER` 는 CEO 열람·개입용이다.

| 행위자 | 전역 role | 추가로 받는 것 | 역할 |
|--------|----------|--------------|------|
| 실무자 | `MEMBER` | — | 공고 발견, 프로젝트 운영, 제안서·보고서·청구서 작성 |
| 입찰 담당자 | `MEMBER` | `page_code='BIDDING'` + `EDITOR` | 공고 탭 · 크롤링 링크 관리 |
| 부서 검토자 | `MEMBER` | — | **결재선 노드**로 참여 의견 등록 |
| 결재자 · 최종 결재자 | `MEMBER` | — | 결재선 상의 **순번**. **role 이 아니다** (DOMAIN §8-1) |
| 재무 담당자 | `MEMBER` | `page_code='FINANCE'` + `EDITOR` | 세금계산서 발행 · 입금 확정 · 프로젝트 매칭 |
| **CEO** | **`MASTER`** | — | 전 프로젝트·전사현황 **열람 + 개입**(로그에 `privileged_override`). ⚠️ **부여·회수는 못 한다. 결재와도 무관** |
| 조직 관리자 | **`ADMIN`** | — | 계정 발급 · role 부여/회수 · `page_permission` 부여/회수 · 부서 · 사원 · 카테고리. **`MASTER` 의 열람·개입을 포함한다** |

> ⛔ **`경영진 · PM` 행은 폐기했다** (2026-08-01). `page_code='EXECUTIVE'` 가 없어졌다.
> 전사 숫자를 봐야 하는 사람에게는 `MASTER` 를 준다 — 단 **수정권이 딸려 간다.** 임원이 여러 명이 되면 `page_code` 부활을 검토한다 (`PERMISSION.md` 백로그).
| AI (비타메이트) | — | — | 공고 요약 초안 · 문서 분석 (사람이 반드시 검토) |
| 발주처 · 외주업체 | 외부 | — | 시스템 사용자 아님 |

## A. 공고 → 프로젝트

### UC-01. 공고 확인 → 프로젝트 생성

| | |
|---|---|
| **행위자** | 입찰 담당자 (`page_code='BIDDING'`) |
| **화면** | 공고 / 입찰 탭 |

- 시스템이 등록된 크롤링 링크를 **주기적으로 수집** → 신규 건 배지
- **자동 스크리닝** — 회사 등록 업종·지역과 대조해 참여 불가 건을 흐리게
- 표시: 공고명 · 공고기관 · 공고번호 · 기초금액 · 추정가격 · **투찰마감(D-n)** · 평가방식
- `프로젝트 시작` → **템플릿 선택 또는 빈 프로젝트**로 생성 (상태 `진행 전`)
- **`project.bid_notice_id` 링크만 건다.** 값을 복사하지 않는다

> ⛔ **스냅샷 복사와 `원본 변경됨` 배지는 폐기했다** (2026-08-01, DOMAIN §1-1).
> 금액·일정은 필요할 때 `bid_notice` 를 조인해 읽는다. 대신 **정정공고를 감지할 수단이 없다** → DOMAIN §15 백로그.

> B2B 는 공고 없이 **프로젝트를 직접 생성**한다. 공고 없는 프로젝트가 정상 케이스다.

### UC-02. 조건 등재

| | |
|---|---|
| **행위자** | 실무자 |
| **화면** | 프로젝트 설정 |

- 자동 채움: **없다.** 금액·일정·제한은 `bid_notice` 를 조인해 **표시만** 한다 (복사하지 않음)
- 입력: **기간(시작~종료)** · 사업 카테고리(**복수 선택 가능**) · 메모
  - ⛔ **담당팀은 없다** (2026-08-01 폐기, DOMAIN §2). 참여자는 개인 단위로만 넣는다
- **날짜를 넣으면 캘린더에 자동으로 뜬다.** 별도 등록 스위치 없음
- **투찰마감 · 개찰일은 `불가역` 등급** — 필터로도 못 끄고 D-7/3/1 알림이 강제된다

> ~~투입 공수~~ 는 범위 밖이다 (`PRODUCT.md` §3-3).

### UC-03. AI 요약 — 결재 판단용

| | |
|---|---|
| **행위자** | 실무자 → AI |
| **화면** | 공고 탭 (프로젝트 생성 전에도 가능) |

- 입력: 공고 원문 + 등재 데이터 + 회사 컨텍스트(수행 실적 · 등록 업종 · 유사 과업)
- 출력: **금액 / 일정 / 과업 성격 / 리스크**
- **AI 초안은 사람이 반드시 검토·수정한 뒤 확정한다.** 그대로 올리지 않는다
- 프롬프트 · 강조 항목은 회사가 편집 가능

> 프로젝트 안의 **AI 블록과는 다른 기능**이다. 이건 공고 영역 기능이고, AI 블록은 스텝 안의 문서 작업용이다.

## B. 참여 결정

### UC-04. 참여 여부 결재

| | |
|---|---|
| **행위자** | 실무자 → 부서 검토자 → 결재자 |
| **화면** | 결재 스텝의 **결재 상신 블록** |

- 결재선을 **템플릿에서 불러오거나 직접 구성**. 금액대별 자동 결정 규칙은 없다
- **부서 검토자(원가분석본부 · 건설사업본부 등)를 결재선 노드로 포함**한다
- 값은 **`승인` / `반려` 2값 + 사유**. ~~`O`/`△`/`X`~~ 3값은 폐기 — △ 는 `반려 + 사유` 로 같은 흐름을 탄다
- 대상: AI 요약 카드 + 첨부 파일 블록. **상신 시점 버전 고정**

| 분기 | 결과 |
|------|------|
| 전원 승인 | UC-05 로 |
| 반려 | 수정 → 재상신. **대상 버전이 바뀌면 전원 재승인** |
| 최종 미참여 | 프로젝트 상태 **`종결` + 사유 필수** |

> 갓 만든 프로젝트에는 스텝이 없어 결재를 올릴 수 없다. **그래서 생성 시 템플릿을 고르거나 스텝을 먼저 만든다.**

## C. 입찰 준비 → 개찰

### UC-05. 스테이지 · 스텝 구성

| | |
|---|---|
| **행위자** | 실무자 |
| **화면** | 프로젝트 사이드바 `+스텝추가` |

- ~~모듈 추가~~ → **템플릿 적용 또는 직접 추가**
- 평가방식에 따라 구성이 달라진다 — 제안서 건은 `제안서 작성` 스텝, 가격 건은 `견적 산출` 스텝
- **스테이지는 분류 라벨**이다. 상태도 권한도 갖지 않는다
- **스텝 순번은 정렬일 뿐 선행 완료를 강제하지 않는다.** 제안서와 견적은 동시에 돈다

### UC-06. 참여인원 선정

| | |
|---|---|
| **행위자** | 실무자 (프로젝트 관리자) |
| **화면** | 프로젝트 > 설정 > 참여자 |

- **담당팀을 고르면 인력 추가 후보가 그 팀으로 좁혀진다**
- **참여자는 개인 단위로만 확정.** 팀을 넣었다고 팀원 전원이 참여자가 되지 않는다
- 권한: 프로젝트 기본값(뷰어 / 편집자 / 관리자) → **스텝별 오버라이드 가능**

### UC-07. 견적 산출 / 제안서 작성

| | |
|---|---|
| **행위자** | 실무자 |
| **화면** | 해당 스텝 > 블록 |

- 블록 구성: **텍스트**(목차 · 본문) + **파일 업로드**(버전) + **체크리스트**(작성 확인 항목)
- **파일은 하나고 버전이 붙는다.** `제안서_최종2.pdf` 를 만들지 않는다
- 체크리스트 항목 중 남에게 시킬 게 생기면 **`이슈로 승격`**

### ~~UC-08. 품질관리 검토~~ — 삭제

품질검토는 **결재선의 한 노드**로 흡수됐다. 결재선에 `품질관리실 박OO` 를 넣으면 그게 곧 품질검토고, `승인 / 반려` 가 곧 `적정 / 보완` 이다.
검토자 · 검토일 · 지적사항은 **결재 이력으로 그대로 남는다.** 자료종류별 체크리스트는 **체크리스트 블록**으로 분리한다.

### UC-09. 결재 → 송부

| | |
|---|---|
| **행위자** | 결재자 → 실무자 |
| **화면** | 결재 상신 블록 → 송부 스텝 |

- 결재 블록이 **같은 스텝의 파일 블록을 지목**한다. 파일을 복사하지 않는다
- **결재가 완료돼야 송부 스텝으로 넘어간다**
- **송부는 스텝이다.** 별도 블록 타입이 없다
  - **발송자 = 그 스텝을 완료 처리한 사람**, **발송일시 = 완료 시각** → 로그에서 자동으로 남는다
  - 방법(전자입찰 / 메일 / 공문) · 수신처 · 첨부 목록은 텍스트 · 체크리스트 블록에 기록
  - ⚠️ 방법별 · 수신처별 **집계는 안 된다.** 필요해지면 블록 타입을 추가한다

### UC-10. 투찰 🚧 v1 범위 축소 (2026-08-01)

| | |
|---|---|
| **행위자** | 실무자 |
| **화면** | 투찰 스텝 |

- 투찰 사실은 **스텝 완료**로 표현한다. 완료자·완료시각이 곧 투찰자·투찰일자다 (UC-09 송부와 같은 패턴)
- 금액·하한율 검증은 **텍스트 / 체크리스트 블록에 기록**한다

> ⛔ **투찰금액을 구조화 필드로 저장하지 않는다** (DOMAIN §2).
> `project` 에서 입찰 관련 금액을 전부 뺐기 때문에 저장할 곳이 없다.
> 구조화가 필요해지면 `bid_participation` 테이블을 신설한다 → DOMAIN §15 백로그.
> **투찰하한율 대비 자동 검증도 함께 미룬다** (`bid_notice` 에 하한율 필드가 없다 — SCREEN G-11).

### UC-11. 개찰 결과 + 사유 🚧 v1 범위 축소 (2026-08-01)

| | |
|---|---|
| **행위자** | 실무자 |
| **화면** | 개찰 스텝 |

- 개찰일에 **결과 입력 알림** (기한 임박 = 액션 요구 알림)
- **결과는 프로젝트 상태로만 남긴다** — 낙찰/선정이면 `진행 중`, 아니면 `종결 + 사유`
- **사유 기록 필수** — 왜 됐는지 / 왜 떨어졌는지 (`project.close_reason_code` + `close_reason_note`)

> ⛔ **순위 · 낙찰가 · 낙찰업체 · 평가점수는 저장하지 않는다** (v1 범위 밖).
> 따라서 **낙찰률 집계도 v1 에서는 불가능하다** — [`PRODUCT.md`](PRODUCT.md) 파생문제 참조.
> 상세 기록은 개찰 스텝의 텍스트 블록에 자유 서술로 남긴다.

| 분기 | 결과 |
|------|------|
| 낙찰 · 선정 | UC-12 로. 상태 `진행 중` |
| 유찰 · 미선정 · 하한가 미달 · 취소 | 상태 **`종결` + 사유** |

## D. 수행

### UC-12. 수행 단계 구성

- 템플릿 적용 또는 직접 추가
- **보고서 회차마다 스텝 1개.** 1차만 / 1·2차 / 1·2·최종 — 회차 수는 자유
- 여기서 입찰과 과업이 **하나의 프로젝트 안에서 이어진다** (별도 키가 필요 없다)

### UC-13. 계약 · 업무코드 · 업무자

| | |
|---|---|
| **화면** | 계약 스텝 |

- 계약일 · 계약기간 · **계약금액(도급금액)** · 계약서 파일 블록
- ⚠️ **계약금액은 프로젝트 속성이다** (`project.contract_amount`). §7-3 의 `잔액 = 계약금액 − Σ입금액` 계산이 이 값에 의존한다
  - 입찰 금액을 전부 뺀 뒤에도 **이 하나는 남긴다.** 공고 없는 B2B 프로젝트도 계약금액은 있다 (DOMAIN §2)
- 업무코드 선택 → 관리부서 · 책임자 · 관련지침 자동 결정
- **스텝 책임자** 지정

### UC-14. 보고서 N차 — 회차마다 스텝 1개

각 회차 스텝이 아래 흐름을 **독립적으로** 돈다.

| 단계 | 행위자 | 기록 |
|------|--------|------|
| ① 작성 | 실무자 | 파일 블록 v1, v2… |
| ② **결재** | 결재선(품질관리실 노드 포함) | 승인 / 반려 + 사유 · **대상 버전 고정** |
| ③ 송부 | 실무자 | 송부 스텝 완료 → 발송자 · 발송일시 자동 |
| ④ 송부확인 | 실무자 | 발주처 수신 확인일 · 확인 방법 |
| ⑤ 발주처 피드백 | 실무자가 대신 기록 | 보완 요청 내용 · 회신기한 → **①로 루프** |

**규칙: 결재 완료 없이 송부 불가.** (구: "품질검토 `적정` 없이 송부 불가")
**반려 후 파일을 고쳤으면 전원 재승인**한다 — 앞 결재자가 본 적 없는 버전이기 때문이다.

### UC-15. 외주 — 해당 건만

- 템플릿으로 외주 스테이지를 추가하거나 직접 구성
- 범위 결정 → 견적 의뢰 → **업체선정 품의(결재 블록)** → 발주 · 계약 → 기성 지급
- 기록: 공종별 자체/외주 구분 · 업체 · 견적금액 · 선정사유 · 외주금액 · 기성 회차·금액·지급일

> **외주비 집계 필드는 없다.** 수익성 분석이 범위 밖이므로 외주비는 해당 스텝의 기록으로만 남는다.

### UC-16. 발주처 확인 · 완료계 제출

- 발주처 확인: 승인일 · 승인자 · 승인 문서 파일 블록

## E. 정산 · 실적

### UC-17. 정산 회차 구성

| | |
|---|---|
| **행위자** | 실무자 |

- ~~정산 모듈 추가 + 회차 수 조정~~ → **정산 회차마다 스텝 1개 + 입금확인 블록 1개**
- **입금확인 블록이 곧 정산 회차다.** 별도 회차 레코드는 없다
- 블록 제목이 회차명이 된다 (`1차 정산(선급 60%)`, `2차 정산(기성 20%)`)
- 템플릿으로 `3회 60/20/20`, `2회 선급50/기성50` 같은 골격을 깔 수 있다

> 정산 시점은 흩어진다 — 선급금은 계약 직후, 기성은 6개월 뒤, 잔금은 1년 뒤. **그래서 회차마다 스텝이다.**

### UC-18. 정산 N차 진행

| 단계 | 행위자 | 어디서 |
|------|--------|--------|
| ① 청구 조건 확인 | 실무자 | 정산 회차 스텝 |
| ② 청구서 작성 | 실무자 | 파일 블록 → **결재** |
| ③ **세금계산서 발행** | **재무 (`page_code='FINANCE'` + `EDITOR`)** | **재무 탭** |
| ④ **입금 확정 · 매칭** | **재무 (`page_code='FINANCE'` + `EDITOR`)** | **재무 탭** |
| ⑤ 확인 | 실무자 | 입금확인 블록 (**읽기 전용**) |

**매칭은 2단이다:**

```
① 프로젝트 매칭 (필수)   ← 블록이 없어도 가능. 돈은 블록보다 먼저 들어올 수 있다
② 블록 연결 (선택)       ← 입금확인 블록이 생기면 그때 연결
```

- ⚠️ **실무자는 입금 확인을 스스로 체크할 수 없다.** 돈 관련 확정은 재무만 한다
- 자동 매칭은 **추천 후보 정렬까지만.** 확정 버튼은 사람이 누른다 (은행 적요에 용역명은 안 온다)
- 프로젝트 > 정산 메뉴에서 회차별 `청구 / 계산서 / 입금` 3열을 조회한다 — **등록·수정은 불가**
- ⚠️ **블록 없이 매칭만 된 입금은 정산 메뉴에 경고로 뜬다.** 안 그러면 그 돈이 프로젝트 어디에도 안 보인다

```
1차 정산: 청구✓ 계산서✓ 입금✓
2차 정산: 청구✓ 계산서✓ 입금 —
3차 정산: 청구 — 계산서 — 입금 —
```

**이 세 줄이 동시에 성립한다.** 회차가 각각 스텝이고 각각 블록이기 때문이다.
