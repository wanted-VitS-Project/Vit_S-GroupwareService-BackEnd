# 🔐 권한 체계

**최종 업데이트**: 2026-08-03 (ADMIN 시스템 계정 확정 · 그룹·직급 추가 · `page_code` 재확정 진행) · 이전 2026-08-01
**작성/관리**: 동훈 · **2026-08-03 수정**: 동현
**연관 문서**: [`DOMAIN.md`](DOMAIN.md) · [`ERD.md`](ERD.md) · [`PAGE.md`](PAGE.md) · [`PROJECT.md`](PROJECT.md) · [`BLOCK.md`](BLOCK.md)

> 이 문서는 **"누가 무엇을 할 수 있는가"** 만 정의한다.

> 🚨 **`MASTER` 는 최상위가 아니다.** 실권 최상위는 **`ADMIN`**, `MASTER` 는 CEO 가 전사를 들여다보는 role 이다.

---

## 0. 원칙

- 권한은 **전부 인원별 직접 지정**이다. **부서·직급·그룹은 권한 판정에 쓰지 않는다.**
- 예외 하나 — 템플릿 공개 범위의 `팀` 단계는 부서를 쓴다. **가시 범위이지 권한이 아니다** (`DOMAIN §13-5`).

### 0-1. ⭐ 그룹 · 직급은 권한이 아니다 (2026-08-03 추가 · 동현)

권한 판정에 쓰이지 않지만 **화면에 존재하는 조직 축**이라 여기 명시한다.

| 축 | 정체 | 권한 판정 | 왜 있나 |
|---|------|:---:|---|
| **부서** `department` | 조직도. 최대 2단(본부 > 팀) | ❌ | 소속 표시 · 목록 필터 |
| **직급** `job_position` | 사원·대리·과장 등. ADMIN 이 생성·수정·삭제 | ❌ | 표시 · 정렬. 사원 등록의 직급 드롭다운 원본 |
| **그룹** `employee_group` | 부서와 별도인 **사람 묶음** | ❌ | **권한 부여 시 여러 명을 한 번에 고르는 도구** |

**그룹이 왜 권한이 아닌가** — 그룹으로 권한을 주면 **저장은 개인 단위 스냅샷**이다. 그룹 참조를 남기지 않는다.

```
재무그룹을 선택 → 구성원 5명에게 각각 page_permission 행 5개 생성
이후 재무그룹에 신입이 추가돼도 → 그 사람은 권한이 없다
재무그룹을 삭제해도       → 기존 5명의 권한은 그대로 남는다
```

그래서 **그룹이 생기고 없어져도 권한이 흔들리지 않는다.** 부서를 권한에서 뺀 것과 같은 이유다.

⛔ **`page_permission` 이나 `step_permission` 에 `group_id` 를 넣지 마라.** 그룹은 선택 UI 의 편의이고 저장 대상이 아니다.

> 상세 API — [`../../api/employee-group.md`](../../api/employee-group.md) · [`../../api/job-position.md`](../../api/job-position.md) · [`../../api/department.md`](../../api/department.md)

## 1. 권한은 3층이다

| 층 | 값 | 저장 | 행이 없으면 |
|----|-----|------|-----------|
| **① 전역 role** | `ADMIN` > `MASTER` > `MEMBER` | `account.role` (단일값) | — (항상 하나는 있다) |
| **② 화면 접근** | `VIEWER` · `EDITOR` | `page_permission` | **접근 불가** (차단) |
| **③ 프로젝트 / 스텝** | `VIEWER` · `EDITOR` · **`NONE`** | `project_member` · `step_permission` | 상위 층에서 **상속** |

## 2. 전역 role — 3종

| role | 성격 | 한 줄 |
|------|------|------|
| **`ADMIN`** | 조직 관리자 = 실권 최상위. **시스템 계정** | 계정·role·화면권한 **부여·회수를 독점**한다. `MASTER` 가 할 수 있는 걸 다 할 수 있다 |
| **`MASTER`** | CEO — 전사 열람·개입 | 모든 프로젝트·페이지에 들어가 **보고 고칠 수 있다.** 단 **부여·회수는 못 한다** |
| **`MEMBER`** | 일반 사용자 | 기본값. 나머지는 ②·③ 층으로 받는다 |

> ⭐ **`ADMIN` 은 사람이 아니다** (2026-08-03 확정 · 동현). 실제 사원에게 부여하는 role 이 아니라
> **개발자가 직접 발급하는 시스템 계정**이다. 자세한 규칙은 §2-4.

### 2-1. ⭐ 세 role 의 차이

| 항목 | `ADMIN` | `MASTER` | `MEMBER` |
|------|:-------:|:--------:|:--------:|
| 관리자 탭 진입 (P-60·P-61·P-63·P-64) | ✅ | ❌ | ❌ |
| 계정 발급 · 비밀번호 초기화 · 비활성화 | ✅ | ❌ | ❌ |
| **role 부여/회수** — `MASTER`·`MEMBER` 만. **`ADMIN` 은 부여 대상이 아니다** (§2-4) | ✅ | ❌ | ❌ |
| **`page_permission` 부여/회수** | ✅ | ❌ | ❌ |
| 부서 · 사원 · 사업 카테고리 CRUD | ✅ | ❌ | ❌ |
| 퇴사 처리 | ✅ | ❌ | ❌ |
| 템플릿 전사 승격 | ✅ | ❌ | ❌ |
| `page_permission` 행 없이 공고·재무 탭 열람 | ✅ | ✅ | ❌ 행 필요 |
| 전사 현황 탭 (P-50·P-51) | ✅ | ✅ | ❌ |
| 참여자가 아닌 프로젝트 **열람** | ✅ | ✅ | ❌ |
| 참여자가 아닌 프로젝트 **수정** | ✅ ⚠️ | ✅ ⚠️ | ❌ |
| **결재 권한** | ❌ 무관 | ❌ 무관 | 결재선에 있으면 ✅ |
| 자기 계정의 role 행 수정 | ❌ 차단 | — (애초에 권한 없음) | ❌ |

⚠️ **`ADMIN`·`MASTER` 가 남의 프로젝트 데이터를 고치면 로그에 `상위권한으로 수정`(`privileged_override = 1`) 을 표기한다** (`DOMAIN §11-4`).

### 2-2. role 확정 사항

- **서열형 단일값 ENUM.** `ADMIN` 이 `MASTER` 를 포함하므로 다중 부여가 없다.
- **부여는 전부 인원별 직접 지정.** 부서에서 상속하지 않는다 (§0).
- **`DEVELOPER` role 은 없다.** `ADMIN` 으로 흡수.
- **`employee.is_system = 1` 은 사람이 아닌 계정 전부다** — `ADMIN` 공용 계정 · 배치 · 크롤러.
  사람을 고르는 모든 조회(사원 목록 · 프로젝트 멤버 · 그룹 구성원 · 담당자 지정)에서 **제외한다.**
- **`EXECUTIVE` · `FINANCE` · `BIDDING` role 은 없다.** `FINANCE`·`BIDDING` 은 ② 층 `page_code` 다 (§3-1).
- **`QUALITY` role 은 없다.** 품질검토는 결재선의 한 노드다 (`DOMAIN §8-1`).

### 2-3. `ADMIN` 은 자기 계정의 role 행을 수정할 수 없다 ⚠️

- 애플리케이션이 자기 role 행 수정 경로를 막는다.
- ~~마지막 `ADMIN` 의 회수·비활성화도 막는다. `ADMIN` 수가 1명이면 거부한다.~~
  → **불필요해졌다** (2026-08-03). `ADMIN` 은 시스템 계정이라 `is_system` 검사로 모든 변경 API 에서 이미 차단된다 (§2-4).

### 2-4. ⭐ `ADMIN` 은 겸직하지 않는다 — 시스템 계정이다

**2026-08-03 확정 (동현)** — 이전 판(`겸직은 표현하지 않는다. CEO 이면서 조직관리자면 ADMIN 을 준다`)을 대체한다.

| 항목 | 확정 |
|------|------|
| 정체 | **시스템 계정.** 실제 사원에게 부여하는 role 이 아니다 |
| 발급 | **개발자가 직접 발급한다.** 애플리케이션에 부여 화면·API 가 없다 |
| 계정 수 | **복수 허용.** 필요하면 개발자가 추가 생성해 제공한다 |
| 사원 레코드 | `employee.is_system = 1` 인 **가상 사원**에 붙는다. 이름 외 인적 사항은 비어 있다 |
| 겸직 | **불가.** 인사 담당자가 ADMIN 업무를 하려면 **자기 계정과 별도로 ADMIN 계정으로 로그인**한다 |
| 목록 노출 | 사원 목록·멤버 선택·담당자 지정에 **나타나지 않는다** |
| 감사 | 공용 계정이라 **행위자를 사람 단위로 특정할 수 없다.** 시연 범위에선 감당하고, 필요해지면 계정을 사람별로 쪼갠다 |

⛔ **`role` 변경 API 로 `ADMIN` 을 부여하려 하면 거부한다.** 실제 사원이 ADMIN 을 갖는 상태를 만들지 않는다.

> ⚠️ **와이어프레임 주의** — 사원 관리 목록에 권한이 `관리자` 인 실제 사원(인사팀 팀장)이 그려져 있다.
> 위 확정과 어긋나므로 **화면 수정 대상**이다.

## 3. 화면 접근 — `page_permission`

```
page_permission(page_code, user_id, permission)

  page_code  = 아래 3-1 표 참조
  permission = VIEWER | EDITOR
  행이 없으면 → 그 탭이 아예 안 열린다
```

> ⭐ **컬럼명은 `user_id` 다** (2026-08-03 수정 · 이전 `employee_id`).
> 사람을 가리키는 모든 FK 는 `employee.user_id`(사번 · `VARCHAR(20)`)를 참조한다. `account_id` 는 계정 관리 밖으로 나가지 않는다.

### 3-1. `page_code` 목록 ⚠️ 재확정 진행 중

**2026-08-03 — 와이어프레임 기준 5개로 가기로 결정했다 (동현).** 이전 판은 `BIDDING`·`FINANCE` 2개였다.

| `page_code` | 페이지명 | 대응 화면 |
|------------|---------|----------|
| `PROJECT_MANAGEMENT` | 프로젝트 관리 | 🔴 **미정** |
| `BUDGET_STATUS` | 예산 현황 | 🔴 **미정** |
| `DISCLOSURE_STATUS` | 공시 현황 | 🔴 **미정** |
| `HR_APPOINTMENT` | 인사 발령 | 🔴 **미정** |
| `PAYROLL` | 임금 명세서 | 🔴 **미정** |

> 🔴 **미해결 — 5개 중 어느 것도 `PAGE.md` §2 의 화면(P-00~P-70)에 대응하지 않는다.**
>
> | 이전 2개 | 대응 탭 | 새 5개 | 대응 탭 |
> |---|---|---|---|
> | `BIDDING` | 공고/입찰 (P-10~P-16) | 프로젝트 관리 | 프로젝트 탭은 **전원 오픈**이라 `page_code` 가 없다 |
> | `FINANCE` | 재무 (P-40~P-44) | 예산 현황 · 인사 발령 · 임금 명세서 | **화면이 아예 없다** |
> | | | 공시 현황 | 공고/입찰과 비슷하나 이름이 다르다 |
>
> **탭 구조를 다시 정하지 않으면 이 5개는 열 화면이 없다.** `PAGE.md` §1 의 탭 8개와 `PRODUCT.md` 범위까지 걸리는 문제다.
> 팀 논의가 필요하다 — 그때까지 **구현 착수 금지.**

| 규칙 | 확정 |
|------|------|
| **전사 현황** | `page_code` 가 아니라 **`MASTER` 이상**이 연다 |
| **부여 주체는 `ADMIN`** | `ADMIN` 이 `page_permission` 행을 넣어 연다 (§2-1) |
| **`ADMIN`·`MASTER` 는 행이 없어도 통과** | 전역 role 이 서열형이므로 (§2) |

### 3-2. 화면에서는 `X / 뷰어 / 편집가능` 3지선다 — `X` 는 행 삭제다

| 화면 선택 | 저장 |
|----------|------|
| **`X`** | **`page_permission` 행을 지운다** |
| `뷰어` | `permission = VIEWER` 행 |
| `편집가능` | `permission = EDITOR` 행 |

⛔ **`page_permission.permission` 에 `NONE` 값을 추가하지 마라.** 행 자체가 없는 게 차단이다. ③ 층(`step_permission`)의 `NONE` 과는 역할이 완전히 다르다 (§4-2 · §7-1).

> 회수 이력은 `activity_log` 로 남긴다. 권한 행에 이력을 담지 않는다.

### 3-3. 탭을 만드는 기준

| 기준 | 예 | `page_code` |
|------|-----|------------|
| ① **프로젝트 밖에 자기 데이터가 있다** | 공고/입찰 · 재무 | **있다** |
| ② **"내 것"을 사람 기준으로 모아 보는 뷰다** | 결재관리 · 알림 · 홈(내 할일) | **없다** — 전원에게 열린다 |

- ②는 데이터 소유를 바꾸지 않는다. 결재 데이터는 프로젝트 안 결재 블록 소유(`approval.block_id`)다.
- ⛔ **②에 `page_code` 를 만들지 마라.** 남의 결재는 애초에 목록에 안 뜬다.
- 품질검토는 프로젝트 안 결재선의 한 노드다. 탭도 `page_code` 도 없다.

## 4. 프로젝트 · 스텝 권한

| 항목 | 확정 |
|------|------|
| 값 | **3값** — `VIEWER` / `EDITOR` / **`NONE`** |
| **`MANAGER`** | **없다.** 관리자 성격의 작업은 전역 role 이 처리한다 |
| 저장 층 | **2층** — 프로젝트(기본값) + 스텝(오버라이드) |
| **판정** | **상속.** 스텝에 행이 없으면 프로젝트 권한을 그대로 쓴다 |
| 스테이지 | **권한을 저장하지 않는다.** 화면의 "하위 스텝 일괄 적용"은 편의 기능이고 데이터는 스텝에만 떨어진다 |
| 기본값 | 참여 인원 등록 시 부여한 권한 → 스텝에서 개별 변경 |
| `VIEWER` 일 때 | **잠금** (보이되 못 고침) |
| **`NONE`** 일 때 | **안 보인다** (목록에서 제외) |
| 3층 오버라이드 | **만들지 않는다** |

### 4-1. 상속

```
스텝 권한 판정
  step_permission 행이 있다   →  그 값을 쓴다        (오버라이드)
  행이 없다                   →  project_member 값   (상속)
  project_member 에도 없다    →  참여자가 아니다 → 접근 불가
                                 (단 전역 role ADMIN·MASTER 는 통과)
```

### 4-2. `NONE` 이 상속을 끊는 값이다

프로젝트 `EDITOR` 인 사람에게 특정 스텝(예: `계약`)만 가리려면 `step_permission(step, 그 사람, NONE)` 을 넣는다. 행을 안 만들면 상속이라 정반대로 동작한다.

### 4-3. 누가 권한을 편집하나

| 대상 | 편집 주체 |
|------|----------|
| 프로젝트 참여자 · 권한 | **프로젝트 `EDITOR` 전원** + `MASTER` + `ADMIN` |
| 스텝 권한 오버라이드 | 동일 |

⛔ **자기 자신의 권한 행은 수정할 수 없다.** 애플리케이션이 막는다 (§2-3 과 동일 규칙).

`page_permission` 은 최상위 탭을, `step_permission` 은 프로젝트 안 스텝 하나를 연다. **대상이 다르다.**

## 6. 판정 순서

**위에서 통과하면 아래를 안 본다.**

```
1) 전역 role
     ADMIN   → 전부 통과 (수정 시 privileged_override 기록)
     MASTER  → 전부 통과 (수정 시 privileged_override 기록)
     MEMBER  → 계속

2) 최상위 탭 진입?
     page_code 가 붙은 탭 (§3-1 목록)
        page_permission 행 없음        → 차단 (탭 자체를 안 그린다)
        VIEWER                         → 조회만
        EDITOR                         → 조회 + 편집
     page_code 없는 탭(홈 · 알림 · 결재관리 · 프로젝트) → 통과

3) 프로젝트 진입?
     project_member 행 없음  → 차단
     NONE                    → 차단 (목록에서도 제외)
     VIEWER / EDITOR         → 계속

4) 스텝 접근?
     step_permission 행 있음 → 그 값       (오버라이드)
     행 없음                 → 3) 의 값     (상속)
     결과가 NONE             → 안 보인다
     결과가 VIEWER           → 잠금 (보이되 못 고침)

5) 블록 타입 제약 (§5)
     PAYMENT_CONFIRM · TAX_INVOICE_VIEW 의 확정·연결
        → page_code='FINANCE' + EDITOR 를 다시 확인
```

⚠️ **5) 를 빼먹지 마라.**

## 7. ⛔ 금지 · ⚠️ 헷갈리는 지점

### 7-1. 두 층의 `permission` 을 같은 enum 으로 묶지 마라

| | `page_permission` | `project_member` · `step_permission` |
|---|------------------|--------------------------------------|
| 값 | `VIEWER` · `EDITOR` | `VIEWER` · `EDITOR` · **`NONE`** |
| 행이 없으면 | **차단** | **상속** |
| 상위 층 | 없다 | 있다 (프로젝트 → 스텝) |

### 7-2. 헷갈리는 지점 4개

| # | 오해 | 사실 |
|---|------|------|
| **1** | `MASTER` 가 최상위다 | **아니다.** 실권 최상위는 `ADMIN` 이다 |
| **1-1** | `ADMIN` 을 사원에게 부여한다 | **아니다.** `ADMIN` 은 개발자가 발급하는 **시스템 계정**이고 겸직이 없다 (§2-4) |
| **1-2** | 그룹에 권한을 준다 | **아니다.** 그룹은 선택 도구이고 저장은 개인 단위 스냅샷이다 (§0-1) |
| **2** | `MASTER` 가 최종 결재자다 | **아니다.** 최종 결재자는 결재선의 마지막 순번(`approval_line.sequence_no` 최댓값)이고 건마다 달라진다 (`DOMAIN §8-1`) |
| **3** | `MASTER` 가 계정을 발급한다 | **아니다.** 계정·role·화면권한은 전부 `ADMIN` 소관이다 (§2-1) |
| **4** | `ADMIN` 은 조직만 관리하고 프로젝트는 못 본다 | **아니다.** `ADMIN` 이 `MASTER` 의 열람·수정을 **포함**한다 |
