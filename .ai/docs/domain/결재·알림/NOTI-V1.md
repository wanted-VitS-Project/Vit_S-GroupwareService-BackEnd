## 0. 한 줄 정의

**결재를 포함한 전 도메인이 공용으로 쓰는 알림 인프라.** 알림은 이벤트로만 생성되고, 본인 것만 조회·삭제·읽음 처리할 수 있다.

---

## 1. 범위

### 1-1. 만든다

| 영역 | 내용 |
|------|------|
| 알림 조회 | 목록(최신순, 카테고리/읽음 필터) · 이동 대상 조회 |
| 알림 처리 | 논리 삭제 · 개별 읽음(조회 시 자동) · 전체 읽음 처리 |
| 생성 인프라 | 이벤트 기반 생성 구조(도메인 무관 재사용) |

### 1-2. 안 한다 (명시)

| 항목 | 왜 |
|------|-----|
| 알림 생성 공개 API | 내부 이벤트로만 생성. 사용자가 직접 호출하는 API 없음 |
| 도메인별 알림 생성 로직 | 각 도메인(결재 등)이 이벤트를 발행하고, 언제·누구에게 보낼지는 그 도메인이 정한다 |
| 카테고리별 실시간 집계 API | 카테고리 탭 개수는 목록 조회를 카테고리별로 다시 호출해서 얻는다(별도 집계 API 없음) |

---

## 2. 요구사항

**표 형식**: `ID │ 대분류 │ 중분류 │ 소분류 │ 요구사항 │ 수용 기준`

### 2-A. 알림 생성 (`GEN`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **GEN-001** | 생성 | 인터페이스 | 공용 이벤트 | 알림은 `NotificationRequestedEvent(recipientUserId, notificationType, title, message, blockId)` 하나로 생성된다 | 도메인마다 다른 이벤트 클래스를 만들지 않는다 |
| **GEN-002** | 생성 | 처리 | 트랜잭션 커밋 후 처리 | 이벤트는 발행한 트랜잭션이 **커밋된 후에만** 알림으로 저장된다 | `@TransactionalEventListener(phase = AFTER_COMMIT)` 사용. 롤백 시 알림 생성 안 됨 |
| **GEN-003** | 생성 | 확장성 | 도메인 무관 | 결재 외 도메인(이슈 등)도 같은 이벤트로 알림을 생성할 수 있다 | 알림 도메인 코드 변경 없이 새 `notificationType` 값만 추가하면 된다 |
| **GEN-004** | 생성 | 데이터 | 개인별 생성 | 알림은 실제 수신자 한 명당 한 행씩 생성된다 | 결재선에 3명이 관련돼도, 그 순간 알림이 필요한 사람에게만 1건 생성 |

### 2-B. 알림 조회 (`VIW`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **VIW-001** | 조회 | 범위 | 본인 알림만 | 사용자는 자신에게 온 알림만 조회할 수 있다 | `recipient(user_id) == 요청자` 조건 강제 |
| **VIW-002** | 조회 | 정렬 | 최신순 | 알림 목록은 항상 최신순으로 조회된다 | 별도 정렬 옵션 없음 |
| **VIW-003** | 조회 | 필터 | 카테고리 | 사용자는 알림을 카테고리(결재/이슈/댓글/시스템 등)로 필터링할 수 있다 | `category` 쿼리 파라미터, `notification_type` 접두어 기준 매핑 |
| **VIW-004** | 조회 | 필터 | 읽음 여부 | 사용자는 안 읽은 알림만 필터링할 수 있다 | `isRead=false` 쿼리 파라미터 |
| **VIW-005** | 조회 | 제외 | 삭제된 알림 제외 | 논리 삭제된 알림은 목록에서 제외된다 | `deleted_at IS NULL` 조건 강제 |
| **VIW-006** | 이동 | 대상 조회 | 도메인 무관 구조 | 알림 클릭 시 이동 대상은 `type`/`targetId`/`extra` 구조로 응답된다 | 결재면 `type=APPROVAL, targetId=approvalId, extra.revisionId`. 매핑 없으면 `type=NONE`(에러 아님) |
| **VIW-007** | 이동 | 경로 해석 | block 경유 | 이동 대상은 `notification.block_id` → `block.type`을 거쳐 판정된다 | `block_id`가 없는 공통 알림은 `type=NONE` |
| **VIW-008** | 이동 | 제한 | 원본 직행 금지 | 알림 클릭은 결재 관리 상세로만 이동하고, 원본 업무 페이지로 바로 가지 않는다 | 원본 이동은 상세 화면의 별도 "원본 블록 보기" 액션으로만 가능 |

### 2-C. 알림 처리 (`ACT`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **ACT-001** | 삭제 | 논리 삭제 | 삭제 | 사용자는 본인 알림을 논리 삭제할 수 있다 | `deleted_at` 기록, 하드 삭제 아님 |
| **ACT-002** | 삭제 | 권한 | 타인 알림 삭제 차단 | 사용자는 다른 사용자의 알림을 삭제할 수 없다 | **403**(`NOTIFICATION_FORBIDDEN`) |
| **ACT-003** | 삭제 | 재삭제 | 이미 삭제된 알림 | 이미 삭제된 알림에 대한 재삭제 요청은 **404**로 응답한다 | 타인 알림과 구분되지 않도록 존재 여부를 노출하지 않는다 |
| **ACT-004** | 읽음 | 개별 | 조회 시 자동 읽음 | 알림 이동 대상 조회(클릭) 시 해당 알림이 자동으로 읽음 처리된다 | `read_at`이 조회 성공 시점에 기록된다 |
| **ACT-005** | 읽음 | 전체 | 일괄 읽음 처리 | 사용자는 본인의 안 읽은 알림을 한 번에 읽음 처리할 수 있다 | `read_at IS NULL`인 알림 전체의 `read_at`을 일괄 기록, 처리 개수 응답 |

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **알림 생성 공개 API는 만들지 않는다** | 사용자가 임의로 남에게 알림을 보낼 수 있으면 스팸 통로가 된다. 항상 비즈니스 이벤트가 트리거다 |
| **INV-02** | **알림 도메인은 특정 도메인(결재 등)을 몰라야 한다** | `type`/`targetId`/`extra` 구조로만 소통해야 새 도메인 추가 시 알림 코드를 안 건드린다 |
| **INV-03** | **`notification_type`은 VARCHAR로 관리한다 (DB ENUM 금지)** | 새 알림 유형이 늘 때마다 DDL을 안 내려면 열린 문자열이어야 한다 |
| **INV-04** | **알림에 `approval_id` 같은 도메인 FK를 두지 않는다** | `block_id` 하나로 모든 도메인을 대응한다. 도메인별 FK를 추가하면 확장할 때마다 컬럼이 늘어난다 |
| **INV-05** | **삭제는 논리 삭제만** | 알림도 이력의 일부. 하드 삭제하면 "왜 안 뜨는지" 추적이 안 된다 |
