- 2026-08-03 — 블록 생성/삭제 주체를 블록팀으로 정정(APR-001·BND-001~003), `approval_id`≠`block_id` 구조 확정(INV-08~10)

## 0. 한 줄 정의

**결재 블록에서 상신하고, 결재관리 탭에서 승인·반려한다.** 상신 시점의 문서·결재선을 고정해 "무엇을 승인했는지"가 영구히 특정되게 한다.

## 1. 범위

### 1-1. 만든다

| 영역 | 내용 |
|------|------|
| 결재 블록 | 생성 · 초안(제목·내용·문서·결재선) · 상신 |
| 재상신 | 반려 후 새 회차 생성 · 반려 지점부터 재개 |
| 결재 처리 | 승인 · 반려 |
| 결재 관리 | 목록 조회(기안/처리/전체) · 상세 조회 · 회차별 이력 조회 |

### 1-2. 안 한다 (명시)

| 항목 | 왜 |
|------|-----|
| 실제 파일 업로드 처리(스토리지 저장·인덱싱) | 공용 파일 업로드 API(파일 도메인) 소관. 결재는 `file_version_id`만 연결 |
| 알림 생성 로직 자체 | 알림 도메인이 이벤트를 받아 처리한다. 결재는 이벤트만 발행 |
| 회수(WITHDRAWN, 상신 후 자진 철회) | v1 범위 밖 → §5 백로그 |
| 문서 업로드 블록과의 연동 | 팀 합의로 폐지됨. 결재 블록에서 직접 업로드로 대체 (`BLOCK.md` §4-8 갱신 필요) |
| **`block` 행 자체의 생성·삭제** | **블록팀(동훈) 소관.** 결재는 이미 존재하는 `blockId`에 `approval` 상세만 붙인다. 블록 삭제도 블록팀이 처리하며, 결재는 잠금 조건(`approval.status`)만 제공한다 |
| **블록 카드 자체의 진행현황 미리보기 조회** | 블록팀의 통합 조회(LEFT JOIN)가 처리할 수 있다. 단 **결재관리 페이지(P-31/P-30)의 조회는 전부 결재 도메인 소관** — 겹치지 않는다 |

## 2. 요구사항

**표 형식**: `ID │ 대분류 │ 중분류 │ 소분류 │ 요구사항 │ 수용 기준`

### 2-A. 결재 블록 · 초안 (`APR`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **APR-001** | 결재 블록 | 생성 | 결재 상세 생성 | 기안자는 **이미 생성된** 결재 블록(`blockId`)에 결재 상세를 붙일 수 있다 | `POST /api/v1/blocks/{blockId}/approval` 호출 시 `approval`(DRAFT) + `approval_revision`(1회차, DRAFT)이 **하나의 트랜잭션**으로 생성된다. **`block` 행 INSERT는 하지 않는다**(블록팀이 이미 생성함). `block`이 없으면 **404**(`BLOCK_NOT_FOUND`), `block.type != APPROVAL`이면 **400**(`BLOCK_TYPE_MISMATCH`), 요청자가 기안자로 지정된다 |
| **APR-001-1** | 결재 블록 | 식별자 | approval_id ≠ block_id | `approval`은 자체 PK(`approval_id`, auto-increment)를 갖고 `block_id`는 별도 컬럼(UNIQUE, FK 아님)이다 | 두 값이 같지 않다. API 응답은 `blockId`·`approvalId`를 **모두** 내려준다 |
| **APR-001-2** | 결재 블록 | 삭제 잠금 | 진행 중 삭제 차단 | 블록팀은 결재 블록 삭제 전 `approval.status`를 확인해 `IN_PROGRESS`면 삭제를 막는다 | **동기 조회로 처리한다(이벤트 아님).** 결재 도메인은 별도 삭제 확인 API를 제공하지 않고, `approval.status` 컬럼 자체가 확인 대상이다 (`BLOCK.md` §8) |
| **APR-002** | 결재 블록 | 초안 | 제목·내용 작성 | 기안자는 DRAFT 상태에서 제목·내용을 작성·수정할 수 있다 | `revision.status == DRAFT`가 아니면 **409**(`APPROVAL_REVISION_NOT_DRAFT`). 기안자 아니면 **403**(`APPROVAL_NOT_DRAFTER`) |
| **APR-003** | 결재 블록 | 초안 | 상태 유지 | 초안은 페이지를 나갔다 들어와도 유지된다 | 별도 임시저장 API 없이, 매번 `PATCH`로 즉시 반영되고 조회 시 그대로 복원된다 |
| **APR-004** | 결재 블록 | 초안 | 알림 제한 | DRAFT 상태에서는 결재자에게 알림이 가지 않는다 | DRAFT 동안 `notification` row가 생성되지 않는다 |
| **APR-005** | 결재 문서 | 연결 | 문서 추가 | 기안자는 업로드 완료된 파일 버전을 결재 문서로 추가할 수 있다 | `file_version.upload_status == COMPLETED`인 것만 연결 가능. 아니면 **409**(`FILE_VERSION_NOT_READY`) |
| **APR-006** | 결재 문서 | 연결 | 중복 방지 | 동일 회차에 동일 `file_version_id`를 중복 연결할 수 없다 | `UNIQUE(approval_revision_id, file_version_id)`로 DB가 막는다 |
| **APR-007** | 결재 문서 | 연결 | 문서 제거 | 기안자는 DRAFT 상태에서 연결된 문서를 제거할 수 있다 | 하드 삭제(이력 보존 대상 아님) |
| **APR-008** | 결재 문서 | 연결 | 상신 후 고정 | 상신된 회차의 문서는 수정·교체할 수 없다 | `revision.status != DRAFT`인 회차의 문서 추가·제거 요청은 **409** |
| **APR-009** | 결재선 | 등록 | 결재자 지정 | 기안자는 DRAFT 상태에서 결재자·순서를 지정할 수 있다 | 기존 결재선 삭제 후 전체 재삽입. **요청 바디는 `userId`(이름 검색으로 선택)만 받는다 — 직책·부서는 클라이언트가 보내지 않는다.** 응답에는 `employee` 라이브 조회로 채운 이름·직책·부서 포함(INV-11) |
| **APR-010** | 결재선 | 검증 | 결재자 1명 이상 | 결재선은 최소 1명이어야 한다 | 0명이면 **400**(`APPROVAL_LINE_EMPTY`) |
| **APR-011** | 결재선 | 검증 | 순서 무결성 | 순서(`order`)는 1부터 중복·누락 없이 연속되어야 한다 | 위반 시 **400**(`APPROVAL_LINE_ORDER_INVALID`) |
| **APR-012** | 결재선 | 검증 | 일반 결재자 자격 | 일반 결재자는 해당 프로젝트의 member여야 한다 | 아니면 **400**(`APPROVAL_LINE_APPROVER_NOT_MEMBER`). **`MASTER`는 이 검증에서 제외**된다 |
| **APR-013** | 결재선 | 확정 | 최종 결재자 | 결재선 **마지막 순번**인 사람이 승인하면 결재가 완료된다 | `MASTER`일 필요 없다 (`BLOCK.md` §4-8, `PERMISSION.md` §7-2). 마지막 순번 강제 검증 없음 |
| **APR-014** | 결재선 | 제한 | 상신 후 고정 | 상신된 회차의 결재선은 수정할 수 없다 | `revision.status != DRAFT`인 회차의 결재선 수정 요청은 **409** |

### 2-B. 상신 · 재상신 (`SUB`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **SUB-001** | 상신 | 검증 | 사전 검증 일괄 | 상신 시 제목·내용·문서·결재선 유효성을 전부 검증한다 | 하나라도 실패하면 상태 변경 없이 해당 에러 코드 반환 |
| **SUB-002** | 상신 | 처리 | 상태 전이 | 상신 성공 시 회차는 `IN_PROGRESS`, 1번 결재선은 `ACTIVE`, 나머지는 `WAITING`, `approval`은 `IN_PROGRESS`로 바뀐다 | 단일 트랜잭션. `submitted_at` 기록 |
| **SUB-003** | 상신 | 알림 | 최초 결재자 알림 | 상신 직후 1번 결재자에게만 알림 이벤트가 발행된다 | `NotificationRequestedEvent(type=APPROVAL_REQUESTED)` 1건만 발행 |
| **SUB-004** | 상신 | 동시성 | 중복 상신 방지 | 동일 회차의 중복 상신 요청은 두 번째부터 거부된다 | `SELECT ... FOR UPDATE`로 잠근 뒤 `status == DRAFT` 재확인. 실패 시 **409** |
| **SUB-005** | 재상신 | 준비 | 새 회차 생성 | 반려된 결재는 새 회차(`revision_no + 1`)를 생성해 재작성한다 | `approval.status == REJECTED`일 때만 가능. 아니면 **409**(`APPROVAL_NOT_REJECTED`) |
| **SUB-006** | 재상신 | 준비 | 내용 복사 | 새 회차는 이전 회차의 제목·내용·문서를 복사한 채로 시작한다 | 이전 회차 원본은 **수정되지 않는다**(이력 보존) |
| **SUB-007** | 재상신 | 준비 | 결재선 재구성 | 새 회차의 결재선은 **반려자부터**만 재생성된다 | 반려자 이전(이미 승인한) 단계는 재생성하지 않는다 |
| **SUB-008** | 재상신 | 준비 | 멱등 처리 | 이미 생성된 DRAFT 회차가 있으면 새로 안 만들고 그대로 반환한다 | 중복 호출 시 200(기존 반환), 최초 호출만 201 |
| **SUB-009** | 재상신 | 재개 규칙 | 버전 무관 재개 | 재개 지점은 파일 버전 변경 여부와 **무관하게 항상 반려자부터**다 | 구버전 "버전 바뀌면 전원 재승인" 규칙 미적용 |
| **SUB-010** | 재상신 | 알림 | 반려자 알림 | 재상신 시 이전 회차의 반려자에게 알림 이벤트가 발행된다 | `APPROVAL_REQUESTED` 이벤트, 대상은 새 회차 1번 결재선(=이전 반려자) |

### 2-C. 승인 · 반려 (`PRC`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **PRC-001** | 승인 | 권한 | ACTIVE만 승인 가능 | 해당 결재선의 결재자 본인만, `status == ACTIVE`일 때만 승인할 수 있다 | 아니면 **403**(본인 아님) 또는 **409**(`APPROVAL_LINE_NOT_ACTIVE`) |
| **PRC-002** | 승인 | 처리 | 다음 단계 활성화 | 승인 시 다음 결재선이 있으면 `ACTIVE`로, 없으면(마지막 순번) 전체가 `APPROVED`로 완료된다 | 마지막 순번 승인 시 `revision`·`approval` 모두 `APPROVED`, `completed_at`·`finished_at` 기록 |
| **PRC-003** | 승인 | 의견 | 승인 의견 | 결재자는 승인 시 선택적으로 의견을 남길 수 있다 | 의견 없이도 승인 가능(필수 아님) |
| **PRC-004** | 승인 | 알림 | 다음 결재자/기안자 알림 | 다음 결재자가 있으면 그에게, 없으면(최종 승인) 기안자에게 알림이 발행된다 | 이미 처리한 이전 결재자에게는 알림이 가지 않는다 |
| **PRC-005** | 반려 | 권한 | ACTIVE만 반려 가능 | 해당 결재선의 결재자 본인만, `status == ACTIVE`일 때만 반려할 수 있다 | 승인과 동일 검증 |
| **PRC-006** | 반려 | 의견 | 반려 사유 선택 | 반려 사유는 **선택 입력**이다 | 사유 없이도 반려 가능(필수 아님) — `PAGE.md` P-30 "반려 사유 필수"는 오기, 정정됨 |
| **PRC-007** | 반려 | 처리 | 이후 단계 취소 | 반려 시 이후 `WAITING` 단계는 전부 `CANCELED`로, 회차·전체는 `REJECTED`로 전환된다 | 단일 트랜잭션 |
| **PRC-008** | 반려 | 알림 | 기안자 알림 | 반려 시 기안자에게만 알림이 발행된다 | `APPROVAL_REJECTED` 이벤트 |
| **PRC-009** | 처리 공통 | 동시성 | 중복 처리 방지 | 동일 결재선에 대한 중복 승인·반려 요청은 두 번째부터 거부된다 | `SELECT ... FOR UPDATE`로 잠근 뒤 `status == ACTIVE` 재확인. 실패 시 **409**(`APPROVAL_LINE_ALREADY_PROCESSED`) |

### 2-D. 결재 관리 · 조회 (`MGT`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **MGT-001** | 목록 | 조회 | 내가 처리할 결재 | 사용자는 자신이 현재 `ACTIVE`인 결재만 조회할 수 있다 (`결재 요청받음`) | `scope=pending` 시 요청자 본인 기준으로 필터 강제 |
| **MGT-002** | 목록 | 조회 | 내가 올린 결재 | 사용자는 자신이 기안한 결재를 조회할 수 있다 (`내가 올린 결재`) | `scope=drafted` 시 `drafterId`를 요청자 본인으로 강제 |
| **MGT-003** | 목록 | 조회 | 전체 조회 | `MASTER`는 전체 결재를 조회할 수 있다 (`전체`) | `scope=all`은 `MASTER`가 아니면 **403** |
| **MGT-004** | 목록 | 필터 | 상태·기간·검색 | 사용자는 상태·기간·제목·프로젝트명으로 목록을 필터링할 수 있다 | `status`/`fromDate`/`toDate`/`keyword` 쿼리 파라미터 지원 |
| **MGT-005** | 상세 | 권한 | ACTIVE·기안자·MASTER만 | 결재 상세는 기안자·해당 회차 ACTIVE 이상 결재자·`MASTER`만 조회 가능하다 | `WAITING` 결재자는 **403**(`APPROVAL_LINE_NOT_VIEWABLE`) |
| **MGT-006** | 상세 | 내용 | 원본 블록 이동 | 결재 상세에는 원본 업무 페이지·블록으로 이동할 정보가 포함된다 | 응답에 `blockOrigin{blockId, stepId, projectId}` 포함 |
| **MGT-007** | 이력 | 조회 | 회차별 이력 | 사용자는 회차별 제목·내용·문서·결재선·처리 결과를 조회할 수 있다 | 현재 회차와 종료된 회차가 `isCurrent`로 구분된다 |

### 2-E. 블록·결재관리 경계 (`BND`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **BND-001** | 경계 | 생성 | 블록 생성 주체 | 결재 블록(그릇)의 생성은 블록팀 API가 담당한다 | 결재 도메인은 `blockId`를 받는 시점부터 관여한다(APR-001) |
| **BND-002** | 경계 | 삭제 | 블록 삭제 주체 | 결재 블록(그릇)의 삭제도 블록팀이 담당한다 | 결재 도메인은 삭제 API를 제공하지 않는다. 삭제 전 잠금 확인만 `approval.status` 조회로 지원한다(APR-001-2) |
| **BND-003** | 경계 | 조회 | 블록 미리보기 vs 결재관리 | 블록 카드의 진행현황 미리보기는 블록팀 통합 조회가 처리할 수 있다 | **결재관리 페이지(목록·상세·이력, MGT-001~007)의 조회는 이 경계와 무관하게 전부 결재 도메인 API로 처리한다** — 어느 쪽이 블록 미리보기를 맡든 결재관리 API는 그대로 유지 |
| **BND-004** | 경계 | 삭제 후처리 | 블록 삭제 이벤트 구독 | 블록팀이 `block` 삭제 시 이벤트를 발행하면, 결재 도메인은 이를 구독해 연관 데이터(`approval`/`approval_revision`/`approval_line`/`approval_document`)를 정리한다 | 삭제 메서드 내에서 이벤트 발행 → 결재 쪽 리스너가 수신해 `approval.block_id`로 조회 후 삭제. 블록팀은 결재 내부 테이블 구조를 몰라도 된다 |

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **`MASTER`는 결재와 무관하다** | 최종 결재자는 결재선 마지막 순번일 뿐, role이 아니다. 강제하면 가벼운 결재(품질검토 등)까지 CEO가 껴야 한다 |
| **INV-02** | **상신된 회차는 수정 불가, 새 회차만 추가된다** | "무엇을 승인했는지"가 영구히 특정돼야 한다. 상신 후 내용이 바뀌면 승인의 의미가 사라진다 |
| **INV-03** | **재개는 항상 반려자부터, 버전 변경과 무관하다** | 회차(`approval_revision`) 단위로 이력이 남는 구조라, 버전 변경 여부로 재개 지점을 분기할 이유가 없다 |
| **INV-04** | **결재 문서는 `file_version_id`만 참조한다** | 파일 실물 저장·인덱싱은 공용 파일 도메인 소관. 결재가 스토리지를 직접 다루지 않는다 |
| **INV-05** | **알림 생성은 이벤트 발행으로만 한다** | 결재 도메인이 `notification` 테이블을 직접 알면 안 된다. 도메인 결합을 막기 위함 |
| **INV-06** | **반려 사유는 필수가 아니다** | 원 요구사항의 "절대 금지" 목록에 "반려 의견 필수 처리"가 명시돼 있다 |
| **INV-07** | **동시 처리는 비관적 락으로 막는다** | 승인/반려/상신 전부 `SELECT ... FOR UPDATE` + 상태 재확인 패턴을 쓴다. 낙관적 락 등 다른 방식과 섞지 않는다 |
| **INV-08** | **`block` 행 생성·삭제는 결재 도메인이 하지 않는다** | 블록팀이 그릇(`block`)을 만들고 지운다. 결재는 `blockId`를 받아 `approval` 상세만 붙인다. 반대로 하면 다른 8종 블록과 생성 책임 구조가 달라진다 |
| **INV-09** | **삭제 잠금 확인은 동기 조회로만 한다 (이벤트 아님)** | "삭제해도 되는가"는 사전에 막아야 하는 검증이라 비동기 이벤트로 처리할 수 없다. 블록팀이 `approval.status`를 직접 조회한다 |
| **INV-10** | **`approval_id`(PK)와 `block_id`(컬럼)는 서로 다른 값이다** | `approval.approval_id`는 auto-increment PK, `block_id`는 FK 제약 없는 UNIQUE 컬럼이다. 둘을 같은 값으로 가정하고 API를 설계하지 않는다 |
| **INV-11** | **결재선의 부서·직책은 스냅샷 저장하지 않고 항상 `employee` 라이브 조회로 채운다** | `approval_line`에 컬럼을 추가하지 않기로 함(DB 수정 없음). 결재선 등록 미리보기(APR-009)·이력 조회(MGT-007) 모두 조회 시점의 **현재** 부서·직책을 보여준다 — 인사이동 이후엔 과거 결재 기록도 현재 직책으로 표시됨(이력 정확성보다 스키마 단순성 선택) |
| **INV-12** | **블록 삭제에 따른 결재 데이터 정리는 이벤트 리스너로만 한다(동기 API 호출 아님)** | 블록팀과 결재팀의 코드 결합을 낮추기 위함. 블록팀은 삭제 이벤트만 발행하고, 결재 도메인 내부 테이블 구조(`approval_revision`/`approval_line`/`approval_document`)를 알 필요가 없다(BND-004) |
