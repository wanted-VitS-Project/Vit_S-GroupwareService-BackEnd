**최종 업데이트**: 2026-08-04 (초안 작성 — API 명세 · BLOCK · PERMISSION 근거로 요구사항/불변식 도출)
**담당**: 김동현
**근거**: [`../../../api/file.md`](../../../api/file.md) (10 엔드포인트) · [`../../global/BLOCK.md`](../../global/BLOCK.md) §4-4·§8 · [`../../global/PERMISSION.md`](../../global/PERMISSION.md) §4·§6

> 이 문서는 **구현자가 이것만 보고 만들 수 있게** 쓴 것이다.
> 모든 요구사항에 **수용 기준**이 붙어 있다. 기준을 통과하면 그 항목은 끝난 것이다.

## 0. 한 줄 정의

**파일은 블록에 붙지만 프로젝트에 소속되는 독립 애그리거트다. 버전이 쌓이고, 저장소와 DB 를 한 트랜잭션에 묶을 수 없어 스스로 상태(`업로드중 / 완료 / 실패`)를 갖는다.**

v1 의 목표는 **`보고서_최종2.xlsx` 를 죽이는 것**이다. 파일 하나에 버전을 쌓고, 지워도 되살리며, 결재가 고정한 버전을 안전하게 지킨다.

## 1. 범위

### 1-1. 만든다

| 영역 | 내용 |
|------|------|
| 업로드 | **2단계** — 시작(presigned 발급) → 클라이언트가 저장소에 직접 PUT → 완료 통보(서버가 저장소 확인) |
| 버전 | 같은 문서에 버전 append. 코멘트 선택 입력. **업로더 스냅샷**(이름·부서·직책) 고정 |
| 조회 | 블록 파일 목록 · 버전 이력 · **버전 단건**(결재용) · 다운로드 URL · 미리보기(PDF 앞 5p) |
| 수정 | 문서 표시명 변경 (원본 파일명은 불변) |
| 삭제 | **soft delete** — 휴지통 이동 · 복구 · 영구 삭제(확인 문자 검증 후 전 버전 저장소 제거) |
| 권한 | 파일 단위 권한 없음. **스텝 권한 3층 상속**을 그대로 따른다 (열람=미리보기+다운로드 / 편집=업로드·삭제) |
| 결합 | 결재·AI 가 고정한 `file_version_id` 보호 — 삭제 잠금 · 영구삭제 차단 · 버전 단건 조회 인터페이스 |

### 1-2. 안 한다 (명시)

| 항목 | 왜 |
|------|-----|
| **파일 단위 권한** | 스텝 권한을 그대로 쓴다. 파일마다 권한을 두면 스텝 권한과 충돌한다 (`PERMISSION.md` §4) |
| **버전 되돌리기 · 버전 삭제** | 버전은 append-only 다. 되돌리려면 새 버전을 올린다 (`VER-007`) |
| **파일 순서 변경** | 목록 정렬은 블록 연결일 오름차순 고정 (`FILE-003`) |
| **미리보기 다운로드 분리 권한** | 열람이면 미리보기·다운로드 둘 다 된다. B안(다운로드는 편집 권한)은 백로그 (`FILE-014`) |
| **PDF 외 미리보기** | v1 은 PDF 만. 다른 형식은 다운로드 안내 (`VER-010`) |
| **서버 경유 다운로드** | 바이너리를 서버가 나르지 않는다. 저장소 URL 을 발급해 클라이언트가 직접 받는다 (`VER-012`) |
| **파일 인덱싱 · 청크(`file_index`·`document_chunk`)** | AI 담당 영역이다. 이 문서는 `file`·`file_version`·`block_file` 만 다룬다 |
| **`approval_document` 자체** | 결재 담당 소관. 파일은 **버전 조회 인터페이스와 삭제 보호**만 제공한다 |

## 2. 요구사항

### 2-A. 업로드 — 2단계 (`FILE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **FILE-004** | **새 문서와 새 버전은 같은 API 다** | `fileId` 를 주면 그 문서의 새 버전, 안 주면 새 문서(버전 1). 검증·발급·완료 흐름이 완전히 같다 |
| **FILE-006** | 파일 바이너리는 이 API 로 올리지 않는다 | 응답의 `uploadUrl` 로 클라이언트가 저장소에 직접 PUT 한다. 서버는 메타데이터만 만든다 |
| **FILE-007** | `sizeBytes` 가 **50MB 초과면 거부** | `400 FILE_SIZE_EXCEEDED`. presigned 를 발급하지 않는다 |
| **FILE-008** | 실행 파일 확장자는 **블랙리스트로 차단** | `.exe .bat .sh .jar` 등. `400 FILE_EXTENSION_BLOCKED`. **화이트리스트가 아니라 블랙리스트** — 업무 문서 종류를 미리 못 박지 않는다 |
| **FILE-009** | 동명 문서가 있으면 **409 로 되묻는다** | `409 FILE_NAME_DUPLICATED`. 사용자가 확인하면 `allowDuplicateName: true` 로 재요청해 통과 |
| **FILE-010** | `uploadUrl` 에 **만료 시간을 실어 응답**한다 | 응답에 `expiresAt` 이 있다. 실제 만료 값은 §8 미확정 |
| **FILE-011** | 업로드 시작 시 버전은 **`업로드중`(UPLOADING) 상태로 생성**된다 | 이 버전은 목록·다운로드·미리보기·버전 이력 어디에도 나타나지 않는다 |
| **FILE-012** | 완료 통보가 안 온 `업로드중` 버전은 **정리 대상**이다 | 일정 시간(잠정 24h) 지난 미완료 버전은 배치가 회수한다. 빈 문서가 목록에 남지 않는다 (`FILE-002` 와 연동) |
| **FILE-013** | **완료 통보 시 서버가 저장소를 직접 확인**한다 ⭐ | 저장소에 객체가 없으면 `409 FILE_OBJECT_NOT_FOUND` 로 거부하고 버전을 **`실패`(FAILED)로 전환**한다. 클라이언트의 "완료" 통보만 믿지 않는다 |

> 🔑 **왜 서버가 확인하나** — 저장소 PUT 과 DB 커밋은 한 트랜잭션이 아니다 (§3 INV-01). 클라이언트가 "올렸다"만 보내고 실제로 안 올렸으면 **깨진 링크**가 생긴다. 완료 통보 시점이 유일하게 둘을 대조할 수 있는 지점이다.
> `checksum` 을 보내면 크기·체크섬도 대조한다 — 불일치면 `409 FILE_SIZE_MISMATCH` / `FILE_CHECKSUM_MISMATCH`.

### 2-B. 조회 — 블록 목록 (`FILE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **FILE-001** | 블록에 붙은 파일 목록을 조회한다 | `GET /blocks/{blockId}/files`. 없으면 빈 배열 |
| **FILE-002** | **완료된 버전이 하나도 없는 문서는 목록에 없다** | 업로드 실패로 버전이 0개인 문서가 빈 항목으로 뜨지 않는다 |
| **FILE-003** | 정렬은 **블록 연결일 오름차순 고정** | 순서 변경 기능이 없다. 항상 같은 순서로 내려온다 |
| **FILE-005** | 응답에 **`canEdit`** 를 담아 프론트 버튼 노출을 돕는다 | 요청자가 편집 권한이면 `true`. 권한 판정은 §2-E |
| **FILE-015** | 모든 파일 조회에서 **`block.deleted_at IS NULL` 을 명시적으로 확인**한다 ⭐ | 블록이 soft delete 됐으면 `404 FILE_BLOCK_NOT_FOUND`. FK `CASCADE` 에 맡기지 않는다 (§4 함정) |
| **FILE-020** | **휴지통도 같은 API 로 조회**한다 | `deleted=true` 파라미터. 데이터·권한이 같아 API 를 나누지 않는다. `deletedAt` 이 채워져 온다 |

### 2-C. 버전 (`VER`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **VER-001** | 버전 이력을 조회한다 | `GET /files/{fileId}/versions`. **버전 차수 내림차순** 정렬 |
| **VER-002** | 업로드마다 **`versionNo` 가 증가**한다 | 같은 문서에 두 번 올리면 v1 → v2. 차수가 재사용되지 않는다 |
| **VER-003** | 같은 `fileId` 로 올리면 **새 버전으로 append** 된다 | 기존 버전을 덮어쓰지 않는다 |
| **VER-004** | `name` 을 생략하면 **확장자를 뗀 원본 파일명**을 표시명으로 쓴다 | `제안서_v1.pdf` → 표시명 `제안서_v1` |
| **VER-005** | 버전 **코멘트는 선택 입력**이다 | 생략하면 `null`. 있으면 이력에 그대로 보인다 |
| **VER-006** | 완료 시점에 **업로더 스냅샷**(이름·부서·직책)이 버전에 박힌다 ⭐ | 이후 업로더가 부서를 옮기거나 퇴사해도 **당시 값이 그대로 조회**된다 |
| **VER-007** | 버전은 **append-only** — 삭제·되돌리기가 없다 | 버전 단건 삭제 API 가 존재하지 않는다. 이력은 조회 전용 |
| **VER-008** | PDF 면 **총 페이지 수를 추출**한다 | `pageCount` 가 채워진다. **추출 실패해도 업로드는 성공**하고 `pageCount` 만 비운다 |
| **VER-009** | `previewable` 은 **PDF 만 `true`** | 확장자·MIME 로 판정. 미리보기 버튼 노출 기준 |
| **VER-010** | 미리보기는 **PDF 만 지원**한다 | PDF 가 아니면 `409 FILE_PREVIEW_NOT_SUPPORTED`. 프론트는 다운로드를 안내 |
| **VER-011** | 다운로드는 **최신·과거 버전이 같은 API** 다 | `GET /file-versions/{fileVersionId}/download`. 버전 번호로 직접 지목 |
| **VER-012** | 다운로드는 **바이너리 대신 저장소 URL** 을 발급한다 | 서버를 거치지 않아 대역폭·메모리를 쓰지 않는다. `downloadUrl` + `expiresAt` 반환 |
| **VER-013** | **버전 단건 조회**를 제공한다 (결재용) ⭐ | `GET /file-versions/{fileVersionId}`. `latest=false` 면 결재가 고정한 버전 이후 새 버전이 올라온 것 → 경고 배지 근거. **문서가 휴지통에 있어도 반환**한다(`fileDeleted: true`) |

### 2-D. 수정 · 삭제 (`FILE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **FILE-016** | **문서 표시명만 수정**한다 | `PATCH /files/{fileId}`. 최대 255자. **원본 파일명은 안 바뀐다** — 버전마다 저장된 원본명은 그대로 |
| **FILE-018** | 삭제는 **휴지통 이동(soft delete)** 이다 | `DELETE /files/{fileId}`. 삭제 시각만 기록. 편집 권한자면 누구나 지운다(업로더 본인 제한 없음) |
| **FILE-019** | 휴지통 이동 시 **저장소 객체는 유지**한다 | 복구할 수 있어야 하므로 객체를 지우지 않는다 |
| **FILE-021** | 휴지통에서 **원래 블록으로 복구**한다 | `POST /files/{fileId}/restore`. 블록 연결은 휴지통 동안에도 유지된다 |
| **FILE-022** | 휴지통 **보관 기간에 제한이 없다** | 자동 영구삭제가 없다. 영구삭제는 사람이 명시적으로 실행 |
| **FILE-023** | 영구삭제는 **확인 문자를 서버가 검증**한다 | `confirmText` 가 정확히 `영구 삭제` 여야 한다. 불일치면 `400 FILE_CONFIRM_TEXT_MISMATCH` |
| **FILE-024** | 영구삭제는 **휴지통 문서만 대상**이다 | 목록에서 바로 영구삭제할 수 없다. 휴지통에 없으면 `400 FILE_NOT_DELETED` |
| **FILE-025** | 영구삭제는 **모든 버전의 저장소 객체를 제거**하고 되돌릴 수 없다 | 저장소 삭제가 일부 실패해도 **DB 는 지운다**. 실패한 키는 정리 대상으로 남긴다. `deletedVersionCount`·`storageDeletedCount` 반환 |

> ⭐ **영구삭제를 `DELETE` 가 아니라 `POST` 로 둔 이유** — 확인 문자를 본문으로 받아 검증해야 하는데, `DELETE` 에 본문을 담으면 일부 프록시·클라이언트가 본문을 버린다.

### 2-E. 권한 (`FILE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **FILE-014** | **열람 권한이면 미리보기·다운로드 둘 다** 된다 | 파일 단위 권한이 없다. 미리보기만 허용하고 다운로드를 막는 안은 백로그 |
| **FILE-026** | 파일 권한은 **스텝 권한을 그대로 따른다** | `file → block_file → block → step` 으로 스텝을 찾아 판정한다. 파일에 자체 권한 컬럼이 없다 |
| **FILE-027** | 스텝 권한은 **3층 상속**이다 ⭐ | `step_permission` 행이 있으면 그 값(오버라이드), 없으면 `project_member` 값(상속). **상속을 빼먹으면 프로젝트 권한만 가진 참여자가 전부 차단**된다 (`PERMISSION.md` §4-1) |
| **FILE-028** | 판정 결과가 **`NONE`·행 없음이면 차단**, `VIEWER`=조회, `EDITOR`=업로드·수정·삭제 | 조회 실패는 `403 FILE_ACCESS_PERMISSION_REQUIRED`, 편집 실패는 `403 FILE_EDIT_PERMISSION_REQUIRED` |
| **FILE-029** | `ADMIN`·`MASTER` 는 통과하되, **남의 프로젝트 파일을 수정·삭제하면 `privileged_override = 1`** 을 로그에 표기한다 | 전역 role 통과가 판정 1순위다 (`PERMISSION.md` §2-1·§6) |

### 2-F. 결재 · AI 결합 (`FILE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **FILE-031** | **진행 중 결재의 대상 파일은 휴지통 이동이 잠긴다** | `409 FILE_APPROVAL_IN_PROGRESS`. `message` 에 결재 정보를 담는다. 결재를 회수하거나 완료해야 지울 수 있다 |
| **FILE-032** | **결재가 참조하는 파일은(완료 포함) 영구삭제가 차단**된다 | `409 FILE_APPROVAL_REFERENCED`. 휴지통 이동은 진행 중 결재만 막지만, 영구삭제는 **모든** 참조를 막는다 — 되돌릴 수 없기 때문 |
| **FILE-033** | 파일 블록 담당이 **버전 단건 조회 인터페이스**를 제공한다 | 결재 블록은 `file_id` 가 아니라 **`file_version_id`** 를 고정한다. 결재 쪽은 그 값만 갖고 버전 하나를 열어야 한다 → `VER-013` |
| **FILE-034** | AI 분석이 참조하는 버전(`vitamate_analysis_document.file_version_id`)도 **영구삭제 차단 대상일 수 있다** | ⚠️ 현재 API 명세는 결재 참조만 차단한다. AI 참조까지 봐야 하는지 **확인 필요** (§8) |

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **저장소 업로드와 DB 커밋은 한 트랜잭션이 될 수 없다** | 저장소 성공 + DB 실패 → 고아 객체 / 반대 → 깨진 링크. 그래서 완료 통보 때 서버가 저장소를 **직접 확인**한다 (`FILE-013`) |
| **INV-02** | 파일은 **자체 상태**(`업로드중 / 완료 / 실패`)를 가진다 | 완료되지 않은 버전은 목록·다운로드·미리보기·버전 이력 **어디에도 나오지 않는다** |
| **INV-03** | 삭제는 **전면 soft delete** 다. 휴지통 이동은 **저장소를 유지**한다 | 복구 가능해야 한다. 삭제 시각만 채운다 (`docs/README.md` §3) |
| **INV-04** | **영구삭제만** 저장소 객체를 제거하고 **되돌릴 수 없다** | 확인 문자 검증을 통과해야만 도달한다 (`FILE-023~025`) |
| **INV-05** | 파일은 **프로젝트 소속**이다. **블록을 지워도 파일은 산다** | `block_file.block_id` 는 FK 없는 다형성 역참조다. 블록 삭제는 연결만 무효화한다 (`BLOCK.md` §4-4) |
| **INV-06** | 모든 파일 조회는 **`block.deleted_at IS NULL` 을 명시적으로 확인**한다 | soft delete 라 `CASCADE` 가 발동하지 않는다. FK 에 맡기면 삭제된 블록의 파일이 계속 조회된다 |
| **INV-07** | 버전은 **append-only** 다. 버전 삭제·되돌리기가 없다 | 이력이 곧 감사 기록이다 (`VER-007`) |
| **INV-08** | 업로더 정보는 **완료 시점 스냅샷**이다 | 부서 이동·퇴사 뒤에도 당시 값이 나와야 이력이 거짓이 되지 않는다 (`VER-006`) |
| **INV-09** | **파일 단위 권한이 없다.** 스텝 권한 3층 상속을 따른다 | `step_permission` → `project_member` 상속을 빼먹으면 프로젝트 권한자만 전부 차단된다 (`PERMISSION.md` §4-1) |
| **INV-10** | 결재가 고정한 버전은 **삭제로부터 보호**된다 | 진행 중 결재 대상은 휴지통 잠금, 참조된 버전은 영구삭제 차단. 지우면 결재 이력에서 문서를 못 연다 (`BLOCK.md` §8) |
| **INV-11** | 결재는 `file_id` 가 아니라 **`file_version_id` 로 버전을 고정**한다 | 새 버전이 올라와도 결재가 본 그 버전을 그대로 열 수 있어야 한다. 파일 블록이 버전 단건 조회를 제공한다 (`VER-013`) |
| **INV-12** | 미리보기는 **서버가 앞 5페이지를 잘라 직접 반환**한다 | presigned 를 주면 전체 PDF 에 접근돼 "5페이지 제한"이 무의미해진다 (`api/file.md` §10) |

## 4. 데이터 규칙 — 구현자가 밟는 함정

| # | 함정 | 처리 |
|---|------|------|
| 1 | **soft delete 라 `CASCADE` 가 안 걸린다** | 블록을 지워도 `block.deleted_at` 만 채워지고 물리 DELETE 가 없다 → `block_file` 행이 그대로 남는다. **조회마다 `block.deleted_at IS NULL` 을 직접 확인**한다 (INV-06) |
| 2 | `block_file` 은 **복합 PK `(block_id, file_id)`** · 다형성 역참조 | 상세 테이블이 `block_id` 를 갖고 `block` 은 파일을 가리키지 않는다 (`BLOCK.md` §1). 블록 삭제와 파일 생명주기가 독립이다 |
| 3 | **`업로드중` 고아 버전** | 완료 통보가 영영 안 오는 버전이 쌓인다. 정리 배치가 필요하다 (`FILE-012`, 주기 미확정) |
| 4 | `file_version` 이 **업로더 스냅샷 컬럼**을 가진다 | `uploaderName`·`uploaderDepartment`·`uploaderPosition`. `employee` 를 조인해 실시간 조회하면 안 된다 — 소속이 바뀌면 이력이 흔들린다 (INV-08) |
| 5 | **미리보기에 presigned 를 쓰면 안 된다** | 앞 5페이지 제한을 지키려면 서버가 잘라 바이너리로 반환해야 한다. 응답이 JSON 이 아니라 `application/pdf` 다 (INV-12) |
| 6 | **확장자는 화이트리스트가 아니라 블랙리스트** | 실행 파일만 차단한다. 업무 문서 종류를 미리 못 박으면 새 포맷마다 배포한다 (`FILE-008`) |
| 7 | **영구삭제는 저장소 일부 실패를 견딘다** | 사용자를 기다리게 하지 않으려 DB 는 먼저 지우고 실패 키를 정리 대상으로 남긴다 (`FILE-025`). `CASCADE` 는 하드삭제 배치용으로 스키마에 남겨둔다 |
| 8 | **결재·AI 가 `file_version` 을 테이블 공유**한다 | `approval_document.file_version_id`·`vitamate_analysis_document.file_version_id` 가 내 버전을 직접 가리킨다. 버킷 공유가 아니라 **테이블 공유**다 — 삭제 보호를 지우면 안 된다 |

### 4-1. 파일 · 버전이 가져야 할 값

| 테이블 | 항목 | 비고 |
|--------|------|------|
| `file` | `project_id`, 표시명(`name`), 삭제 시각(`deleted_at`) | **파일은 프로젝트 소속.** 표시명만 수정 대상 |
| `file_version` | `file_id`, `version_no`, 상태(`업로드중/완료/실패`) | 상태는 애그리거트 자체 필드 (INV-02) |
| `file_version` | 원본 파일명 · 확장자 · 크기 · MIME · `page_count` · 코멘트 | `page_count` 는 PDF 만, 실패 시 `null` |
| `file_version` | **업로더 스냅샷** — 이름 · 부서 · 직책 | 완료 시점 고정 (INV-08) |
| `file_version` | 완료 시각(`completed_at`) | 이력·정렬 기준 |
| `block_file` | 복합 PK `(block_id, file_id)` · `sort_order` · `linked_by` | 다형성 역참조 (함정 2) |
