**담당**: 김동현
**근거**: `../../../api/account.md` · `employee.md` · `department.md` · `job-position.md` · `employee-group.md` · `page-permission.md` · `../../global/PERMISSION.md` · `PAGE.md`

> 이 문서는 **구현자가 이것만 보고 만들 수 있게** 쓴 것이다.

> ⛔ API 경로·필드·상태코드·에러코드는 `../../../api/{도메인}.md` 소관이다. 여기서는 **무엇을 보장해야 하는가**를 정의한다.

> 🔖 **ID 규칙** — 각 영역 프리픽스(`ACC`·`EMP`·`DEPT`·`POS`·`GRP`·`PAGE`)와 번호는 **API 명세 사본이 쓰는 ID 를 그대로 이어받는다.**
> API 사본이 `요구사항 ACC-013~020` 처럼 이 번호를 직접 참조하므로 재번호를 매기지 않는다. 참조가 없는 번호는 표에 나타나지 않는다.

## 0. 한 줄 정의

**회사가 사람을 시스템에 들이고(계정·사원), 어디에 속하는지 정하고(부서·직급·그룹), 무엇을 볼 수 있는지 여는(페이지 권한) 관리 축 전체.**

인사는 단일 기능이 아니라 **6개 하위 영역의 묶음**이다. 이들은 `ADMIN`(시스템 계정)이 조작하고, **사람을 가리키는 모든 참조가 `employee.user_id`(사번) 하나로 모인다**는 점에서 한 도메인이다.

| 영역 | 프리픽스 | 무엇을 하나 |
|------|---------|-----------|
| 계정 | `ACC` | 인증 자격 발급·비밀번호 재설정·전역 role·계정 상태 |
| 사원 | `EMP` | 사람 등록·수정·퇴사·목록/상세·엑셀 일괄 등록 |
| 부서 | `DEPT` | 조직도(최대 2단) CRUD |
| 직급 | `POS` | 직급 CRUD·표시 순서 |
| 그룹 | `GRP` | 선택용 사람 묶음 CRUD·구성원 |
| 페이지권한 | `PAGE` | 고정 카탈로그에 대한 사람×페이지×등급 부여/회수 |

## 1. 범위

### 1-1. 만든다

| 영역 | 내용 |
|------|------|
| 계정 | 전역 role 변경(`MASTER`·`MEMBER`) · 계정 상태 토글 · 비밀번호 재설정(개인·다중 통합) |
| 사원 | 목록·상세 · 등록(계정 동반) · 수정 · 퇴사 · 엑셀 템플릿·검증·일괄 등록 |
| 부서 | 트리 조회(인원 2종) · 생성(최상위/하위) · 이름 수정 · 삭제 |
| 직급 | 목록 · 생성 · 수정(이름·순서) · 삭제 |
| 그룹 | 목록·구성원 조회(전체 사용자) · 생성·수정·삭제 · 구성원 추가/제거 |
| 페이지권한 | 내 페이지 목록 · 페이지 목록 · 접근 가능자 · 권한 부여/등급변경 · 회수 |

### 1-2. 안 한다 (명시)

| 항목 | 왜 |
|------|-----|
| **자가 회원가입** | 전부 관리자 프로비저닝이다. `ADMIN` 이 계정을 발급한다 |
| **`ADMIN` 부여·발급 화면/API** | `ADMIN` 은 개발자가 직접 발급하는 시스템 계정이다. role API 로 줄 수 없다 (`ACC-001`) |
| **비밀번호 "재발송" 전용 API** | 해시만 저장해 원문이 없다. 재발송 = 새 난수 = 재설정과 같다 (`ACC-019`) |
| **부서 이동(상위 변경)** | 이름 수정 모달에 상위 부서 필드가 없다. 필요하면 2단·순환 검사와 함께 별도 설계 (`DEPT` `ASK-03`) |
| **그룹·직급 기반 권한 판정** | 부서·직급·그룹은 권한 축이 아니다. 판정은 전부 인원별 직접 지정이다 |
| **엑셀 일괄 등록의 ADMIN 부여** | 템플릿에 권한 컬럼은 있으나 `ADMIN` 값은 거부한다 (`EMP-010`) |
| **페이지 자체의 생성·삭제** | 페이지는 개발자가 코드로 제공하는 고정 카탈로그다. DB 테이블이 없다 |
| **감사(행위자 사람 단위 특정)** | `ADMIN` 이 공용 계정이라 행위자를 사람으로 못 가른다. 시연 범위에선 감당 |

## 2. 요구사항

### 2-A. 계정 (`ACC`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **ACC-001** | 전역 role 부여 대상에서 `ADMIN` 을 제외한다. role API 가 받는 값은 `MASTER`·`MEMBER` 뿐 | `ADMIN` 을 보내면 `ACC_ADMIN_ROLE_NOT_ALLOWED` 400. `ADMIN` 은 개발자가 직접 발급한다 |
| **ACC-002** | 사원 등록 시 계정이 **항상 함께** 발급된다 | 사원만 만드는 경로가 없다. 등록 트랜잭션에서 `account` 가 1행 생성된다 |
| **ACC-003** | 로그인 아이디는 **사번(`user_id`)** 이다 | 별도 `login_id` 를 받지 않는다. 사번으로 로그인한다 |
| **ACC-004** | 계정 발급 시 초기 비밀번호를 **난수로 생성해 Argon2id 해시로만** 저장한다 | 평문은 DB·응답·화면 어디에도 없다 |
| **ACC-007** | 비밀번호 재설정은 **개인·다중이 같은 API** 다 | 1명이면 `userIds` 배열 길이 1 로 호출한다 |
| **ACC-009** | `ADMIN` 은 대상 사원의 전역 role 을 `MASTER`↔`MEMBER` 로 변경한다 | 자기 자신·시스템 계정은 대상 불가(`ACC_SELF_MODIFICATION_NOT_ALLOWED`·`ACC_SYSTEM_ACCOUNT_NOT_ALLOWED`) |
| **ACC-010** | 사원 등록 시 전역 role 을 지정한다(`MASTER`·`MEMBER`) | 기본값을 임의 부여하지 않고 요청의 `role` 을 쓴다. `ADMIN` 은 거부 |
| **ACC-011** | 계정 상태를 `ACTIVE`·`INACTIVE` 로 토글한다 | 사원 상세의 계정 상태 토글이 이 API 다 |
| **ACC-012** | 이미 같은 상태로의 변경은 거부한다 | `ACC_STATUS_UNCHANGED` 400. 시스템 계정은 대상 불가 |
| **ACC-013** | 재설정 대상은 `userIds` 배열로 받는다 | 화면에서 목록을 보고 선택하므로 다건이 기본이다 |
| **ACC-014** | 존재하지 않는 사번이 섞이면 **전체를 거부**한다 | `ACC_NOT_FOUND` 404. 부분 처리로 원인을 숨기지 않는다 |
| **ACC-015** | 이메일 미등록 대상은 **비밀번호를 바꾸지 않는다** | 전달 못 할 비번을 바꾸면 로그인 불가가 된다. `reason=EMAIL_NOT_REGISTERED`, `passwordChanged=false` |
| **ACC-016** | 각 실패 건에 `passwordChanged` 를 내려 재시도 판단을 준다 | 메일 발송 실패는 `passwordChanged=true`(다시 호출 필수), 미등록은 `false`(이메일 등록 후 재시도) |
| **ACC-017** | 처리 결과를 `requestedCount`·`successCount`·`failedCount` 로 집계한다 | 실패가 섞여도 **200**. 프론트가 집계를 보여준다 |
| **ACC-018** | 실패 건은 `failures[]`(사번·이름·사유)로 반환한다 | 메일 발송 단계만 부분 실패를 허용한다 |
| **ACC-019** | 화면의 `재발송` 버튼도 이 재설정 API 를 호출한다 | 재발송 시 새 난수가 발급된다. 이전 임시 비번은 복원되지 않는다 |
| **ACC-020** | 응답·화면에 비밀번호를 표시하지 않는다 | 해시만 저장하므로 원문을 되돌려줄 수 없다 |
| **ACC-021** | 이메일이 없어도 사원·계정은 등록된다 | `email` 미입력이 등록을 막지 않는다 |
| **ACC-022** | 이메일이 없으면 초기 비밀번호를 전달할 수 없어 **로그인하지 못한다** | `emailRegistered=false` 로 내려가 `⚠ 미등록` 배지가 뜬다 |
| **ACC-023** | `ADMIN` 계정은 재설정 대상이 될 수 없다 | 대상에 `ADMIN` 이 포함되면 `ACC_ADMIN_ACCOUNT_NOT_ALLOWED` 403 |
| **ACC-024** | `ADMIN` 계정은 이메일이 없다(시스템 계정) | 재발급은 개발자가 한다. 애플리케이션이 재설정하지 않는다 |
| **ACC-025** | 비밀번호 재설정은 **동기** 처리로 즉시 결과를 반환한다 | 큐잉·비동기 없이 응답 시점에 집계가 확정된다 |

> **왜 `passwordChanged` 가 핵심인가** — `false` 면 이메일을 등록한 뒤 다시 시도하면 되고, `true` 면 그 사원은 새 비밀번호를 모르는 상태라 **반드시 다시 호출**해야 한다. 이 한 필드가 운영자의 다음 행동을 가른다.

### 2-B. 사원 (`EMP`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **EMP-001** | 사원 목록을 검색·필터·페이징으로 조회한다 | `keyword`·`departmentId`·`role`·`status`·`resigned` 로 좁혀진다. 기본 20건 |
| **EMP-002** | 사원 상세를 조회한다 | 목록 필드 + 부서/직급 ID · 연락처 · 입사일 · 마지막 로그인 · 소속 그룹을 준다 |
| **EMP-003** | **시스템 계정(`is_system=1`)은 어떤 조회에도 나오지 않는다** | 목록·상세·멤버 선택·담당자 지정 어디서도 제외된다. 상세 직접 조회 시 `ACC_SYSTEM_ACCOUNT_NOT_ALLOWED` 403 |
| **EMP-004** | 사원 등록 시 계정을 함께 발급한다 | 사번·이름·부서·입사일·role 필수. 시스템은 초기 비번을 만들어 계정을 생성한다 |
| **EMP-005** | 엑셀로 사원을 일괄 등록한다 | 템플릿→검증→등록 3스텝으로 동작한다 |
| **EMP-006** | 파일을 열기 전 오류(없음·형식·5MB 초과)만 400 으로 막는다 | 그 외 행별 오류는 200 + `errors[]` 로 간다 |
| **EMP-007** | 파일 내 사번 중복을 검출한다 | `validation=USER_ID_DUPLICATED`, 어느 행과 겹치는지 메시지에 담는다 |
| **EMP-008** | 존재하지 않는 부서명을 검출한다 | `validation=DEPARTMENT_NOT_FOUND` |
| **EMP-009** | 필수 컬럼 누락을 검출한다 | `validation=REQUIRED_COLUMN`, 누락 컬럼명을 메시지에 담는다 |
| **EMP-010** | 엑셀로는 `ADMIN` 권한을 부여할 수 없다 | 권한 컬럼에 `ADMIN` 이면 `validation=ADMIN_ROLE_NOT_ALLOWED`. 컬럼 자체는 템플릿에 존재한다 |
| **EMP-011** | **부분 등록을 허용한다** | `skipErrors=true` 면 오류 행을 빼고 나머지를 등록한다. `false` 인데 오류가 있으면 `EMP_HAS_ERRORS` 400 |
| **EMP-012** | 일괄 등록 결과를 집계로 반환한다 | `totalRows`·`registeredCount`·`failedCount`·`emailSentCount` 를 준다 |
| **EMP-013** | 사원 정보를 부분 수정한다(전달한 필드만) | 사번은 바꿀 수 없다. 수정할 필드가 없으면 `EMP_INVALID_REQUEST` 400 |
| **EMP-014** | 부서 배정은 별도 API 가 아니다 — `departmentId` 로 소속을 바꾼다 | 수정 API 에 `departmentId` 를 보내면 소속이 변경된다 |
| **EMP-015** | 퇴사 처리는 **삭제가 아니다** — 퇴사일을 기록한다 | 사원 행은 남는다. 과거 프로젝트·파일 이력에 이름이 유지된다 |
| **EMP-016** | 퇴사 시 계정을 **자동으로 `INACTIVE`** 로 바꾼다 | 계정 상태 변경 API 를 따로 호출하지 않는다. 응답 `accountStatus=INACTIVE` |
| **EMP-017** | 이메일 미등록 사원에 `emailRegistered=false` 를 준다 | 로그인 불가 상태라 목록에 `⚠ 미등록` 배지가 뜬다 |
| **EMP-018** | 이메일 없이도 등록되며 초기 비번은 전달되지 않는다 | `ACC-021`·`ACC-022` 와 같은 규칙. 등록은 성공(201) |
| **EMP-019** | 일괄 등록에서 이메일 없는 행 수를 집계한다 | `emailNotRegisteredCount`·`emailNotRegistered[]` 로 후속 재설정을 유도한다 |

> **왜 계정 상태와 비밀번호 상태를 분리하나** — 화면이 계정 상태(토글)와 비밀번호 상태(배지)를 따로 보여준다. `accountStatus`(`ACTIVE`·`INACTIVE`)와 `passwordStatus`(`NORMAL`·`RESET_REQUIRED`)를 계산값 하나로 합치지 않는다.

### 2-C. 부서 (`DEPT`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **DEPT-001** | 부서를 계층 트리로 조회한다 | 페이징 없이 전체를 반환한다. `children` 안에 또 `children` 이 없다(최대 2단) |
| **DEPT-002** | 각 부서의 **직속 인원**과 **하위 포함 전체 인원**을 함께 제공한다 | `directEmployeeCount`(삭제 판정)·`totalEmployeeCount`(화면 표시). 시스템 계정·퇴사자는 제외 |
| **DEPT-003** | 최상위 부서를 생성한다 | `parentId` 생략 시 최상위로 생성된다 |
| **DEPT-004** | 상위를 지정해 하위 부서를 생성한다 | `parentId` 유무로 최상위/하위가 갈린다(같은 API) |
| **DEPT-005** | 계층을 **최대 2단**으로 제한한다 | 하위 부서를 `parentId` 로 지정하면 `DEPT_MAX_DEPTH_EXCEEDED` 409 |
| **DEPT-006** | 부서명은 **전체에서** 중복될 수 없다 | 최상위끼리도 중복 차단(`NULL` parent 도 유니크로 취급). `DEPT_NAME_DUPLICATED` 409 |
| **DEPT-007** | 부서명을 수정한다 | 소속 사원의 배정은 그대로다. 상위 부서는 바꾸지 않는다 |
| **DEPT-008** | 부서를 삭제한다 | 소프트 삭제가 아니라 행을 제거한다(권한 판정·이력 스냅샷에 안 쓰이므로) |
| **DEPT-009** | 직속 사원이 있으면 삭제를 차단한다 | `DEPT_HAS_EMPLOYEES` 409, 메시지에 인원 수 |
| **DEPT-010** | 하위 부서가 있으면 삭제를 차단한다 | `DEPT_HAS_CHILDREN` 409. CASCADE 로 하위를 함께 지우지 않는다 |
| **DEPT-011** | 부서를 **권한 판정에 사용하지 않는다** | 부서가 생기고 없어져도 권한이 흔들리지 않는다 |

### 2-D. 직급 (`POS`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **POS-001** | 직급 목록을 조회한다(`ADMIN`) | 페이징 없음. `sortOrder` 오름차순, 같으면 직급명 오름차순 |
| **POS-002** | 각 직급의 사용 인원을 제공한다 | `employeeCount`. 시스템 계정 제외 |
| **POS-003** | 직급을 생성한다 | `sortOrder` 생략 시 마지막 순서+1 |
| **POS-004** | 직급명은 중복될 수 없다 | DB UNIQUE. `POS_NAME_DUPLICATED` 409 |
| **POS-005** | 직급명을 수정한다 | 이름 수정과 순서 변경이 같은 API |
| **POS-006** | 표시 순서를 지정한다 | `sortOrder` 에 UNIQUE 를 걸지 않아 맞바꿀 때 값이 겹쳐도 오류가 아니다 |
| **POS-007** | 직급을 삭제한다 | 소프트 삭제가 아니라 행을 제거한다 |
| **POS-008** | 사용 인원이 있으면 삭제를 차단한다 | `POS_IN_USE` 409, 메시지에 인원 수. 먼저 사원 직급을 비우거나 바꿔야 한다 |
| **POS-009** | 직급을 **권한 판정에 사용하지 않는다** | 부서와 같은 원칙 |

### 2-E. 그룹 (`GRP`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **GRP-001** | 그룹 목록을 조회한다(**전체 사용자**) | 권한 부여·멤버 선택에서 쓰이므로 일반 사용자도 본다. 이름 오름차순 |
| **GRP-002** | 빈 그룹을 생성한다 | 생성 시 구성원을 함께 넣지 않는다. 그룹명 중복은 `GRP_NAME_DUPLICATED` 409 |
| **GRP-003** | 그룹 이름·설명을 수정한다 | 이름 변경이 기존 권한에 영향을 주지 않는다 |
| **GRP-004** | 그룹을 삭제한다 | **구성원이 있어도 삭제된다.** 구성원 매핑은 CASCADE 로 제거. 사용 중 차단이 없다 |
| **GRP-005** | 구성원을 다건 추가한다(멱등) | 이미 구성원인 사번은 오류가 아니라 조용히 건너뛰고 집계에만 반영한다 |
| **GRP-006** | 구성원을 **한 명씩** 제거한다 | 화면의 개별 `제거` 버튼에 대응. 이 그룹 구성원이 아니면 `GRP_MEMBER_NOT_FOUND` 404 |
| **GRP-007** | 한 사원이 여러 그룹에 속할 수 있다 | 그룹 간 배타 제약이 없다 |
| **GRP-008** | 구성원 목록을 조회한다(**전체 사용자**) | 시스템 계정·퇴사자는 제외된다. 이름 오름차순 |
| **GRP-009** | 구성원 목록에 **추가일(`created_at`)** 을 노출한다 | `addedAt` 컬럼. `employee_group_member` 는 `(group_id·user_id·created_at)` 3컬럼이다 |
| **GRP-010** | 그룹은 권한 축이 아니다 — 저장은 **개인 단위 스냅샷** | 구성원이 바뀌거나 그룹이 삭제돼도 이미 부여된 권한은 변하지 않는다 |

> **왜 그룹은 삭제를 차단하지 않나** — 그룹으로 권한을 주면 구성원 각자에게 개인 단위 행이 생기고 그룹 참조는 남지 않는다. 그룹이 사라져도 그 행들은 그대로다. 부서·직급과 달리 "사용 중"이라는 개념이 성립하지 않는다.

### 2-F. 페이지 권한 (`PAGE`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **PAGE-001** | 내 페이지 목록을 조회한다(사이드바 노출의 **유일한 근거**) | 응답에 있으면 프론트가 버튼을 그리고, 없으면 안 그린다. 판정 규칙은 서버 한 곳에만 있다 |
| **PAGE-002** | `permission` 은 `NONE`·`VIEWER`·`EDITOR` 3값이며 **노출과 접근은 다르다** | `NONE` 은 버튼은 보이되 접근 불가. 미부여 `MEMBER` 의 `BIDDING`·`FINANCE` 가 이 상태다 |
| **PAGE-003** | `ADMIN` 전용 페이지(`ADMIN_ONLY`)를 구분한다 | 해당하는 건 `TEMPLATE` 하나. `MASTER`·`MEMBER` 에게는 미반환 |
| **PAGE-004** | `ADMIN`·`MASTER` 는 **부여 기록 없이도** 열람된다(`GLOBAL_ROLE`) | 이 열람은 회수 불가. role 게이트로 열리는 페이지는 항상 `EDITOR` |
| **PAGE-005** | 페이지 목록·접근 가능자 목록을 조회한다(`ADMIN`) | 페이지 목록의 부여 대상은 `BIDDING`·`FINANCE` **2개뿐**이다. role 로 여는 4개는 목록에 없다 |
| **PAGE-006** | 접근 가능자는 **부여 + 전역 권한 UNION** 으로 뽑는다 | `page_permission` 만 조회하면 "3명 줬는데 왜 5명이 보나"가 된다. `MASTER` 는 `revocable=false` |
| **PAGE-007** | 권한을 부여한다 — **전체 교체가 아닌 부분 반영**(`POST`) | 요청 목록에 없는 사용자의 권한은 건드리지 않는다. `grantedCount`·`updatedCount`·`unchangedCount` 집계 |
| **PAGE-008** | 부여와 등급 변경이 같은 API 다 | 이미 권한이 있으면 등급을 갱신한다 |
| **PAGE-009** | 권한을 회수한다 | `MASTER` 를 회수해도 전역 권한으로 열람은 유지된다(`stillAccessible=true`). 부여 기록이 없으면 `PAGE_PERMISSION_NOT_FOUND` 404 |
| **PAGE-010** | 그룹으로 부여해도 **개인 단위로 저장**한다 | 프론트가 구성원 목록을 같은 등급 배열로 펼쳐 보낸다. 이후 그룹 변경이 이 권한을 바꾸지 않는다 |

> **카탈로그(6) ≠ 부여 대상(2)** — 카탈로그는 `BIDDING`·`FINANCE`·`PROJECT_CREATE`·`MY_PROJECT`·`TEMPLATE`·`SETTINGS` 6개다. 이 중 `page_permission` 행이 생기는 것은 `BIDDING`·`FINANCE` 뿐이고, 나머지 4개는 role 로 열려 행이 아예 생기지 않는다. DB 컬럼은 `ENUM('BIDDING','FINANCE')` 다.

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **사람을 가리키는 모든 FK 는 `employee.user_id`(사번)** 다. `account_id` 는 계정 관리 밖으로 나가지 않는다 | 계정은 사라질 수 있고 사람은 남는다. 도메인이 인증에 결합되면 안 된다 |
| **INV-02** | **로그인 아이디 = 사번.** 별도 `login_id` 컬럼을 만들지 않는다 | 식별자가 2개가 되면 혼란만 커진다. `account.user_id` 는 `NOT NULL UNIQUE` |
| **INV-03** | 사람을 고르는 모든 조회에 **`is_system = 0` 을 기본 조건**으로 넣는다 | 빠뜨리면 `ADMIN`·배치·크롤러가 사원 목록·프로젝트 멤버·그룹·담당자 지정에 섞인다 |
| **INV-04** | **`ADMIN` 은 공용 시스템 계정이다.** 실제 사원에게 부여하지 않고 겸직하지 않는다 | 인사 담당자가 관리 업무를 하려면 자기 계정과 별도로 `ADMIN` 으로 다시 로그인한다 |
| **INV-05** | `ADMIN` 은 role 변경 API 로 **부여할 수 없다.** 개발자가 직접 발급한다 | 실제 사원이 `ADMIN` 을 갖는 상태를 만들지 않는다 |
| **INV-06** | 계정과 사원 테이블은 **1:1 이되 합치지 않는다** | 비밀 정보 분리 · 갱신 빈도 상이(`last_login_at`) · 사원 없는 계정(`ADMIN`) 존재 · 애그리거트 경계 |
| **INV-07** | 계정 발급 시 초기 비밀번호 메일을 보내되 **실패해도 등록은 성공**한다 | 사원·계정은 이미 만들어졌다. 비번만 다시 보내면 된다(`emailSent=false` 안내) |
| **INV-08** | 전역 role 은 서열형 `ADMIN`>`MASTER`>`MEMBER` 이나, 실무 화면 판정은 **허용 role 집합**이다 | `ADMIN` 은 "내 것이 생기는 화면"(`프로젝트 생성`·`내 프로젝트`)에서 제외된다. 시스템 계정이라 `project_member` 에 못 들어간다 |
| **INV-09** | `page_permission` DB 값은 **`BIDDING`·`FINANCE` 2개뿐**이다. 카탈로그 6 ≠ 부여 대상 2 | 나머지 4개는 role 로 열려 행이 생기지 않는다 |
| **INV-10** | `page_permission.permission` 에 **`NONE` 값을 저장하지 않는다.** 행 없음이 곧 차단이다 | `NONE` 은 응답 계산값일 뿐이다. 스텝 권한(③층)의 `NONE` 과 역할이 완전히 다르다 |
| **INV-11** | `MASTER` 는 행이 없어도 `BIDDING`·`FINANCE` 를 열람한다. 접근 가능자 목록은 **UNION** 으로 뽑는다 | 부여 기록만 조회하면 접근자를 틀리게 센다(`PAGE-006`) |
| **INV-12** | 부서·직급·그룹은 **권한 판정에 쓰지 않는다.** `page_permission`·`step_permission` 에 `group_id` 를 넣지 않는다 | 권한은 전부 인원별 직접 지정. 그룹은 선택 UI 편의일 뿐 저장 대상이 아니다 |
| **INV-13** | `employee_group_member` 는 **`created_at`(추가일)** 을 포함한다 | 구성원 목록 화면이 추가일을 노출한다. `(group_id·user_id·created_at)` 3컬럼 |
| **INV-14** | 부서 계층은 **최대 2단**, 삭제 시 **직속 사원 또는 하위 부서가 있으면 차단**한다 | CASCADE 로 두면 팀 하나 지우려다 본부 전체가 사라진다 |
| **INV-15** | 직급은 **사용 인원이 있으면 삭제를 차단**한다 | 사원 직급을 먼저 비우거나 바꿔야 한다 |
| **INV-16** | `ADMIN` 은 **자기 계정의 role 행을 수정할 수 없다** | 애플리케이션이 자기 role 수정 경로를 막는다 |
| **INV-17** | 엑셀 일괄 등록은 **부분 등록을 허용**한다 | `오류 제외하고 등록 (N건)` 버튼에 대응. 재업로드 중복 문제는 부분 등록으로 해소된다 |

| 1 | **그룹 관리 주체가 미확정** — `ADMIN` 전용으로 가정했다. `MASTER` 도 허용할지 | `GRP` 생성·수정·삭제·구성원 변경의 권한 게이트 |
