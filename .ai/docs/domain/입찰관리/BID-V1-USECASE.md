## A. 수집

### UC-B01. 수집 조건 등록

| | |
|---|---|
| **행위자** | 입찰 담당자 (`BIDDING`) |
| **화면** | P-14 수집 조건 관리 |
| **선행조건** | `crawl_source` 에 지원 소스가 시드돼 있다 |
| **요구사항** | SRC-01~05 |

**기본 흐름**

1. `수집 조건 추가` 클릭
2. **소스를 드롭다운에서 고른다** — `나라장터-용역` · `한국원가관리협회` · `직접등록`
3. 조건 이름을 입력한다 (`원가계산 용역` 등)
4. 저장 → 목록에 `enabled=on` 으로 추가된다
5. 목록에서 **마지막 수집 시각 · 수집 건수**를 확인한다

> **↔ 원본과 다름** — 원본 `UC-01` 은 "크롤링 링크 등록"이었다.
> **임의 URL 입력칸이 없다.** 사이트마다 파서가 따로라 코드가 지원하는 소스만 고를 수 있다.
> `DOMAIN §3-1` 이 블록 타입을 닫은 논리와 같다 — *"확장 가능은 환상이다. 결국 매번 배포한다."*

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| `BIDDING` 아닌 사용자 | 403. 화면 진입 불가 |
| 조건을 끔(`enabled=off`) | 다음 스케줄에서 제외. 기존 수집분은 그대로 |
| 업무구분이 다름(용역/공사) | **조건을 따로 등록한다.** 소스가 곧 오퍼레이션이다 |

### UC-B02. 자동 수집 — 일 1회 ⭐ 이 영역의 심장

| | |
|---|---|
| **행위자** | 수집 잡 (시스템) |
| **화면** | 없음 (백그라운드) |
| **선행조건** | `enabled` 인 수집 조건이 1개 이상 |
| **요구사항** | CRW-01~07 · INV-01·02·04 |

**기본 흐름**

```
1. 스케줄 트리거 (일 1회)
2. enabled 인 수집 조건을 전부 조회
3. 조건마다 반복 ─┐
   4. 소스 타입으로 분기
        OPENAPI → 마지막 성공 시각 ~ 현재 로 기간 조회
                  totalCount 를 다 받을 때까지 페이지 순회
        HTML    → 목록 페이지 파싱 (인코딩 명시 · 프레임 내부 URL)
                  번호 없는 고정공지 행은 스킵
   5. 응답을 공고 표준 형태로 정규화
        · 금액 '-'          → 없음
        · 하한율 '공고문참조' → 문자열 그대로
        · 날짜 '0000-00-00' → 없음
   6. 자연키(출처 + 외부식별자 + 차수)로 UPSERT
        신규 → 삽입. 상태는 소스에 따라 결정 (UC-B03 표)
        기존 → 갱신
   7. 이 공고로 만든 프로젝트가 있나?
        없음 → 다음 건
        있음 → 프로젝트 스냅샷과 비교 → UC-B08 로
   8. 조건별 수집 건수 · 실행 시각 기록
   └─ 다음 조건
9. 종료
```

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 조건 A 호출 실패 | **조건 B 는 계속 실행한다.** 실패는 로그에 남기고 마지막 성공 시각은 갱신하지 않는다 |
| 페이지 순회 중 끊김 | 그 조건을 실패 처리. 다음 실행에서 같은 기간을 다시 조회한다 |
| 같은 공고가 또 들어옴 | **UPSERT 로 갱신.** 행이 늘지 않는다 |
| 파싱 실패 건 | 그 건만 건너뛰고 로그. 잡 전체를 죽이지 않는다 |

> ⚠️ **수집 잡은 AI 요약을 호출하지 않는다.** 요약은 사람이 누를 때만 (UC-B05).
> v1 은 전량 수집이라 자동이면 하루 수백 건이 LLM 을 탄다.

### UC-B03. 신규 공고 확인

| | |
|---|---|
| **행위자** | 입찰 담당자 |
| **화면** | P-10 공고 목록 |
| **요구사항** | LST-01~09 · INV-06 |

**기본 흐름**

1. 공고 탭 진입 → 목록이 **공고일 역순**으로 뜬다
2. **마지막 수집 배치 이후 들어온 건에 `NEW` 배지**가 붙어 자연히 위에 모인다
3. 각 행에서 확인한다 — 공고명 · 기관 · **출처** · 투찰마감 `D-n` · 기초금액 · 추정가격
4. 값이 없는 칸은 `-` 로 보인다 (조합 공고는 금액이 원래 없다)
5. 관심 건을 클릭 → UC-B04

**수집 시 상태**

| 출처 | 들어올 때 상태 | 왜 |
|------|--------------|-----|
| 나라장터 | **`REGISTERED`** (대장 등재) | 필드가 이미 다 차 있다 |
| KCAA(HTML) | **`COLLECTED`** | 제목·작성일뿐. 금액·마감일이 첨부 공고문 안에 있다 |
| 직접등록 | **`REGISTERED`** | 사람이 채워 넣은 것 |

> **↔ 원본과 다름** — 원본 `UC-01` 의 *"자동 스크리닝 — 참여 불가 건을 흐리게"* 는 **v1 에 없다.**
> 조건 조회로 가져오면 안 맞는 건이 애초에 안 들어온다. 회사 등록 업종·지역 테이블도 만들지 않는다.
>
> **↔ 원본과 다름** — *"신규 건 배지"* 를 **글로벌 알림이 아니라 목록 행 라벨**로 구현한다.
> 전량 수집이면 하루 수백 건이고, `DOMAIN §9` 가 스스로 경고했다 — *"알림을 끄면 결재 상신도 못 본다."*

### UC-B04. 공고 상세 확인 · 원문 대조

|---|---|

| 원문 사이트가 죽음 | 링크만 실패. 저장된 값은 그대로 보인다 |

### UC-B05. AI 요약 — 요청 → 검토 → 확정

| | |
|---|---|
| **행위자** | 입찰 담당자 → 파이썬 서버 → 입찰 담당자 |
| **화면** | P-11 상세 안의 요약 패널 |
| **요구사항** | SUM-01~05 · INV-07 |

**기본 흐름**

1. 상세에서 **`AI 요약 생성`** 을 누른다 ← **사람이 누를 때만 실행된다**
2. 시스템이 파이썬 서버에 공고 내용을 보낸다
3. **금액 / 일정 / 과업 성격 / 리스크** 4항목이 돌아온다
4. 패널에 `검토 필요` 상태로 표시된다
5. 담당자가 읽고 **수정**한다
6. `확정` → 확정 상태로 바뀐다

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 파이썬 서버 응답 없음 | **요약만 실패.** 공고 목록·상세는 정상 동작한다 |
| 확정하지 않은 요약 | 프로젝트 전환에 쓰지 않는다 |
| 다시 생성 | 새 요약이 미확정 상태로 추가된다 |

> **↔ 원본과 다름** — 원본 `UC-03` 은 입력에 *"회사 컨텍스트(수행 실적 · 등록 업종 · 유사 과업)"* 를 넣었다.
> **그 데이터가 스키마에 없다.** v1 은 공고 내용만 보낸다.

### UC-B06. 공고 제외 — 사유 필수

| | |
|---|---|
| **행위자** | 입찰 담당자 |
| **화면** | P-10 목록 또는 P-11 상세 |
| **요구사항** | STS-04·05 |

**기본 흐름**

1. 볼 필요 없는 건에서 `제외` 를 누른다
2. **사유를 입력한다** — 사유 없이는 진행되지 않는다
3. 상태가 `제외됨` 이 되고 기본 목록에서 빠진다
4. **삭제되지 않는다.** 필터로 다시 볼 수 있다

**왜 사유가 필수인가**

`PRODUCT §6` 이 종결 사유를 필수로 만든 이유와 같다 — *"미참여·유찰 이유가 안 쌓여 판단 기준이 개선되지 않았다."*
v2 에서 수집 조건을 좁히려면 **왜 안 봤는지가 데이터로 쌓여야** 한다. 그게 없으면 v2 도 감으로 정하게 된다.

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 제외한 공고가 재수집됨 | **상태는 유지된다.** 다시 `COLLECTED` 로 돌아가지 않는다 |
| 제외를 되돌림 | 이전 상태로 복귀. 사유는 이력으로 남는다 |

## C. 넘기기

### UC-B07. 프로젝트 전환

| | |
|---|---|
| **행위자** | 입찰 담당자 |
| **화면** | P-11 상세 → 프로젝트 페이지 |
| **선행조건** | 아직 전환되지 않은 공고 |
| **요구사항** | CNV-01~07 · BLK-* · INV-01 · INV-08~10 |

**기본 흐름**

1. 상세에서 **`프로젝트 시작`** 을 누른다
2. 시스템이 프로젝트를 생성한다
   - 공고 값을 **스냅샷으로 복사** — 이름 · 기초금액 · 추정가격 · 투찰마감 · 개찰일
   - 원본 공고 참조를 유지한다
   - 상태 `진행 전`
3. 전환 요청자를 `project_member` 에 등록한다
4. 입찰 스테이지와 입찰 스텝을 자동 생성한다
5. 입찰 스텝 안에 입찰 공고 블록을 자동 생성한다
6. **프로젝트 페이지로 이동한다**
7. 이후는 실무자 영역 (`UC-02` 조건 등재부터)

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 이미 전환된 공고 | **거부.** 프로젝트가 2개 생기지 않는다. 목록에서 기존 프로젝트로 이동 |
| 공고가 없음 | 404 |

> **↔ 원본과 다름** — 원본 `UC-01` 은 *"템플릿 선택 또는 빈 프로젝트"* 였다.
> **v1 은 템플릿 선택 없이 정해진 입찰 진입 구조를 만든다.** 프로젝트, 입찰 스테이지, 입찰 스텝, 입찰 공고 블록까지 자동 생성하고 버튼 하나로 끝난다.
>
> ⚠️ **스냅샷인 이유** — 이 복사본은 이후 재수집이 **절대 덮지 않는다** (UC-B08).
> 기초금액 3억을 보고 참여 결재를 올렸는데 정정공고로 2억이 되고 그게 조용히 덮이면, **그 결재 기록은 거짓이 된다.**

### UC-B08. 정정공고 감지 → `원본 변경됨` ⚠️

| | |
|---|---|
| **행위자** | 수집 잡 → 실무자 |
| **화면** | 없음 → 프로젝트 화면에 배지 |
| **선행조건** | 이미 프로젝트로 전환된 공고 |
| **요구사항** | INV-01·02 |

**기본 흐름**

1. 수집 잡이 그 공고를 다시 받는다 (정정공고 또는 값 변경)
2. **공고 레코드는 최신 값으로 갱신**된다
3. 이 공고로 만든 프로젝트가 있는지 확인한다
4. 있으면 **프로젝트 스냅샷과 비교**한다 — 기초금액 · 추정가격 · 투찰마감
5. 다르면 **프로젝트에 `원본 변경됨` 배지**를 세운다
6. **프로젝트 값은 건드리지 않는다**
7. 실무자가 배지를 보고 `그때 값 vs 지금 값` 을 나란히 확인한다
8. 반영 여부를 **사람이 결정**한다. 반영하면 로그가 남는다

```
프로젝트 스냅샷 (그때)     공고 레코드 (지금)
기초금액  300,000,000   →   200,000,000   ⚠️ 변경됨
투찰마감  2026-08-20    →   2026-08-20
```

> **↔ 원본과 다름** — `DOMAIN §1-1` 문면은 *"프로젝트가 된 건은 **자동 재크롤링 안 함.** 수동 버튼"* 이다.
> **그러면 배지를 자동으로 세울 수 없다.** 아무도 버튼을 안 누르면 정정공고를 영원히 모른다.
> `PRODUCT §3-2` 원칙 1 — *"사람이 안 하면 깨지는 규칙을 만들지 마라"* 에 정면으로 걸린다.
>
> **v1 해석: 수집은 하되 프로젝트 값을 안 덮는다.** §1-1 이 진짜 금지한 건 *"프로젝트 값을 절대 덮지 않는다"* 이지 "데이터를 보지 마라"가 아니다.
> ⚠️ **이 해석은 팀 합의가 필요하다.**

### UC-B09. 수동 등록

|---|---|

1. `직접 등록` 클릭 → 대장 항목 폼이 뜬다
2. 공고명 · 기관 · 마감일 · 금액 등을 입력한다
3. 저장 → 출처 `직접등록`, 상태 `대장 등재` 로 목록에 합류한다
4. 이후 전환·제외는 수집 건과 **동일하게** 동작한다

> 나라장터에 없는 공고(민간 재개발조합 등)를 대장에 넣는 통로다.
> 실제 대장 5건 중 조합 발주가 2건이었다 — **API 만으로는 절반도 못 채운다.**

### UC-B11. 입찰 블록 조회

| | |
|---|---|
| **행위자** | 프로젝트 실무자 |
| **화면** | 프로젝트 상세 안 입찰 공고 블록 |
| **선행조건** | 공고에서 전환된 프로젝트이고 입찰 공고 블록이 생성됨 |
| **요구사항** | BLK-01~03 · INV-08 |

**기본 흐름**

1. 프로젝트 상세에 진입한다
2. 입찰 스텝의 입찰 공고 블록을 연다
3. 시스템은 연결된 공고 원본과 프로젝트 스냅샷을 함께 조회한다
4. 화면에는 공고명, 금액, 일정, 참여 요건, 원문 링크, 현재 공고 변경 여부가 보인다
5. 사용자는 공고 원본을 수정하지 않고 프로젝트 판단 자료로만 활용한다

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 연결된 공고가 없음 | 데이터 정합성 오류. 블록은 500 이 아니라 관리자가 확인할 수 있는 오류로 응답한다 |
| 공고값이 프로젝트 스냅샷과 다름 | 변경 배지와 비교 진입점을 보여준다 |

### UC-B12. 프로젝트 스냅샷 비교 · 선택 반영

| | |
|---|---|
| **행위자** | 프로젝트 실무자 |
| **화면** | 입찰 공고 블록의 변경 비교 화면 |
| **선행조건** | 재수집으로 공고 원본과 프로젝트 스냅샷 값이 달라짐 |
| **요구사항** | INV-02 · INV-09 · BLK-03 |

**기본 흐름**

1. 사용자가 입찰 공고 블록에서 `원본 변경됨` 배지를 확인한다
2. 비교 화면에서 `그때 값(프로젝트 스냅샷)` 과 `현재 값(공고 원본)` 을 나란히 본다
3. 반영할 항목을 사람이 선택한다
4. 시스템은 선택된 항목만 프로젝트 스냅샷에 반영하고 반영 이력을 남긴다
5. 반영 후에도 공고 원본은 그대로 유지된다

**분기 · 예외**

| 상황 | 결과 |
|------|------|
| 사용자가 반영하지 않음 | 프로젝트 스냅샷은 유지된다 |
| 변경 항목이 사라짐 | 배지를 내리고 비교 화면은 빈 상태로 보인다 |
