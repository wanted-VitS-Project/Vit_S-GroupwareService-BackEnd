# 📌 공고 · 입찰 v1 — 요구사항 명세

**최종 업데이트**: 2026-08-03 (노션 정리본 반영 — 입찰 블록 자동 생성 · 스냅샷 정책 보강)
**담당**: 김동현
**근거**: [`USECASE.md`](../../global/USECASE.md) UC-01~03 · [`BLOCK.md`](../../global/BLOCK.md) · 결정 근거는 [`../../api/bid.md`](../../api/bid.md) §0

> 이 문서는 **구현자가 이것만 보고 만들 수 있게** 쓴 것이다.
> 모든 요구사항에 **수용 기준**이 붙어 있다. 기준을 통과하면 그 항목은 끝난 것이다.
> ⛔ API 형태는 [`../../api/bid.md`](../../api/bid.md) 소관. 그쪽은 아직 `📝 초안` 이라 **구현 금지**다.

## 0. 한 줄 정의

**여러 출처의 입찰 공고를 매일 자동으로 모아 한 목록에 보여주고, 쓸 만한 건은 프로젝트로 넘긴다.**

v1 의 목표는 **거르는 게 아니라 가져오는 것**이다. 무엇을 거를지는 데이터를 쌓아본 뒤 v2 에서 정한다.

## 1. 범위

### 1-1. 만든다

| 영역 | 내용 |
|------|------|
| 수집 | 나라장터 OpenAPI(용역) 일 1회 · KCAA HTML 파서 1개 · 수동 등록 |
| 조회 | 공고 목록(`NEW` 배지 · 출처 · D-n) · 상세 · 원문 링크 |
| 상태 | `COLLECTED → REGISTERED / DISMISSED` |
| AI | 요약 생성(수동 트리거, 파이썬 서버) → 사람이 검토·확정 |
| 전환 | 공고 → 프로젝트 생성 (스냅샷 복사) + 입찰 스테이지·스텝·블록 자동 생성 |
| 관리 | 수집 소스 조회 · 수집 조건 CRUD · 수동 수집 실행 |

### 1-2. 안 한다 (명시)

| 항목 | 왜 |
|------|-----|
| **자동 스크리닝 (참여 불가 건 흐리게)** | OpenAPI 조건 조회면 애초에 안 들어온다. 회사 프로필 테이블도 만들지 않는다 |
| **수집 조건으로 좁히기** | v1 은 전량 수집. `crawl_link.params` 컬럼만 만들고 실사용은 v2 |
| **개인별 읽음 상태** | `crawled_at` 기준 `NEW` 만 |
| **HTML 소스의 대장 등재** | KCAA 건은 `COLLECTED` 고정. 필드 수동 입력 화면은 v2 |
| **첨부 공고문 자동 필드 추출** | HWP/PDF 파싱. 파이썬 서버 v2 일감 |
| **글로벌 알림(`notification`) 연동** | 목록 `NEW` 배지로만. 이유는 §3 INV-06 |
| **프로젝트 내부 화면 전체 설계** | 프로젝트 도메인 영역이다. 단, 전환 시 입찰 공고 블록을 생성하고 조회하는 계약은 입찰관리에서 정의한다 |

## 2. 요구사항

### 2-A. 수집 (`CRW`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **CRW-01** | 등록된 수집 조건을 **일 1회** 자동 실행한다 | 스케줄러가 하루 1회 트리거된다. 실행 시각·소스·수집 건수가 로그에 남는다 |
| **CRW-02** | 나라장터는 **조회 기간 증분**으로 가져온다 (`inqryBgnDt`~`inqryEndDt`) | 마지막 성공 실행 시각 이후 범위만 조회한다. 첫 실행은 N일 전부터 |
| **CRW-03** | 응답이 여러 페이지면 **끝까지 순회**한다 | `totalCount` 를 다 받을 때까지 `pageNo` 를 증가시킨다. 중간에 끊기면 실패로 기록 |
| **CRW-04** | 같은 공고를 다시 받으면 **INSERT 하지 않고 UPDATE** 한다 | **잡을 연속 2회 실행해도 `bid_notice` 행 수가 늘지 않는다** |
| **CRW-05** | 자연키는 `(source_code, external_id, notice_ord)` 다 | DB UNIQUE 제약으로 강제한다. 앱 로직에만 의존하지 않는다 |
| **CRW-06** | 수집 실패가 다른 조건의 수집을 막지 않는다 | 조건 A 가 실패해도 조건 B 는 계속 실행된다. 실패는 로그에 남는다 |
| **CRW-07** | KCAA HTML 파서 — 목록에서 `제목 · 작성일 · 상세링크 · 첨부유무 · idx` 를 뽑는다 | 목록 1페이지에서 일반글 15건이 파싱된다 |
| **CRW-08** | 수동 수집 실행 버튼 | 호출 즉시 해당 조건 1건만 수집한다. 스케줄과 무관하게 동작 |

### 2-B. 목록 · 상세 (`LST`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **LST-01** | 목록은 **`announced_at` 역순** 고정 | 최신 공고가 맨 위 |
| **LST-02** | **마지막 수집 배치 이후 유입된 건에 `NEW` 배지** | 잡 실행 직후 새로 들어온 건만 `isNew=true`. 다음 배치가 돌면 해제 |
| **LST-03** | 목록에 **출처명**을 표시한다 | `[나라장터] · [KCAA] · [직접등록]` 이 각 행에 보인다 |
| **LST-04** | 목록·상세에서 **원문으로 이동**할 수 있다 | `sourceUrl` 클릭 시 원 사이트 해당 공고가 열린다 |
| **LST-05** | 투찰마감까지 **남은 일수(D-n)** 를 계산해 내려준다 | 마감이 없으면 `null`. 지난 건은 음수 또는 `마감` 표시 |
| **LST-06** | 값이 없는 필드는 **`null`** 로 내려준다 | 금액 `-`, 하한율 `공고문참조` 같은 원문은 §4 규칙대로 처리 |
| **LST-07** | 필터 — 상태 · 출처 · 공고명 검색 | 기본 조회에서 `DISMISSED` 는 제외된다 |
| **LST-08** | 페이징 | 기본 20건 |
| **LST-09** | 이미 전환된 공고는 **`projectId` 를 함께** 내려준다 | 목록에서 전환 여부가 구분된다 |

### 2-C. 상태 (`STS`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **STS-01** | 상태는 **3단** — `COLLECTED` · `REGISTERED` · `DISMISSED` | 수집 시 기본 `COLLECTED` |
| **STS-02** | **나라장터 수집 건은 `REGISTERED` 로 들어온다** | 필드가 이미 다 차 있으므로 검토 단계가 필요 없다 |
| **STS-03** | **HTML(KCAA) 수집 건은 `COLLECTED` 고정** | v1 에서 `REGISTERED` 로 승격하지 않는다 |
| **STS-04** | `DISMISSED` 로 바꿀 때 **사유를 받는다** | 사유 없이 제외 처리하면 거부한다 |
| **STS-05** | `DISMISSED` 건은 기본 목록에서 빠지되 **삭제하지 않는다** | 필터로 다시 볼 수 있다 |

> **왜 사유를 필수로 받나** — `PRODUCT §6` 이 종결 사유를 필수로 만든 이유와 같다.
> *"미참여·유찰 이유가 안 쌓여 판단 기준이 개선되지 않았다."* 수집 조건을 v2 에서 좁히려면 **왜 안 봤는지가 쌓여야** 한다.

### 2-D. AI 요약 (`SUM`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **SUM-01** | 요약은 **수동 트리거만** | 수집 잡이 요약을 자동 호출하지 않는다 |
| **SUM-02** | 파이썬 서버에 요청해 **금액 / 일정 / 과업 성격 / 리스크** 를 받는다 | 4개 항목이 응답에 있다 |
| **SUM-03** | 생성 직후는 **미확정**(`confirmed=0`) | 화면에 `검토 필요` 표시 |
| **SUM-04** | 사람이 수정·확정하면 `confirmed=1` | 확정 전 요약은 프로젝트 전환에 쓰지 않는다 |
| **SUM-05** | 파이썬 서버가 죽어도 **공고 조회는 정상 동작**한다 | 요약 실패가 목록·상세를 막지 않는다 |

> ⛔ **자동 실행 금지 이유** — v1 은 전량 수집이라 하루 수백 건이다. 자동이면 LLM 비용이 그대로 터진다.

### 2-E. 프로젝트 전환 (`CNV`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **CNV-01** | 전환 시 `project` 를 생성하고 **`projectId` 를 반환**한다 | 프론트가 이 값으로 프로젝트 페이지로 이동한다 |
| **CNV-02** | 공고 값을 **스냅샷으로 복사**한다 | 이름 · `bid_notice_id` · 기초금액 · 추정가격 · 투찰마감 · 개찰일 |
| **CNV-03** | 생성 상태는 `NOT_STARTED` | |
| **CNV-04** | **이미 전환된 공고는 거부**한다 | 두 번 호출하면 409. 프로젝트가 2개 생기지 않는다 |
| **CNV-05** | 전환 직후 **입찰 스테이지와 입찰 스텝을 자동 생성**한다 | 프로젝트 첫 화면에 공고 정보를 볼 수 있는 위치가 생긴다 |
| **CNV-06** | 입찰 스텝 안에 **입찰 공고 블록을 자동 생성**한다 | `bid_notice_block` 이 `block_id` 와 `bid_notice_id` 를 연결한다 |
| **CNV-07** | 템플릿은 **쓰지 않는다** | ERD 에 템플릿 저장소가 없고, v1 은 정해진 입찰 진입 구조만 만든다 |

### 2-F. 소스 · 수집 조건 (`SRC`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **SRC-01** | 수집 소스는 **코드가 지원하는 목록에서만 고른다** | 화면에 드롭다운. **임의 URL 입력칸이 없다** |
| **SRC-02** | 수집 조건 CRUD (`BIDDING` 만) | 다른 role 은 403 |
| **SRC-03** | 조건 하나는 **소스 하나**에 붙는다 | 업무구분(용역/공사/물품)이 다르면 조건도 따로 등록 |
| **SRC-04** | 조건을 껐다 켤 수 있다 (`enabled`) | 꺼진 조건은 스케줄에서 제외 |
| **SRC-05** | 조건 목록에서 **마지막 수집 시각과 건수**가 보인다 | 담당자가 조건을 스스로 조율할 근거 |

### 2-G. 참여 요건 (`REQ`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **REQ-01** | 참가 자격, 지역 제한, 업종 제한, 공동수급 가능 여부를 공고에 보존한다 | 수집·수동 등록·상세 조회 응답에서 같은 필드가 유지된다 |
| **REQ-02** | 금액·하한율처럼 파싱이 애매한 값은 원문 문자열을 보존한다 | `공고문참조`, `-2% ~ 2%` 같은 값이 숫자 변환 실패로 사라지지 않는다 |
| **REQ-03** | AI 요약은 참여 요건을 참고할 수 있지만 확정값을 자동으로 덮지 않는다 | 사람이 확인·확정한 값만 전환 판단에 사용한다 |

### 2-H. 입찰 공고 블록 (`BLK`)

| ID | 요구사항 | 수용 기준 |
|----|---------|----------|
| **BLK-01** | 전환된 프로젝트에는 입찰 공고를 보여주는 전용 블록이 생긴다 | 프로젝트 화면에서 공고명, 금액, 마감, 참여 요건을 확인할 수 있다 |
| **BLK-02** | 블록은 공고 원본을 수정하지 않고 조회한다 | 블록 수정 API 로 `bid_notice` 자체가 바뀌지 않는다 |
| **BLK-03** | 프로젝트 스냅샷과 현재 공고값이 다르면 변경 여부를 보여준다 | 재수집 후 변경된 값이 있으면 비교 화면을 열 수 있다 |

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **재수집이 `project` 값을 절대 덮지 않는다** | 기초금액 3억 보고 결재 올렸는데 2억으로 조용히 바뀌면 **그 결재 기록이 거짓이 된다** (`DOMAIN §1-1`) |
| **INV-02** | 재수집 결과가 `project` 스냅샷과 다르면 **`project.notice_changed = 1`** 만 세운다 | 반영 여부는 사람이 결정한다 |
| **INV-03** | 공고는 **스텝·블록이 아니다.** 독립 테이블·독립 페이지 | `DOMAIN §1` — 프로젝트가 생기기 전 단계의 독립 기능 |
| **INV-04** | 자연키 중복은 **DB 제약으로 막는다** | 앱 로직만 믿으면 동시 실행 시 뚫린다 |
| **INV-05** | 크롤링 링크 관리는 **`BIDDING`** 소관 (`ADMIN` 아님) | `DOMAIN §14-3` 마지막 줄 |
| **INV-06** | 신규 공고를 **`notification` 에 넣지 않는다** | 전량 수집이면 하루 수백 건. `DOMAIN §9` 스스로 경고 — *"알림을 끄면 결재 상신도 못 본다."* 공고 알림이 결재 알림을 죽인다 |
| **INV-07** | 확정되지 않은 AI 요약을 **그대로 쓰지 않는다** | `UC-03` — 사람이 반드시 검토·수정한 뒤 확정 |
| **INV-08** | 입찰 공고 블록은 공고 원본을 편집하지 않는다 | 블록은 프로젝트 안에서 공고를 보는 창이다. 공고 수정은 입찰관리 소관 |
| **INV-09** | 전환 시 생성된 프로젝트 스냅샷은 재수집으로 자동 덮지 않는다 | 정정공고 감지는 하되, 반영 여부는 사람이 결정한다 |
| **INV-10** | 입찰 스테이지·스텝·블록 자동 생성은 한 번만 일어난다 | 같은 공고로 프로젝트/블록이 중복 생성되면 안 된다 |

## 4. 데이터 규칙 — 실측으로 확인된 함정

**아래는 실제 입찰 대장과 대상 사이트에서 확인한 것이다. 추측이 아니다.**

| # | 실제 값 | 처리 |
|---|--------|------|
| 1 | 투찰하한율 `공고문참조`, 예가변동폭 `-2% ~ 2%` | **숫자 타입 금지.** 문자열로 원문 보존. 파싱은 v2 |
| 2 | 기초금액 `-` | `null` 로 정규화 |
| 3 | 입찰개시일 `0000-00-00 00:00:00` | **MySQL strict mode 에서 INSERT 가 죽는다.** `null` 치환 필수 |
| 4 | 날짜 포맷 3종 `2025-09-25 09:00:00` / `25-10-14 18:00` / `9/24` | 파서가 전부 수용 |
| 5 | 지역제한 `[부산][울산]`, 업종제한 `[정비산업][원가계산][기타]` | v1 은 **원문 문자열 그대로**. 정규화는 v2 |
| 6 | KCAA 인코딩 **EUC-KR** | UTF-8 로 읽으면 **한글 전부 깨진다.** 인코딩 명시 필수 |
| 7 | KCAA 는 `<frameset>` | 루트 대신 **프레임 내부 URL** 을 직접 호출 |
| 8 | KCAA HTTPS 인증서가 self-signed | **HTTP 로 호출**한다 |
| 9 | KCAA 고정공지 3건이 번호 없이 항상 맨 위 | **번호 없는 행은 스킵.** 안 그러면 `NEW` 판정(LST-02)이 꼬인다 |
| 10 | KCAA 상세 링크의 `board_data` 가 Base64 | 디코드하면 `idx=1204&...`. **`idx` 가 자연키**, 화면 번호(`listNo`)는 글 삭제 시 밀리므로 **키로 쓰면 안 된다** |
| 11 | KCAA 목록 `<td>` 11개 중 내용은 3개 | 인덱스 대신 **텍스트 있는 칸만** 선택 |

### 4-1. 공고가 가져야 할 값

| 항목 | 출처 | 비고 |
|------|------|------|
| 출처 코드 · 출처명 | 시스템 | **필수** |

## 5. ⚠️ 구현자가 반드시 알아야 할 함정

**`NULL` 을 자연키에 넣지 마라.**

MySQL 은 UNIQUE 인덱스에서 `NULL` 을 **서로 다른 값으로 취급**한다.
차수가 `NULL` 이면 같은 공고가 몇 번이든 INSERT 된다 → **CRW-04 가 통째로 무효**다.

이 프로젝트는 이미 같은 함정을 밟은 적이 있다. 기존 마이그레이션 `department` 테이블 주석에 그대로 적혀 있다:

> MySQL 은 UNIQUE 인덱스에서 NULL 을 서로 다른 값으로 취급하므로 … 같은 이름으로 여러 개 들어간다

**차수와 외부 식별자는 `NOT NULL`.** 값이 없으면 빈 문자열을 쓴다.
수동 등록 건은 외부 식별자를 앱에서 생성해 채운다.
