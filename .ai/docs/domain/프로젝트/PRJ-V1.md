## 0. 한 줄 정의

**프로젝트 하나에 스테이지 > 스텝 > 블록을 자유롭게 조립하고, 그 진행 상태를 한 화면에서 답한다.**

계층이 이 서비스의 뼈대다. 도메인 의미는 전부 블록이 갖고, **계층 자체는 의미를 모른다** — 그래서 회사마다 다른 절차를 담을 수 있다.

## 2. 요구사항

**표 형식**: `ID │ 대분류 │ 중분류 │ 소분류 │ 요구사항 │ 수용 기준`

### 2-A. 프로젝트 (`PRJ`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **PRJ-001** | 프로젝트 | 생성 | 직접 생성 | 사용자는 공고 없이 프로젝트를 직접 생성할 수 있다 | `bid_notice_id` 가 `NULL` 인 행이 생기고 상태가 `NOT_STARTED` 다. **정상 경로로 처리되며 경고가 뜨지 않는다** |
| **PRJ-002** | 프로젝트 | 생성 | 공고 전환 | 사용자는 공고에서 프로젝트를 생성할 수 있고, 이때 **링크만** 걸린다 | `project.bid_notice_id` 만 채워진다. **기초금액·추정가격·마감일이 `project` 에 복사되지 않는다** |
| **PRJ-003** | 프로젝트 | 상태 | 상태 전이 | 사용자는 상태를 `진행 전 → 진행 중 → 정산 중 → 완료` 로 바꿀 수 있다 | 4개 값이 저장된다. 역방향 전이를 막지 않는다 (되돌릴 일이 실제로 있다) |
| **PRJ-004** | 프로젝트 | 상태 | 종결 | 사용자는 어느 상태에서든 프로젝트를 `종결` 로 바꿀 수 있다 | `CLOSED` 로 저장된다. **목록·로그에서 사라지지 않는다** |
| **PRJ-005** | 프로젝트 | 상태 | 종결 사유 | 사용자는 종결 시 사유(미참여/유찰/미선정/취소)를 **반드시** 입력해야 한다 | 사유 없이 요청하면 **400**. `close_reason_code` + `close_reason_note` 가 저장된다 |
| **PRJ-006** | 프로젝트 | 조건 등재 | 기간 | 사용자는 시작일·종료일을 직접 입력할 수 있다 | 자동 계산하지 않는다. 날짜가 있으면 캘린더 조회 응답에 포함된다 |
| **PRJ-007** | 프로젝트 | 조건 등재 | 사업 카테고리 | 사용자는 사업 카테고리를 **복수** 선택할 수 있다 | `project_business_category` 에 N 행이 생긴다. 같은 카테고리 중복은 `UNIQUE` 로 차단 |
| **PRJ-008** | 프로젝트 | 금액 | 계약금액 | 사용자는 계약금액을 프로젝트 속성으로 입력할 수 있다 | **`project.contract_amount` 한 곳에만** 저장된다. 블록에 금액 컬럼을 만들지 않는다 |
| **PRJ-009** | 프로젝트 | 참여자 | 개인 단위 등록 | 사용자는 참여자를 **한 명씩** 추가할 수 있다 | **팀·부서 일괄 추가 API 가 존재하지 않는다.** `project_member` 에 1행씩 생긴다 |
| **PRJ-010** | 프로젝트 | 참여자 | 권한 부여 | 사용자는 참여자마다 `VIEWER` / `EDITOR` / `NONE` 을 줄 수 있다 | 3값만 허용. `MANAGER` 를 보내면 **400** |
| **PRJ-011** | 프로젝트 | 참여자 | 자기 권한 잠금 | 사용자는 **자기 자신의 권한 행**을 수정할 수 없다 | 자기 `project_member` 행 수정 요청은 **403**. `EDITOR` 여도 막힌다 |
| **PRJ-012** | 프로젝트 | 참여자 | 편집 주체 | 프로젝트 `EDITOR` 전원과 `MASTER`·`ADMIN` 이 참여자·권한을 편집할 수 있다 | `VIEWER` 의 편집 요청은 403 |
| **PRJ-013** | 프로젝트 | 진척 | 프로젝트 진척률 | 사용자는 `완료 스텝 / 전체 스텝` 진척률을 볼 수 있다 | **이슈 수가 계산식에 들어가지 않는다.** 스텝 0개면 % 를 응답에 담지 않는다 |
| **PRJ-014** | 프로젝트 | 삭제 | 삭제 조건 | 사용자는 `진행 전` 이고 **스텝·블록이 0개**일 때만 프로젝트를 삭제할 수 있다 | 그 외에는 **409** 와 함께 "종결로 처리하라" 안내. 삭제는 `deleted_at` |
| **PRJ-015** | 프로젝트 | 목록 | 필터 | 사용자는 목록을 상태·카테고리·기간으로 필터링할 수 있다 | **보관 기능이 없다.** 종결 건도 필터로 다시 볼 수 있다 |
| **PRJ-016** | 프로젝트 | 로그 | 활동 기록 | 시스템은 계층 사건을 프로젝트 단위 로그로 남긴다 | 계층 사건이면 `activity_log.project_id` 를 **앱이 반드시 채운다**(기록 규칙 · **컬럼 제약은 NULL 허용** — 재무 미매칭 로그 때문), **`target_name` 스냅샷이 반드시 채워진다** → [`ERD.md`](ERD.md) §5-4 |
| **PRJ-017** | 프로젝트 | 로그 | 상위권한 표기 | `MASTER`·`ADMIN` 이 참여자가 아닌 프로젝트를 고치면 로그에 표기된다 | `privileged_override = 1` 이 저장되고 활동기록 화면에 `상위권한으로 수정` 이 보인다 |

### 2-B. 스테이지 (`STG`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **STG-001** | 스테이지 | 관리 | CRUD | 사용자는 스테이지를 만들고 이름을 바꾸고 지울 수 있다 | `stage` 에 `project_id`·`name`·`sort_order` 만 저장된다 |
| **STG-002** | 스테이지 | 관리 | 순서 변경 | 사용자는 스테이지 순서를 바꿀 수 있다 | `sort_order` 만 갱신된다. 하위 스텝은 안 건드린다 |
| **STG-003** | 스테이지 | 삭제 | 하위 스텝 이전 | 사용자는 스테이지 삭제 시 **하위 스텝을 어디로 옮길지** 고른다 | **스텝이 함께 삭제되지 않는다.** 이전 대상 미지정이면 400 |
| **STG-004** | 스테이지 | 권한 | 권한 미저장 | 시스템은 스테이지에 권한·상태를 저장하지 않는다 | `stage_permission` 테이블이 **없다**. 화면의 "하위 스텝 일괄 적용"은 `step_permission` 에 떨어진다 |

### 2-C. 스텝 (`STP`)

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **STP-001** | 스텝 | 관리 | CRUD | 사용자는 스텝을 만들고 고치고 지울 수 있다 | `step.project_id` 가 **`NOT NULL` 로 채워진다.** `stage_id` 는 `NULL` 허용 |
| **STP-002** | 스텝 | 관리 | 순서 변경 | 사용자는 스텝 순서를 바꿀 수 있다 | `sort_order` 만 바뀐다. **선행 스텝 완료를 검사하지 않는다** |
| **STP-003** | 스텝 | 속성 | 기본 속성 | 사용자는 이름 · 기간 · 책임자를 설정할 수 있다 | `owner_user_id` 는 `employee_id` 다(계정 id 아님). 책임자는 **작업자가 아니다** |
| **STP-004** | 스텝 | 상태 | 3상태 | 사용자는 스텝 상태를 미시작 / 진행 중 / 완료 로 둘 수 있다 | `NOT_STARTED`·`IN_PROGRESS`·`DONE` 저장. **스텝 진척률과 별개 값이다** |
| **STP-005** | 스텝 | 완료 처리 | 완료 버튼 | 스텝 편집 권한자는 **이슈가 미완료여도** 스텝을 완료로 바꿀 수 있다 | 미완료 이슈가 있어도 완료된다. `completed_by`·`completed_at` 이 기록된다 |
| **STP-006** | 스텝 | 완료 처리 | 미완료 이슈 | 사용자는 완료 시 남은 이슈를 `그대로 두기 / 함께 종료` 중에서 고를 수 있다 | 미완료 수가 표시된다. `그대로 두기` 면 그 이슈에 `완료된 스텝` 배지가 붙는다 |
| ~~**STP-007**~~ | ~~스텝~~ | ~~완료 처리~~ | ~~송부 스텝~~ | ⛔ **폐기 (2026-08-03)** — 송부 스텝 개념을 만들지 않는다 | `step.step_type` 을 신설하지 않는다. 완료 처리는 `STP-005` 하나로 통일 → [`ERD.md`](ERD.md) §0-1 |
| **STP-008** | 스텝 | 삭제 | 이슈 처리 | 사용자는 스텝 삭제 시 이슈를 `이동 / 함께 종료` 중에서 고른다 | 미선택이면 400. **조용히 같이 지우지 않는다** |
| **STP-009** | 스텝 | 삭제 | 잠금 검사 | 잠금 블록이 있는 스텝은 삭제할 수 없다 | 입금이 연결된 입금확인 블록이 있으면 **409** |
| **STP-010** | 스텝 | 권한 | 오버라이드 | 사용자는 스텝별로 `VIEWER` / `EDITOR` / `NONE` 을 줄 수 있다 | `step_permission` 에 저장된다. `NONE` 이면 목록에서 제외된다 |
| **STP-011** | 스텝 | 권한 | 상속 | `step_permission` 행이 없으면 **프로젝트 권한을 그대로 쓴다** | 행 없음이 차단이 아니다. 특정 스텝만 가리려면 `NONE` 행을 **명시적으로** 넣어야 한다 |
| **STP-012** | 스텝 | 진척 | 스텝 진척률 | 사용자는 `완료 이슈 / 전체 이슈` 진척률을 스텝 카드에서 볼 수 있다 | **이슈가 0개면 응답에 % 를 담지 않는다** (`0` 으로 내리지 않는다) |

### 2-D. 블록 골격 (`BLK`)

> 타입별 상세는 각 담당 소관이다 (§1-2). 여기는 **모든 블록에 공통으로 적용되는 골격**이다.

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **BLK-001** | 블록 | 타입 | 닫힌 enum | 사용자는 정의된 **10종** 안에서만 블록을 만들 수 있다 | 목록 밖 타입은 **400**. 확장형 JSON 스키마 입력 경로가 없다.<br/>✅ **10종 (2026-08-03)** — ⛔ `MEMO` **폐기** · ⭐ `BID_NOTICE` **신설**. 자유 서술은 `TEXT` 담당 → [`ERD.md`](ERD.md) §0-11 |
| **BLK-002** | 블록 | 소유 | 스텝 소유 | 블록은 **항상 스텝**에 붙는다 | `block.step_id` `NOT NULL`. ⛔ **`block.project_id` 는 없다** (2026-08-03 폐기) — 프로젝트는 `step` 을 조인해서 얻는다 → [`ERD.md`](ERD.md) §0-13 |
| **BLK-003** | 블록 | 배치 | 3열 그리드 | 사용자는 블록을 `row_index` · `sort_order` · `col_span` 으로 배치할 수 있다 | `col_span` 이 1~3 밖이면 400. **총 열 수는 3 고정** |
| **BLK-004** | 블록 | 배치 | 드래그 재배치 | 사용자는 블록을 끌어서 순서를 바꿀 수 있다 | `UNIQUE(step_id,row_index,sort_order)` 를 **걸지 않아** 드래그 중간 중복이 허용된다 |
| **BLK-005** | 블록 | 상태 | 상태 미보유 | 블록은 자체 진행 상태를 갖지 않는다 | **`block.status` 컬럼이 없다.** 진행 상태는 연결된 이슈가 표현한다 |
| **BLK-006** | 블록 | 조회 | 스텝 단위 일괄 조회 | 사용자가 스텝을 열면 블록과 타입별 상세가 **한 번에** 내려온다 | `LEFT JOIN` 한 방으로 처리된다. 타입 수만큼 쿼리가 늘지 않는다 |
| **BLK-007** | 블록 | 삭제 | soft delete | 블록 삭제는 `deleted_at` 플래그다 | **하드 삭제 API 가 존재하지 않는다.** 로그가 가리키는 대상이 사라지지 않는다 |
| **BLK-008** | 블록 | 삭제 | 잠금 **4종** | 잠금 대상 블록은 삭제할 수 없다 | ① 입금 연결 입금확인 ② **계산서 연결 조회**(TXL-009) ③ 진행 중 결재 ④ 결재 대상 파일 블록 → **409.** 그 외는 전부 삭제된다 → [`BLOCK.md`](../../global/BLOCK.md) §8 |
| **BLK-009** | 블록 | 이슈 연결 | 같은 스텝 검증 | `issue_block` 연결 시 블록과 이슈가 **같은 스텝**이어야 한다 | `block.step_id ≠ issue.step_id` 면 **400.** DB 제약으로 못 걸어서 애플리케이션이 막는다 |
| **BLK-010** | 블록 | 이슈 연결 | 중복 방지 | 같은 이슈-블록 쌍을 두 번 연결할 수 없다 | `UNIQUE(issue_id, block_id)` 로 DB 가 막는다 |
| **BLK-011** | 블록 | 이슈 연결 | 완료 배지 | 블록 카드 우하단에 연결된 이슈의 `완료/전체` 가 보인다 | 삭제된 블록(`deleted_at IS NOT NULL`)은 집계에서 빠진다. 연결 행 자체는 유지된다 |
| **BLK-012** | 블록 | 담당자 | 블록 담당자 | 사용자는 블록마다 담당자를 지정할 수 있다 | `block.owner` 에 **사번(`VARCHAR(20)`)** 이 저장된다. **선택 입력.** ✅ 운용 규칙 확정 — 정산현황 담당자 = **다음 예정일 회차 블록의 `owner`** → [`../재무관리/STL-V1.md`](../재무관리/STL-V1.md) §5-6 |

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **스테이지는 권한·상태·데이터를 저장하지 않는다** | 저장 지점이 3층이 되면 "이 사람이 이 스텝을 고칠 수 있나"를 사람이 추적 못 한다 → 아무도 권한을 안 건드린다 |
| **INV-02** | **`step.project_id` 는 `NOT NULL`** | `stage_id` 가 `NULL` 인 스텝이 정상 케이스인데, `project_id` 가 없으면 **어느 프로젝트 소속인지 알 방법이 사라진다** |
| **INV-03** | **프로젝트 진척률에 이슈를 섞지 않는다** | 프로젝트 % 는 다른 팀·경영진이 **비교하는 숫자**다. 이슈 세분화 정도가 다르면 비교가 무의미해진다 |
| **INV-04** | **이슈 0개인 스텝은 % 를 안 띄운다** | `0/0` 은 100% 로 봐도 0% 로 봐도 거짓말이다. 완료 판정은 어차피 수동 버튼이 한다 |
| **INV-05** | **하드 삭제가 없다** | 로그가 참조하는 대상이 사라지면 **로그가 고아 문자열**이 된다. 이력 관리가 이 서비스의 존재 이유다 |
| **INV-06** | **`issue_block` 은 같은 스텝만** | 없으면 스텝 A 블록 카드엔 `2/5` 가 뜨는데 스텝 A 진척률에는 안 들어간다. **사용자 눈에는 그냥 버그다** |
| **INV-07** | **참여자는 개인 단위만** | 팀 단위를 허용하면 인턴 배정 즉시 전 프로젝트 견적·단가가 보인다 |
| **INV-08** | **금액은 `project.contract_amount` 한 곳** | 블록·스텝은 자유 편집이라 스텝 재배치에 금액이 사라질 수 있다. **블록은 입력 UI 일 뿐이다** |
| **INV-09** | **`activity_log.target_name` 을 반드시 채운다** | soft delete 라 대상은 안 사라지지만 **이름은 바뀐다.** FK 만 들면 과거 로그가 전부 새 이름으로 표시되고 그 로그는 거짓이 된다 |
| **INV-10** | **자기 권한 행은 못 고친다** | `VIEWER` 로 초대된 사람이 자기를 `EDITOR` 로 올리면 **권한 체계가 장식이 된다** |
