## 0. 한 줄 정의

**돈이 실제로 들어왔는지를 재무가 확정하고, 그것을 프로젝트 정산 회차에 붙인다.**

핵심은 **경계**다 — 계획(정산 회차·비율·청구조건)은 프로젝트 안 실무자가, 실행(입금 확정)은 프로젝트 밖 재무가 한다.
그리고 **돈은 블록보다 먼저 들어올 수 있다.** 이 한 문장이 매칭을 2단으로 만든 이유 전부다.

| **분할 입금 / 상계 / 지연이자 구조화** | 한 입금 = 한 행. 분할은 행을 여러 개 만든다. 구조화는 v2 |

| **청구서 작성·결재** | 프로젝트 쪽 파일 블록 + 결재 블록 소관 |

## 2. 요구사항

### 2-A. 입금 등록 · 확정 (`PAY`) — P-40

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **PAY-001** | 입금관리 | 입금 등록 | 직접 등록 | 재무 담당자는 입금 건을 직접 등록할 수 있다. **수집 경로와 별개로 항상 열려 있다** | `page_code='FINANCE'` + `EDITOR` 가 아니면 **403**. `payment` 에 1행 생성 |
| **PAY-002** | 입금관리 | 입금 등록 | 필수 항목 | 사용자는 입금일 · 금액 · 적요를 입력한다 | `paid_at` 또는 `amount` 가 없으면 **400**. `bank_memo` 는 선택 |
| **PAY-003** | 입금관리 | 입금 등록 | 미매칭 허용 | 사용자는 **어느 프로젝트인지 모르는 상태로도** 입금을 등록할 수 있다 | `payment.project_id` 가 `NULL` 인 행이 정상 저장된다. 경고가 뜨지 않는다 |
| **PAY-004** | 입금관리 | 입금 목록 | 미매칭 우선 정렬 | 사용자는 목록에서 **미매칭 건을 먼저** 본다 | `project_id IS NULL` 인 행이 상단에 정렬된다. 떠도는 돈이 먼저 보인다 |
| **PAY-005** | 입금관리 | 입금 목록 | 필터 | 사용자는 기간 · 매칭 여부 · 프로젝트로 목록을 좁힐 수 있다 | 각 조건이 단독·조합으로 동작한다 |
| **PAY-006** | 입금관리 | 입금 확정 | 확정 주체 | **재무만** 입금을 확정할 수 있다 | `matched_by` 에 `employee_id` 가 기록된다. 프로젝트 참여자(실무자) 요청은 **403** |
| **PAY-007** | 입금관리 | 입금 수정 | 금액·일자 수정 | 재무는 등록한 입금의 금액·일자를 고칠 수 있다 | `FINANCE`+`EDITOR` 만. 수정 사실이 로그에 남는다 |
| **PAY-008** | 입금관리 | 입금 삭제 | 연결 시 잠금 | 블록에 연결된 입금은 삭제할 수 없다 | **409.** 먼저 `MTC-007` 로 연결을 해제해야 한다 |
| **PAY-009** | 입금관리 | 권한 | 조회 주체 | 프로젝트 참여자(실무자)는 재무 탭 입금 목록에 들어갈 수 없다 | `page_code='FINANCE'` 행이 없으면 **403**. 실무자는 블록으로만 본다 |

### 2-B. 입금 수집 (`IMP`) — P-40

**수집은 자동, 확정은 사람.** 이 절은 `payment` 행을 **만드는 경로**만 다룬다. 매칭·확정은 2-C 소관이고 INV-02 가 그대로 적용된다.

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **IMP-001** | 입금관리 | CSV 수집 | 파일 업로드 | 재무 담당자는 은행에서 받은 거래내역 CSV 를 올려 입금을 일괄 등록한다 | `FINANCE`+`EDITOR` 가 아니면 **403**. 성공 시 파싱된 행 수만큼 `payment` 생성 |
| **IMP-002** | 입금관리 | CSV 수집 | 컬럼 매핑 | 사용자는 CSV 의 어느 열이 입금일 · 금액 · 적요인지 지정한다 | 은행마다 헤더가 달라 **고정 파서를 쓰지 않는다.** 매핑 없이 업로드하면 **400** |
| **IMP-003** | 입금관리 | CSV 수집 | 입금 건만 | 출금 행은 수집하지 않는다 | 금액이 출금인 행은 건너뛴다. 건너뛴 수가 결과에 표시된다 |
| **IMP-004** | 입금관리 | CSV 수집 | 부분 실패 안내 | 파싱 실패 행이 있어도 나머지는 저장된다 | `성공 N건 / 실패 M건` 과 실패 행 번호·사유가 반환된다. 전체 롤백하지 않는다 |
| **IMP-005** | 입금관리 | 수집 공통 | 중복 차단 | 같은 거래를 두 번 수집하지 않는다 | **은행 거래 고유번호**가 같은 행은 **건너뛴다**(에러 아님). 건너뛴 수가 표시된다 |
| **IMP-006** | 입금관리 | 수집 공통 | 고유번호 필수 | 고유번호가 없는 행은 수집하지 않는다 | 해당 행은 실패로 집계된다. **키 없이 넣으면 중복을 영영 못 막는다** |
| **IMP-007** | 입금관리 | 수집 공통 | 출처 기록 | 각 입금은 **어떻게 들어왔는지**를 기록한다 | 직접 등록 · CSV 를 구분해 저장·표시한다 |
| **IMP-008** | 입금관리 | 수집 공통 | 미매칭 저장 | 수집된 입금은 **미매칭 상태로** 들어온다 | `project_id` 가 `NULL` 이다. 수집이 매칭을 겸하지 않는다 (INV-02) |

### 2-C. 매칭 — 2단 (`MTC`) — P-41

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **MTC-001** | 입금관리 | 매칭 ① | 프로젝트 매칭 | 재무는 입금을 프로젝트에 매칭한다. **이것이 필수 단계다** | `payment.project_id` 가 채워진다. **입금확인 블록이 하나도 없어도 성공한다** |
| **MTC-002** | 입금관리 | 매칭 ② | 블록 연결 | 재무는 입금을 입금확인 블록에 연결할 수 있다. **선택 단계다** | 연결 사실과 `linked_by` 가 저장된다 ⚠️ 저장 위치 미정 → §5-4 |
| **MTC-003** | 입금관리 | 매칭 ② | 선후 관계 | 블록 연결 전에 **프로젝트 매칭이 먼저** 되어 있어야 한다 | `project_id` 가 `NULL` 인 입금을 블록에 연결하면 **400** |
| **MTC-004** | 입금관리 | 매칭 ② | 프로젝트 일치 | 연결하려는 블록은 **매칭된 그 프로젝트**에 속해야 한다 | `block.project_id ≠ payment.project_id` 면 **400** |
| **MTC-005** | 입금관리 | 자동 매칭 | 후보 추천 | 시스템은 매칭 후보를 정렬해 보여준다 | **발주처명 ↔ 적요 일치** → 금액 → 입금일 근접 순으로 정렬된다. **자동으로 확정하지 않는다** |
| **MTC-005B** | 입금관리 | 매칭 해제 | 해제 주체 | **재무만** 프로젝트 매칭을 해제할 수 있다 | `FINANCE`+`EDITOR` 아니면 **403.** 해제하면 `project_id` 가 `NULL` 로 돌아간다 |
| **MTC-005C** | 입금관리 | 매칭 해제 | 블록 연결 시 차단 | 블록에 연결된 입금은 프로젝트 매칭을 해제할 수 없다 | **409.** 먼저 `MTC-007` 로 블록 연결을 해제해야 한다 |
| **MTC-006** | 입금관리 | 자동 매칭 | 사람이 확정 | **확정 버튼은 사람이 누른다** | 자동 확정 경로가 코드에 존재하지 않는다. 배치가 `project_id` 를 쓰지 않는다 |
| **MTC-007** | 입금관리 | 연결 해제 | 해제 주체 | **재무만** 블록 연결을 해제할 수 있다 | `FINANCE`+`EDITOR` 가 아니면 **403.** 실무자는 요청 경로 자체가 없다 |
| **MTC-008** | 입금관리 | 연결 해제 | 잠금 풀림 | **연결된 입금이 0건이 되어야** 블록·스텝을 다시 삭제할 수 있다 | 3건 중 1건만 풀면 여전히 **409**. 전부 풀면 삭제 요청이 **200** |
| **MTC-009** | 입금관리 | 매칭 제약 | **1블록 N입금** | 입금확인 블록 하나에 입금을 **여러 건** 붙일 수 있다 | 분할 입금 3건이 한 회차 블록에 모두 연결된다 |
| **MTC-010** | 입금관리 | 매칭 제약 | 1입금 1블록 | 입금 하나는 블록 **한 곳에만** 붙는다 | 이미 연결된 입금을 다른 블록에 연결하면 **409.** 같은 돈이 두 회차에 잡히면 안 된다 |

### 2-D. 입금확인 블록 (`PCB`) — P-22A

| ID | 대분류 | 중분류 | 소분류 | 요구사항 | 수용 기준 |
|----|--------|--------|--------|---------|----------|
| **PCB-001** | 입금관리 | 회차 관리 | 회차 생성 | 실무자는 정산 스텝에 입금확인 블록을 만들어 **정산 회차를 만든다** | **별도 회차 테이블이 없다.** 블록 1개 = 회차 1개 |
| **PCB-001B** | 입금관리 | 회차 관리 | **스텝당 1개** | 한 스텝에는 입금확인 블록을 **하나만** 만들 수 있다 | 두 번째 생성은 **409.** 회차를 늘리려면 스텝을 새로 판다 → INV-07C |
| **PCB-002** | 입금관리 | 회차 관리 | 제목 = 회차명 | 사용자는 블록 제목에 회차명을 쓴다 (`1차 정산(선급 60%)`) | `block.title` 에 저장된다. 별도 회차명 컬럼을 만들지 않는다 |
| **PCB-002B** | 입금관리 | 회차 관리 | 회차 번호 | 각 회차는 프로젝트 안에서 **유일한 회차 번호**를 갖는다 | `round_no` 에 저장된다. 생성 시 `max+1` 자동 부여 후 **수정 가능.** 프로젝트 단위 `UNIQUE` |
| **PCB-002C** | 입금관리 | 회차 계획 | 예정일 · 예정금액 | 실무자는 회차에 **입금 예정일**과 **예정금액**을 적을 수 있다 | 둘 다 **선택 입력.** 계약 조건을 아는 건 실무자다 ([`DOMAIN.md`](DOMAIN.md) §7-2 계획/실행 분리) |
| **PCB-002D** | 입금관리 | 회차 계획 | 예정금액 상한 | 회차 예정금액의 합은 계약금액을 **넘을 수 없다** | `Σ 예정금액 > contract_amount` 면 **400.** 모자란 것(미계획)은 정상, 초과는 입력 실수뿐이다 |
| **PCB-003** | 입금관리 | 블록 표시 | 읽기 전용 | 프로젝트 참여자는 입금 정보를 **읽기만** 한다 | 스텝 `EDITOR` 여도 확정·연결 요청은 **403** ([`PERMISSION.md`](PERMISSION.md) §5) |
| **PCB-004** | 입금관리 | 블록 표시 | 표시 항목 | 사용자는 블록에서 연결된 입금을 **건별로** 본다 — 입금일 · 금액 · 확정자 | 여러 건이면 목록으로 나온다. 미연결이면 `대기`. 빈 화면이 아니다 |
| **PCB-004B** | 입금관리 | 블록 표시 | 합계 | 사용자는 블록에서 연결된 입금의 **합계 금액**을 본다 | 분할 입금 3건이면 3건의 합이 표시된다. 회차 단위 수금액이 한눈에 보인다 |
| **PCB-005** | 입금관리 | 블록 삭제 | 블록 잠금 | 입금이 **한 건이라도** 연결된 블록은 삭제할 수 없다 | **409** + "재무가 연결을 해제해야 합니다" 안내 |
| **PCB-006** | 입금관리 | 블록 삭제 | 스텝까지 잠금 | 그 블록이 들어 있는 **스텝도** 삭제할 수 없다 | **409.** 블록만 막고 스텝을 열어두면 우회로가 생긴다 |
| **PCB-007** | 입금관리 | 템플릿 | 담기는 범위 | 템플릿에는 블록과 **제목만** 담긴다 | 연결된 입금은 복사되지 않는다. 적용된 블록은 미연결 상태로 생성된다 |

### 2-E. 정산 조회 화면 → 이관

**조회 화면은 [`STL-V1.md`](STL-V1.md) 소관이다.** 전사 축 P-44 · 프로젝트 축 P-25(후순위) 둘 다.

## 3. 불변식 — 절대 깨지면 안 되는 것

| ID | 규칙 | 왜 |
|----|------|-----|
| **INV-01** | **실무자는 입금을 확정할 수 없다** | 실무자가 스스로 체크하면 "받았다고 쳤는데 실제론 안 들어옴"이 생기고, **그 순간 정산 데이터를 아무도 못 믿는다** |
| **INV-02** | **수집은 자동, 매칭·확정은 사람.** 자동 매칭은 추천 후보 정렬까지만 | 은행 적요에 용역명은 안 온다(회사명 축약만). 금액도 분할입금·상계·지연이자로 자주 안 맞는다. **오매칭 복구가 매우 비싸다** — CSV·API 로 들어와도 미매칭 상태로 선다 |
| **INV-02B** | **수집 경로가 죽어도 직접 등록은 산다** | 은행 포맷 변경·API 장애로 재무 업무가 멈추면 안 된다 |
| **INV-03** | **① 프로젝트 매칭은 필수, ② 블록 연결은 선택** | **돈은 블록보다 먼저 들어올 수 있다.** 계약 직후 선급금이 들어왔는데 실무자가 아직 정산 스텝을 안 팠을 수 있다 |
| **INV-04** | **블록 없이 매칭만 된 상태가 정상이다** | 1단만 있으면 그 입금이 시스템 밖에서 떠돈다 — **Excel 시절과 똑같아진다** |
| **INV-05** | **연결되면 블록과 스텝 둘 다 삭제 잠금** | 블록만 막고 스텝을 열어두면 스텝을 지워 블록을 없애는 우회로가 생긴다 |
| **INV-06** | **연결 해제는 재무만** | 실무자가 풀 수 있으면 잠금 자체가 무의미하다 |
| **INV-07** | **입금확인 블록이 곧 정산 회차다** | 별도 회차 레코드를 두면 이중 관리가 되고, **어긋났을 때 어느 쪽이 맞는지 아무도 모른다** |
| **INV-07B** | **회차 1개에 입금 N건, 입금 1건은 회차 1곳** | 계약금 1억이 5천만원씩 2번 들어와도 회차는 하나다. 반대로 같은 돈이 두 회차에 잡히면 **수금액이 두 배로 보인다** |
| **INV-07C** | **스텝 1개 = 회차 1개** | 한 스텝에 회차가 둘이면 **같은 스텝의 세금계산서 블록이 어느 회차 것인지 알 수 없다.** [`TAX-V1.md`](TAX-V1.md) INV-08 이 "회차(=정산 스텝)가 계산서와 입금을 묶는다"고 쓴 것과 이 조항이 짝이다 |
| **INV-08** | **같은 거래를 두 번 수집하지 않는다 — 판정은 은행 거래 고유번호로** | 중복 행이 들어오면 잔액·정산 숫자가 조용히 부풀고, 어느 쪽이 진짜인지 사후에 못 가린다. **`날짜+금액` 으로 판정하면 진짜 2건을 1건으로 지운다** |
