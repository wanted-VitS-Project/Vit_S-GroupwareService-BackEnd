## 1. 브랜치 전략

### ✅ 2단계 확정 — `main` + `develop`

> 초기 세팅 커밋(`d714cad`) 시점에 원격에 `main` / `develop` 두 브랜치가 함께 생성되어 있음.
> 세부 규칙(브랜치명 이슈번호 포함, 보호 규칙, 머지 방식)은 아래 🔴 항목으로 남아 있다.

| 브랜치 | 역할 | 보호 |
|--------|------|------|
| `main` | 배포 기준. 항상 배포 가능한 상태 | ✅ 직접 push 금지, PR 필수 |
| `develop` | 통합 개발. 기능 브랜치의 머지 대상 | ✅ 직접 push 금지, PR 필수 |
| `feat/*` | 기능 개발 | — |
| `fix/*` | 버그 수정 | — |
| `refactor/*` | 리팩토링 | — |
| `chore/*` | 설정·빌드·문서 | — |
| `hotfix/*` | 운영 긴급 수정 (`main` 에서 분기) | — |

**흐름**: `feat/*` → PR → `develop` → (검증) → PR → `main` → 배포

### 🔒 브랜치 보호 (2026-07-28 적용 완료)

`main` · `develop` 둘 다 아래 규칙이 걸려 있다.

| 규칙 | 설정 | 의미 |
|------|------|------|
| 직접 push | ❌ 금지 | 반드시 PR 을 거친다 |
| 승인 인원 | **1명** | 본인 PR 은 본인이 승인 불가 → 항상 누군가 봐야 함 |
| 새 커밋 시 기존 승인 | 자동 무효화 | 승인 후 코드를 바꿔치기하는 것 방지 |
| 리뷰 코멘트 | 전부 해결해야 머지 | |
| force push · 브랜치 삭제 | ❌ 금지 | |
| 선형 히스토리 | ✅ 필수 | Squash 전용 정책과 일치 |
| **관리자 예외** | ❌ **없음** | 조직원 전원이 admin 이라 예외를 두면 규칙이 무의미해짐 |

> ⚠️ 관리자도 예외가 없다. 긴급 상황에는 GitHub 설정에서 보호를 잠시 껐다가
> **반드시 다시 켠다.** 끈 채로 두는 것이 가장 위험하다.

### 브랜치 이름 규칙

```
<타입>/<간단한-설명>
```

- 소문자 + 하이픈(`-`) 사용. 한글·공백·언더스코어 금지.
- 예: `feat/user-login`, `fix/token-expiry`, `chore/github-actions`

**🔴 논의 필요**
- [ ] 이슈 번호를 브랜치명에 넣을 것인가 (`feat/12-user-login`)
- [ ] 브랜치 보호 규칙: 승인 몇 명 필요? CI 통과 필수 여부?
- [ ] `main` / `develop` 브랜치 보호 규칙이 실제로 설정되어 있는지 확인 (현재 미확인)

## 2. 커밋 메시지

상세 양식: [template/COMMIT.md](template/COMMIT.md)

```
<prefix>: <한 줄 요약> (#이슈번호)

- 변경 사항 1
- 변경 사항 2
```

| prefix | 사용 시점 |
|--------|----------|
| `feat` | 신규 기능 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 (동작 변화 없음) |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드·설정·의존성 |
| `ci` | CI/CD 파이프라인 |

## 3. PR 규칙

상세 양식: [template/PR.md](template/PR.md)

- **제목**: `[타입] 작업 내용` — 예: `[Feat] 로그인 API 구현`
- **본문**: 템플릿 준수 (PR 생성 시 자동 적용), `Closes #N` 으로 이슈 연결
- **승인**: **1명 필수**
- **머지 방식**: **Squash 전용** (Merge commit · Rebase 비활성화)
  - 머지 커밋 제목 = PR 제목 / 본문 = 개별 커밋 메시지 모음
- **머지 후**: 브랜치 **자동 삭제** (설정 적용됨)
- **리뷰어 자동 지정**: `.github/CODEOWNERS` 경로에 걸리면 소유자에게 리뷰 요청이 자동으로 간다

### PR 타입

| 타입 | 사용 시점 |
|------|----------|
| `[Feat]` | 기능 구현·추가 |
| `[Update]` | 기존 기능 수정·보완 |
| `[Fix]` | 오류·버그 수정 |
| `[Ref]` | 리팩토링·구조 개선 |
| `[Chore]` | 설정·빌드·문서 |

## 4. 이슈 규칙

상세 양식: [template/ISSUE.md](template/ISSUE.md)

- **제목**: `[타입] 작업 내용`
- **타입**: `[Feat]` `[Task]` `[Fix]` `[Ref]`
- 라벨·마일스톤·담당자는 GitHub 우측 필드에서 지정

### 라벨 (2026-07-28 적용 완료)

| 라벨 | 용도 | 대응 타입 |
|------|------|----------|
| `feature` | 기능 구현·추가 | `[Feat]` |
| `bug` | 오류·버그·예외 수정 | `[Fix]` |
| `task` | 기능 외 작업 — 설정·인프라·문서·조사 | `[Task]` |
| `refactor` | 리팩토링·구조 개선 | `[Ref]` |
| `chore` | 빌드·설정·의존성 | `[Chore]` |
| `infra` | 인프라·CI/CD·배포 | — |
| `documentation` | 문서 작업 | — |

> 이슈 템플릿을 쓰면 `feature` / `bug` / `task` 는 자동으로 붙는다.
> GitHub 기본 라벨(`enhancement`, `duplicate`, `wontfix` 등)은 혼란을 줄이기 위해 삭제했다.

**🔴 논의 필요**
- [ ] GitHub Projects 사용 여부
- [ ] 우선순위 라벨(`P0`/`P1`/`P2`) 도입 여부

## 5. 코드 리뷰

- **승인 1명**이 있어야 머지된다. (브랜치 보호로 강제)
- 리뷰 코멘트는 **전부 해결(resolve)** 해야 머지 버튼이 열린다.
- 승인 후 새 커밋을 푸시하면 **기존 승인이 무효화**된다. 다시 받아야 한다.
- `.github/CODEOWNERS` 에 걸린 경로는 소유자에게 리뷰가 자동 요청된다.

**🔴 논의 필요**
- [ ] 리뷰 응답 기한 (예: 24시간 내)
- [ ] 자동 리뷰 도구 도입 여부 (CodeRabbit 등)
