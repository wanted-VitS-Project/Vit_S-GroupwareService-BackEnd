## 1. 브랜치 전략

### ✅ 2단계 확정 — `main` + `develop`

> 초기 세팅 커밋(`d714cad`) 시점에 원격에 `main` / `develop` 두 브랜치가 함께 생성되어 있음.
> 세부 규칙(브랜치명 이슈번호 포함, 보호 규칙, 머지 방식)은 아래 🔴 항목으로 남아 있다.

| 브랜치 | 역할 | 보호 |
|--------|------|------|
| `main` | 배포 기준. 항상 배포 가능한 상태 | ✅ 직접 push 금지, PR 필수 |
| `develop` | 통합 개발. 기능 브랜치의 머지 대상 | ✅ 직접 push 금지, PR 필수 |
| `feat/*` | 기능 개발 | — |
| `fix/*` | 버그 수정 | — |
| `refactor/*` | 리팩토링 | — |
| `chore/*` | 설정·빌드·문서 | — |
| `hotfix/*` | 운영 긴급 수정 (`main` 에서 분기) | — |

**흐름**: `feat/*` → PR → `develop` → (검증) → PR → `main` → 배포

### 🔒 브랜치 보호 (2026-07-28 적용 완료)

`main` · `develop` 둘 다 아래 규칙이 걸려 있다.

| 규칙 | 설정 | 의미 |
|------|------|------|
| 직접 push | ❌ 금지 | 반드시 PR 을 거친다 |
| 승인 인원 | **1명** | 본인 PR 은 본인이 승인 불가 → 항상 누군가 봐야 함 |
| 새 커밋 시 기존 승인 | 자동 무효화 | 승인 후 코드를 바꿔치기하는 것 방지 |
| 리뷰 코멘트 | 전부 해결해야 머지 | |
| force push · 브랜치 삭제 | ❌ 금지 | |
| 선형 히스토리 | ❌ 미적용 | 머지 커밋 방식과 양립하지 않아 해제 (2026-07-29) |
| **관리자 예외** (`enforce_admins`) | ⚠️ **켜져 있지 않음** (`false`, `main`·`develop` 둘 다) | 실제 GitHub 설정은 admin 이 위 규칙을 **우회할 수 있는 상태** — "예외 없음"을 의도했던 원 취지(조직원 전원이 admin 이라 예외를 두면 규칙이 무의미해짐)와 실제 설정이 어긋난다 |

> ⚠️ 2026-08-16 `gh api repos/.../branches/{main,develop}/protection` 실측 결과다.
> 의도와 실제 설정이 다르다는 사실만 기록한다 — **설정을 바꿀지는 팀 결정 사항, 확인 필요.**

### 브랜치 이름 규칙

```
<타입>/<간단한-설명>
```

- 소문자 + 하이픈(`-`) 사용. 한글·공백·언더스코어 금지.
- 예: `feat/user-login`, `fix/token-expiry`, `chore/github-actions`

> ⚠️ **실제로는 `feat/*` 와 `feature/*` 가 혼용되고 있다.** `git branch -r`/`git log` 확인 결과
> `feature/txt-create`, `feature/flyway-migration-clean`, `feature/tax-invoice` 같은 브랜치가
> 존재한다(2026-08-16 확인). 위 5개 타입에는 `feature/*` 가 없다 — 새 브랜치는 `feat/*` 를 쓰고,
> 기존 `feature/*` 브랜치를 볼 때 오타·별도 규칙이 아니라 **혼용 실태**임을 알아둘 것.

**🔴 논의 필요**
- [ ] 이슈 번호를 브랜치명에 넣을 것인가 (`feat/12-user-login`)
- [ ] `feat/*` / `feature/*` 혼용을 정리할 것인가 (하나로 통일할지, 둘 다 허용할지)
- [ ] 브랜치 보호 규칙: 승인 인원·필수 상태 체크 구성은 이미 적용됨(§1 위 표, [PIPELINE.md §7](PIPELINE.md) 참고) — 추가로 조정할 항목이 있는지

## 2. 커밋 메시지

상세 양식: [template/COMMIT.md](template/COMMIT.md)

```
<prefix>: <한 줄 요약> (#이슈번호)

- 변경 사항 1
- 변경 사항 2
```

| prefix | 사용 시점 |
|--------|----------|
| `feat` | 신규 기능 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 (동작 변화 없음) |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 |
| `chore` | 빌드·설정·의존성 |
| `ci` | CI/CD 파이프라인 |

## 3. PR 규칙

상세 양식: [template/PR.md](template/PR.md)

- **제목**: `[타입] 작업 내용` — 예: `[Feat] 로그인 API 구현`
- **본문**: 템플릿 준수 (PR 생성 시 자동 적용), `Closes #N` 으로 이슈 연결
- **승인**: **1명 필수**
- **머지 방식**: **Merge commit 전용** (Squash · Rebase 비활성화) — 2026-07-29 변경
  - 머지 커밋 제목 = PR 제목 / 본문 = 비움
  - **개별 커밋이 그대로 히스토리에 남는다.** 따라서 커밋 하나하나가 의미 있는 단위여야 한다.
    "오타 수정", "wip" 같은 커밋을 남기지 말고, 필요하면 push 전에 정리한다.
  - ⚠️ 이 방식과 **선형 히스토리 필수**는 양립하지 않는다. 그래서 보호 규칙에서 해제했다.
- **머지 후**: 브랜치 **자동 삭제** (설정 적용됨)
- **리뷰어 자동 지정**: `.github/CODEOWNERS` 경로에 걸리면 소유자에게 리뷰 요청이 자동으로 간다

### PR 타입

| 타입 | 사용 시점 |
|------|----------|
| `[Feat]` | 기능 구현·추가 |
| `[Update]` | 기존 기능 수정·보완 |
| `[Fix]` | 오류·버그 수정 |
| `[Ref]` | 리팩토링·구조 개선 |
| `[Chore]` | 설정·빌드·문서 |

## 4. 이슈 규칙

상세 양식: [template/ISSUE.md](template/ISSUE.md)

- **제목**: `[타입] 작업 내용`
- **타입**: `[Feat]` `[Task]` `[Fix]` `[Ref]`
- 라벨·마일스톤·담당자는 GitHub 우측 필드에서 지정

### 라벨 (2026-07-28 적용 완료)

| 라벨 | 용도 | 대응 타입 |
|------|------|----------|
| `feature` | 기능 구현·추가 | `[Feat]` |
| `bug` | 오류·버그·예외 수정 | `[Fix]` |
| `task` | 기능 외 작업 — 설정·인프라·문서·조사 | `[Task]` |
| `refactor` | 리팩토링·구조 개선 | `[Ref]` |
| `chore` | 빌드·설정·의존성 | `[Chore]` |
| `infra` | 인프라·CI/CD·배포 | — |
| `documentation` | 문서 작업 | — |

> 이슈 템플릿을 쓰면 `feature` / `bug` / `task` 는 자동으로 붙는다.
> GitHub 기본 라벨(`enhancement`, `duplicate`, `wontfix` 등)은 혼란을 줄이기 위해 삭제했다.

> ⚠️ **실제로는 위 7개 외에 도메인 라벨 11종이 추가로 존재한다** (`gh label list` 실측, 2026-08-16):
> `Notification`, `Finance`, `Project`, `Log`, `Issue`, `Approval`, `Auth`, `employee`, `file`, `vitamate`, `bid`.
> 이 문서에는 규칙이 없다 — 이슈를 어느 도메인 라벨과 묶을지는 팀 관행으로 붙여지고 있는 것으로 보인다.
> 표준화 여부는 확인 필요.

**🔴 논의 필요**
- [ ] GitHub Projects 사용 여부
- [ ] 우선순위 라벨(`P0`/`P1`/`P2`) 도입 여부

## 5. 코드 리뷰

- **승인 1명**이 있어야 머지된다. (브랜치 보호로 강제)
- 리뷰 코멘트는 **전부 해결(resolve)** 해야 머지 버튼이 열린다.
- 승인 후 새 커밋을 푸시하면 **기존 승인이 무효화**된다. 다시 받아야 한다.
- `.github/CODEOWNERS` 에 걸린 경로는 소유자에게 리뷰가 자동 요청된다.

**🔴 논의 필요**
- [ ] 리뷰 응답 기한 (예: 24시간 내)
- [ ] 자동 리뷰 도구 도입 여부 (CodeRabbit 등)
