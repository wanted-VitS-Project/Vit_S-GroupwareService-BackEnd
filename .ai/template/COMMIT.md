# 📝 커밋 메시지 양식

> ⚠️ **AI 는 선제적으로 커밋·푸시하지 않는다.** 기본은 아래 양식대로 **메시지 텍스트만 제공**하는 것이다.
> 사용자가 **"커밋해" · "푸시해" 라고 명시적으로 요청할 때만** `git add` / `git commit` / `git push` 를 실행한다.
> **PR·이슈 생성은 여전히 사용자 몫이다** (`AGENTS.md` §9).
> (2026-08-03 완화 — 이전 규칙은 실행 전면 금지였다)

---

## 양식

```
<prefix>: <한 줄 요약> (#이슈번호)

- 변경 사항 1
- 변경 사항 2
- 변경 사항 3
```

## prefix

| prefix | 사용 시점 |
|--------|----------|
| `feat` | 신규 기능 추가 |
| `fix` | 버그·오류 수정 |
| `refactor` | 리팩토링 (동작 변화 없음) |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 작성·수정 |
| `chore` | 빌드·설정·의존성 |
| `ci` | CI/CD 파이프라인 |

## 작성 규칙

- 요약은 **명령형 현재시제**, 마침표 없이. (`추가함` ❌ → `추가` ✅)
- 요약 줄은 50자 이내 권장.
- 본문 bullet 은 **2~4개**. 실제 변경 파일 기준으로 작성.
- 이슈 번호가 없으면 `(#이슈번호)` 를 생략한다.
- 하나의 커밋에 서로 다른 성격의 변경을 섞지 않는다.

## 작성 절차

1. `git status` / `git diff` 로 변경 파일과 내용 확인
2. 변경의 성격을 보고 prefix 판단
3. 요약 + bullet 작성
4. 사용자에게 **텍스트로 제공**
5. 사용자가 **명시적으로 커밋을 요청한 경우에만** 실행한다
   - 성격이 다른 변경은 **커밋을 나눈다** (하나의 커밋에 섞지 않는다는 규칙의 연장)
   - 커밋 전 `./gradlew build` 로 빌드가 깨지지 않는지 확인한다
   - 커밋을 나눴다면 **중간 커밋도 단독으로 빌드되는지** 확인한다 (CI 가 커밋 단위로 돌 수 있다)

## 예시

```
feat: 이메일 인증 코드 발송 API 구현 (#12)

- EmailVerificationService 추가
- 6자리 코드 생성 및 Redis 5분 TTL 저장
- SMTP 설정을 application.yml 환경변수로 분리
```

```
ci: PR 빌드·테스트 워크플로우 추가 (#3)

- push/PR 트리거로 gradle build + test 실행
- Gradle 캐시 적용으로 빌드 시간 단축
```
